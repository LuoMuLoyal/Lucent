# 2026-09-11

## fix(assistant): SSE 响应丢失 CORS 头导致浏览器端流被拦截

现象（Web 端，页面 origin 与 API 不同源）：助手发送消息后前端报
`DioException [connection error]`（内层 `LucentFailure(network/connectionError)`），界面显示
「这次回复没有完成 / 连接中断了」，而后端日志显示同一次
`POST /api/v1/user/assistant/messages/stream` **200 正常完成**（2667ms）——两侧日志一成一败。

排查：服务端成功、客户端报连接错误，说明失败发生在响应进入浏览器之前。用带 `Origin` 的探针请求
对比三类响应头：

- `GET /assistant/capabilities`（普通 JSON 端点）→ 有 `access-control-allow-origin`
- `OPTIONS /assistant/messages/stream`（预检）→ 有
- `POST /assistant/messages/stream`（SSE 本体）→ **没有**

浏览器因此判定跨域响应不可读，XHR 触发 `onError` → dio `DioExceptionType.connectionError`
（时间点在请求发出后数百毫秒，即服务端刚 flush 完响应头时）；服务端不受影响继续写完
chunk 并记 200，于是出现「客户端已中断、服务端仍成功」的错位。

根因：`prepareSse()` 直接对 `reply.raw` 调 `writeHead()`，绕过了 Fastify 的 reply pipeline，
而 `@fastify/cors` 是通过 `reply.header()` 暂存头部的——这些头只在 `reply.send()` 路径上落到
raw response。对照：helmet 用 `reply.raw.setHeader`，所以安全头在 SSE 响应上一直存在，
这正解释了为什么只有 CORS 头缺失。

修复：

- `src/common/api/sse/sse.ts`：`prepareSse()` 新增 `inheritedHeaders` 参数并合并进
  `writeHead()`（SSE 协议头优先），JSDoc 写明「raw 写头必须显式转发 reply 头，否则
  `@fastify/cors` 头丢失、浏览器判定跨域失败」。
- 4 个 SSE 端点改为传 `reply.getHeaders()`：`assistant`（messages/stream、regenerate）、
  `reports`（summary/generate/stream）、`today-analysis`（generate/stream）。

测试：

- `sse.spec.ts`：新增「转发插件注册头（CORS）」与「同名键冲突时 SSE 头优先」两例。
- `assistant.controller.spec.ts` / `today-analysis.controller.spec.ts` /
  `reports.controller.spec.ts`：reply mock 补 `getHeaders()`，并断言携带的头进入 `writeHead`。
- `test/e2e/assistant/assistant.e2e-spec.ts`：新增「跨域调用时 SSE 响应带
  `access-control-allow-origin`」；负向对照（临时去掉 `reply.getHeaders()`）该用例报
  `expected undefined to be 'http://localhost:9100'`，确认用例真的守得住此回归。

验证：全量单测通过；`pnpm typecheck`、`pnpm lint:check` 通过；assistant e2e 通过。
API 契约未变（响应 schema、路径、状态码均未动），无需 `pnpm export:openapi`。
