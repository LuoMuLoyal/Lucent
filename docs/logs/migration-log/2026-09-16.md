## fix(assistant): 餐食 digest 上限提示不再谎报「你请求了 N 条」

（来源：2026-09-11 至 09-15 五日审查报告的 warning 项，报告已处理完毕、文件已删。）

### 背景

`limitCapped` 的判定是 `analyzed.length > limit.value`——「窗口内已分析餐食多于单次返回
上限」，与模型是否传过 `limit` 无关。但提示文案回落成 `requestedLimit ?? digest.limit`，
于是模型**没传** `limit` 时渲染出：

> Requested 20 meals, but the digest returns at most 20 analyzed meals.

两个数字相同，且它根本没请求过。这段文本是给 LLM 读的（写进 `ambiguities` 让它知道自己
拿到的是哪一段），自相矛盾的说明会直接污染模型对结果完整性的判断。

注意报告里的推断（`requestedLimit` 为 null 时回落）方向对，但成因不是 `clampPositiveInt`
——那个函数的 `capped: true` 必然伴随非空 `requested`；真正的成因是上面 `limitCapped` 的
判定本身与「请求」无关。

### 变更

- `src/modules/assistant/tools/shared/tool-constants.ts`：
  `MEAL_DIGEST_LIMIT_CAP_MESSAGE` 接受 `requestedLimit: number | null`，为 null 时改说
  「窗口内已分析餐食多于单次返回上限，只含最新 N 条」。同时给 `MEAL_DIGEST_DAYS_CAP_MESSAGE`
  同样的 null 分支——它的 `?? windowDays` 目前不可达（封顶必伴随非空 `requested`），
  但保留同样的兜底措辞，免得将来封顶条件变化时又出现同类自相矛盾的句子。
- `src/modules/assistant/tools/read/read.service.ts`：两处调用点不再 `?? ` 回落，直接把
  可空值交给文案函数。

注：这两段文案都不是面向用户的界面文案，是工具返回里给模型看的 `ambiguities`。

### 验证

- `src/modules/assistant/tools/read/read.service.spec.ts` 补两条用例：未传 `limit` 时提示
  不含「Requested」且给出上限数字；传了 `limit: 99` 时仍如实说「Requested 99」。
- 反向验证：临时恢复 `?? digest.limit`，新用例如期失败并**原样重现**了上面那句
  `Requested 20 meals, but the digest returns at most 20 analyzed meals.`；恢复后通过。
- `npx vitest run` 两个相关 spec 全绿；`pnpm typecheck`、`npx eslint` 无问题。

## test(reports,assistant): 锁住 SSE 头确实走到了裸 socket

（来源：2026-09-11 至 09-15 五日审查报告的 warning 项，报告已处理完毕、文件已删。本轮无行为改动。）

### 背景

`prepareSse` 直接对裸 response `writeHead`，因此绕过了框架 reply 管线——只有把
`reply.getHeaders()` 显式传进去，插件注册的头（`@fastify/cors`、`vary: Origin`）才能到
socket；少了它浏览器会以 CORS 失败为由直接断开流。

三个 SSE 端点的**实现**都是对的（五处 `prepareSse` 调用全都传了 `getHeaders()`），
但测试对这条的覆盖参差不齐。核对实际情况如下（与报告的推测有出入）：

- `today-analysis`：用真实 `prepareSse` 断言 `writeHead` 同时收到 CORS 头与
  `Content-Type` —— 已经是对的，无需改动。
- `assistant`：只断言 `prepareSse` 收到了第 4 个参数，且 fixture 的
  `getHeaders()` 返回 `{}` —— 断言存在，但传空对象时**丢掉 `getHeaders()` 也照样通过**，
  实际没有防护力。（另一个端点 `regenerateLastMessage` 的断言早已带真实头。）
- `reports`：`getHeaders: () => ({})` 写死，且完全没有对 `writeHead` 的断言 —— 真缺口。

`prepareSse` 本身（含 CORS 透传与键冲突时 SSE 协议头优先）已有专项 spec，覆盖良好，
缺的是「各端点确实把 `getHeaders()` 传下去了」。

### 变更

- `src/modules/reports/reports.controller.spec.ts`：`makeMockReply` 的 `getHeaders`
  改为可注入（默认仍为空对象），SSE 用例带上真实 CORS 头并断言 `writeHead` 收到
  CORS 头与 `Content-Type: text/event-stream; charset=utf-8`。
- `src/modules/assistant/assistant.controller.spec.ts`：SSE 用例的 fixture 带上真实
  CORS 头，断言随之改为校验真实头对象（空对象断言 ⇒ 真实头断言）。

### 验证

## fix(common): Error 日志的堆栈改回字符串并清掉空 error 字段

（来源：2026-09-11 至 09-15 五日审查报告的 warning 项，报告已处理完毕、文件已删。报告的归因有误，
实际缺陷与描述不同，见下。）

### 背景

`logger.error(new Error('boom'))` 是 NestJS 的惯用写法，nest-winston 会把 Error 当**元数据**
转发，Winston 于是产出：

```json
{
  "context": "CtxTwo",
  "error": {},
  "level": "error",
  "message": "boom",
  "stack": ["Error: boom\n    at ..."]
}
```

两个真实的缺陷（用 nest-winston + 本仓 format 实测复现，非推测）：

- `stack` 是**数组**而不是字符串。开发格式的 `devConsoleFormat` 里 `printf` 只认
  `typeof info['stack'] === 'string'`，所以**开发环境下 Error 的堆栈从来没被打印过**；
  JSON 消费者（VictoriaLogs / Loki）也拿到不符合字符串预期的形态。
- `error: {}` 序列化后不含任何信息（Error 的自有可枚举属性为空），却留在日志里冒充数据。

报告原本的说法（`_msg` 在 `manuallyRegisterLogger` 里丢失）在本仓不可达，已实测排除；
但顺着它检查这条链路时发现了上面两个真问题。

### 变更

- `src/common/logger/logger.config.ts`：新增 `errorNormalizeFormat`，接在两种格式的
  `otelTraceFormat` **之前**，让两个 sink 看到同一形态：
  - 数组 `stack` 拼成单个字符串（空数组则整个删掉）；
  - `error` 为空对象时删掉；带真实数据时原样保留；
  - 已经是字符串的 `stack` 不动。

### 验证

- `src/common/logger/logger.config.spec.ts` 新增 6 条用例：数组 stack 展平、空 error 删除、
  有内容的 error 保留、字符串 stack 不动、空数组 stack 删除，以及**开发格式下堆栈确实
  被打印**（直接断言输出含 `at one`）。
- 反向验证：临时从两种格式里摘掉 `errorNormalizeFormat`，6 条中 4 条如期失败；
  恢复后通过。
- `npx vitest run src/common/logger` 全绿；`npx eslint`、`pnpm typecheck` 无问题。
