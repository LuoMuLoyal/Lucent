## test(config): 补缓存跳过 Redis 分支的用例

（来源：`plans/Lucent-review-2026-09-11-to-09-15.md` 的 warning 项。）

### 背景

`CacheConfigService` 在 `OPENAPI_EXPORT_SKIP_REDIS === 'true'` 时退回内存 store，
这条分支是给「没有 Redis 的 CI 里跑 OpenAPI 导出」用的，但此前没有用例覆盖：
两个既有用例一个只给 `REDIS_URL` 传 undefined，另一个对所有 key 都返回同一个
`rediss://` 字符串（因此恰好走的是 `!== 'true'` 那一侧）。

### 变更

- `src/config/services/cache.config.spec.ts`：补两条用例——`OPENAPI_EXPORT_SKIP_REDIS`
  为字面量 `'true'` 时退回内存且不建 Keyv store；为其它值（`'false'`）时仍走 Redis。
  按 key 分派的 mock 取代了原先「所有 key 同一个返回值」的写法。

### 验证

- `npx vitest run src/config/services/cache.config.spec.ts` 全绿。
- 反向验证：临时去掉 `OPENAPI_EXPORT_SKIP_REDIS` 判断，skip 用例如期失败；
  恢复后通过。

## docs(daily-records): 记录餐食分析 v1 历史记录的展示表现

（来源：`plans/Lucent-review-2026-09-11-to-09-15.md` 的 warning 项。本轮无行为改动。）

### 背景

餐食分析 v2 重构把 `payload` 收敛成只有 `mealAnalysis` 一个键，并要求 `version: 2`。
但这次重构**改变了已存在记录的可见行为**，此前只在类型文件里写了形状差异，没写用户可见后果：

- v1→v2 新增的热列（状态/标题/热量/revision）在旧行上全是默认值（null / 0），
  读路径据此按「没有分析」处理；
- `mealAnalysisPayloadSchema` 的 `version: 2` 校验让 v1 的 `mealAnalysis` 被判为
  形状不匹配，`parseMealRecordPayload` 直接置 null。

合起来的结果是：**迁移之前已经分析过的餐食记录，客户端不再显示分析结果。**

### 变更

- `src/modules/daily-records/types/meal-analysis.types.ts`：在读写路径的头注释里补上这段
  表现，并写明为什么不回填——v1 的自由形状 `mealInput` 与人工确认快照，和 v2 的一次
  多模态直出模型没有可靠映射，猜出来的分析结论比「没有结论」更糟；用户对该记录重新
  发起一次分析即可拿到 v2 数据。
- `docs/TODO.md`：登记 B7（P3），把「若产品要求旧记录可见」的验收口径固定为**重新分析**
  而非数据迁移。

### 验证

- `pnpm docs:verify` 通过；`npx eslint` 对改动文件无告警。
- 本轮不改代码行为，未新增测试。
