## test(config): 补缓存跳过 Redis 分支的用例

（来源：`plans/Lucent-review-2026-09-11-to-09-15.md` 的 warning 项。）

### 背景

`CacheConfigService` 在 `OPENAPI_EXPORT_SKIP_REDIS === 'true'` 时退回内存 store，
这条分支是给「没有 Redis 的 CI 里跑 OpenAPI 导出」用的，但此前没有用例覆盖：
两个既有用例一个只给 `REDIS_URL` 传 undefined，另一个对所有 key 都返回同一个
`rediss://` 字符串（因此恰好走的是 `!== 'true'` 那一侧）。

### 变更

- `src/config/services/cache.config.spec.ts`：补两条用例——`OPENAPI_EXPORT_SKIP_REDIS`
  为字面量 `'true'` 时退回内存且不建 Keyv store；为其它值（`'false'`）时仍走 Redis。
  按 key 分派的 mock 取代了原先「所有 key 同一个返回值」的写法。

### 验证

- `npx vitest run src/config/services/cache.config.spec.ts` 全绿。
- 反向验证：临时去掉 `OPENAPI_EXPORT_SKIP_REDIS` 判断，skip 用例如期失败；
  恢复后通过。

## docs(daily-records): 记录餐食分析 v1 历史记录的展示表现

（来源：`plans/Lucent-review-2026-09-11-to-09-15.md` 的 warning 项。本轮无行为改动。）

### 背景

餐食分析 v2 重构把 `payload` 收敛成只有 `mealAnalysis` 一个键，并要求 `version: 2`。
但这次重构**改变了已存在记录的可见行为**，此前只在类型文件里写了形状差异，没写用户可见后果：

- v1→v2 新增的热列（状态/标题/热量/revision）在旧行上全是默认值（null / 0），
  读路径据此按「没有分析」处理；
- `mealAnalysisPayloadSchema` 的 `version: 2` 校验让 v1 的 `mealAnalysis` 被判为
  形状不匹配，`parseMealRecordPayload` 直接置 null。

合起来的结果是：**迁移之前已经分析过的餐食记录，客户端不再显示分析结果。**

### 变更

- `src/modules/daily-records/types/meal-analysis.types.ts`：在读写路径的头注释里补上这段
  表现，并写明为什么不回填——v1 的自由形状 `mealInput` 与人工确认快照，和 v2 的一次
  多模态直出模型没有可靠映射，猜出来的分析结论比「没有结论」更糟；用户对该记录重新
  发起一次分析即可拿到 v2 数据。
- `docs/TODO.md`：登记 B7（P3），把「若产品要求旧记录可见」的验收口径固定为**重新分析**
  而非数据迁移。

### 验证

- `pnpm docs:verify` 通过；`npx eslint` 对改动文件无告警。
- 本轮不改代码行为，未新增测试。

## fix(assistant): 餐食 digest 上限提示不再谎报「你请求了 N 条」

（来源：`plans/Lucent-review-2026-09-11-to-09-15.md` 的 warning 项。）

### 背景

`limitCapped` 的判定是 `analyzed.length > limit.value`——「窗口内已分析餐食多于单次返回
上限」，与模型是否传过 `limit` 无关。但提示文案回落成 `requestedLimit ?? digest.limit`，
于是模型**没传** `limit` 时渲染出：

> Requested 20 meals, but the digest returns at most 20 analyzed meals.

两个数字相同，且它根本没请求过。这段文本是给 LLM 读的（写进 `ambiguities` 让它知道自己
拿到的是哪一段），自相矛盾的说明会直接污染模型对结果完整性的判断。

注意报告里的推断（`requestedLimit` 为 null 时回落）方向对，但成因不是 `clampPositiveInt`
——那个函数的 `capped: true` 必然伴随非空 `requested`；真正的成因是上面 `limitCapped` 的
判定本身与「请求」无关。

### 变更

- `src/modules/assistant/tools/shared/tool-constants.ts`：
  `MEAL_DIGEST_LIMIT_CAP_MESSAGE` 接受 `requestedLimit: number | null`，为 null 时改说
  「窗口内已分析餐食多于单次返回上限，只含最新 N 条」。同时给 `MEAL_DIGEST_DAYS_CAP_MESSAGE`
  同样的 null 分支——它的 `?? windowDays` 目前不可达（封顶必伴随非空 `requested`），
  但保留同样的兜底措辞，免得将来封顶条件变化时又出现同类自相矛盾的句子。
- `src/modules/assistant/tools/read/read.service.ts`：两处调用点不再 `?? ` 回落，直接把
  可空值交给文案函数。

注：这两段文案都不是面向用户的界面文案，是工具返回里给模型看的 `ambiguities`。

### 验证

- `src/modules/assistant/tools/read/read.service.spec.ts` 补两条用例：未传 `limit` 时提示
  不含「Requested」且给出上限数字；传了 `limit: 99` 时仍如实说「Requested 99」。
- 反向验证：临时恢复 `?? digest.limit`，新用例如期失败并**原样重现**了上面那句
  `Requested 20 meals, but the digest returns at most 20 analyzed meals.`；恢复后通过。
- `npx vitest run` 两个相关 spec 全绿；`pnpm typecheck`、`npx eslint` 无问题。

## fix(daily-records): 过期回收改用独立的作业丢失失败码

（来源：`plans/Lucent-review-2026-09-11-to-09-15.md` 的 warning 项。**跨仓契约变更**。）

### 背景

`MealAnalysisSweeperService` 回收超时仍停在 `analyzing` 的记录时写
`analysis_failed(model_timeout)`，但它自己的注释（以及 `MEAL_ANALYSIS_STALE_AFTER_MS`
的注释）写的是「作业已经丢失：进程崩溃、队列丢单、Redis 数据被清」——判定的是
**作业没跑完就没了**，不是**模型调用超时**。两者对用户的补救动作一样（重试），但故障
归因完全不同，混成一个码会让「模型超时」的告警淹没有真实基础设施故障的时段。

（`model_timeout` 仍在用，且用法正确：`worker.service.ts` 的模型调用超时映射。）

### 变更

- `schemas/meal-analysis.schema.ts`：失败原因码词表新增 `job_lost`，并写明它与
  `model_timeout` 的区别是责任方（谁该被叫醒）。
- `services/meal-analysis/sweeper.service.ts`：落 `job_lost`（含日志文案）。
- `constants/meal-analysis.constants.ts`、`dto/record-item.dto.ts`：同步注释与契约描述。
- `docs/reference/generated/openapi.json`：`pnpm export:openapi` 重导出。
- 对侧（Luminous）：`analysis_summary_card.dart` 增加 `job_lost` 的 l10n 分支并新增
  `recordMealAnalysisFailureJobLost`（中「分析中断了，请重试」/ 英），跑 merge + gen-l10n；
  `dart run scripts/contract/bootstrap.dart` 重生成客户端。

### 验证

- 契约影响面已核对：该字段在契约里是普通 `string`（不是生成枚举），所以新增取值
  **不产生**生成客户端的编译破坏——`openapi.json` 与 `generated/lucent_api` 的 diff
  都只有描述文本变化。
- 客户端有 `_ =>` 通用兜底，未知码不会白屏；新增分支由既有参数化用例覆盖，
  该用例显式枚举每个码，因此**必须同步加一项**才真正覆盖（已验证：临时删掉分支，
  用例如期报 `Found 0 widgets with text "分析中断了，请重试"`）。
- `sweeper.service.spec.ts` 期望值同步为 `job_lost`。
- Lucent：`npx vitest run` 全绿（含 17 个 daily-records spec）、`pnpm lint:check` 0 warning
  0 error、`pnpm typecheck` 通过。
- Luminous：`flutter analyze` 无问题、`flutter test test/record` 全绿、
  `dart run scripts/docs/verify.dart --verify` 通过。

## test(daily-records): 补餐食 payload 写入服务的单元用例

（来源：`plans/Lucent-review-2026-09-11-to-09-15.md` 的 warning 项。本轮无行为改动。）

### 背景

`MealPayloadWriterService` 是「客户端提交 → 落库 payload」的唯一闸门，四个公共方法各自
带独立的早返回（无既有分析、图片数量不为 1、状态不是 analyzing、无 payload 等），
但它此前没有自己的 spec——只被 `records.service.spec.ts` 的端到端路径间接覆盖，
单条分支（尤其「多张图不置 analyzing」「revision 覆盖与状态判定读法不同」）测不到。

### 变更

- `src/modules/daily-records/services/meal-payload-writer.service.spec.ts`：新增，18 条用例
  按方法分组，覆盖每个早返回、客户端菜名编辑（标记 `source: 'user'`、不重算结论）、
  恰好一张图时的入队占位与 revision 递增、热列投影、以及入队的四种分支。

### 验证

- `npx vitest run src/modules/daily-records` 全绿；`npx eslint`、`pnpm typecheck` 无问题。
- 用例有效性：临时把 `attachments.length !== 1` 放宽成只判 null，5 条用例如期失败；
  恢复后通过。

  半截形状，本轮不改（只加用例记录差异，改动其一时必须同时面对）。
