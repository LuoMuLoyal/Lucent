## 校验失败可诊断性:保留 Standard Schema issue 的 path

来源:2026-09-15 UI 巡检中「3 条 dose_log 同步失败永久卡在队列、`VALIDATION_FAILED`/400
无法定位字段」的问题。核实结论:`.strict()` schema 拒绝未知键时,内置
`StandardSchemaValidationPipe` 的默认 exception factory 只把 issue 压平成
`["unrecognized_keys"]` 之类的 message 字符串,`ApiExceptionFilter.resolveErrors` 对
`Array.isArray(message)` 走 `{ general: [...] }` 分支,`issues[].path` 被彻底丢弃,
客户端拿不到任何字段线索。

### 改动

- 新增 `src/common/filters/validation-exception.ts`:`ValidationException`
  (继承 `BadRequestException`),把 issue 列表结构化为 `errors.issues[] = {path, message}`;
  `message` 保留人类可读摘要供日志使用。
- `src/setup-app.ts`:`StandardSchemaValidationPipe` 传入 `exceptionFactory`,
  将 `path`(含 Standard Schema 的 `PathSegment.key` 解包)与 `message` 映射为
  `ValidationIssue`。status 仍为 400、code 仍由 filter 回落为 `VALIDATION_FAILED`,
  线上行为只在 `errors` 字段上变丰富,不改变既有 status/code 语义。
- `src/common/filters/api-exception.target.spec.ts`:新增用例断言 `errors.issues[0].path`
  到达 problem+json body。

### 验证

- `pnpm typecheck` 通过;`vitest run src/common/filters/api-exception.target.spec.ts`
  10 项通过。
- `@standard-schema/spec` 的 `Issue` 类型只有 `message`/`path?`,不含 zod 私有的
  `code`,故 `ValidationIssue` 不声明 `code`,避免绑定 zod 实现细节。

## 助手把上游模型故障映射为 dependency 失败

巡检「AI chat 稳定返回 This reply did not complete」的根因放大器:模型不可用时用户
只能看到通用错误卡。核实链路:`stream-orchestrator.service.ts` / `agent/runtime.service.ts`
的 `toDomainFailure` 只识别 `DomainFailureException`,上游 provider 的 4xx/5xx 直接逸出为
原始异常 → `sse-problem-details.ts` 按 statusCode 回落为 `INTERNAL_ERROR` /
`VALIDATION_FAILED` → 客户端 `conversation_sending.dart` 把一切非网络失败折叠为 `server`
→ 恒定渲染通用错误卡,且「Continue generating」逐字节重发同一请求。

### 变更

- 新增 `services/provider-failure.ts`:`classifyProviderFailure` 读取 `status` /
  `response.status` / `statusCode` 三种形态,映射为 dependency 级失败 ——
  429→`DEPENDENCY_UNAVAILABLE`(可重试);408/504→`DEPENDENCY_TIMEOUT`(可重试);
  5xx→`DEPENDENCY_BAD_GATEWAY`(可重试);400/404/422→`DEPENDENCY_UNAVAILABLE`
  **`retryable: false`**(模型下线/请求被永久拒绝,重放无意义);
  401/403→`DEPENDENCY_UNAVAILABLE`(凭据或配额,可重试且与通用错误区分)。
  无法识别者返回 null,仍走原有 rethrow,不吞其他异常。
- `stream-orchestrator.service.ts` / `agent/runtime.service.ts`:`toDomainFailure` 接入该分类。
- 客户端 `conversation.dart`:`AssistantSendErrorType` 增加 `dependency` / `modelRejected`;
  `conversation_sending.dart` 按 Problem Details code + `retryable` 分流;
  `ui_formatters.dart` 补两条文案分支;**`above_composer.dart` 不再对 `modelRejected`
  渲染「继续生成」**(确定性拒绝,重试必然同样失败)。
- `l10n/src/assistant_{en,zh}.arb`:新增 `assistantErrorDependency` /
  `assistantErrorModelRejected`。

## Review 覆盖卡 delta 与「数据不足」不再并存

巡检「Month 视图 Water 卡同时显示 Too little data、`--` 与 `+0.0`」。核实结论:
颜色判断(原报告称 +0.0 是绿色)有误 —— `_DeltaLabel` 把 `flat` 映射为 neutral;
真问题是**显示闸门漏判 sparse**,以及**零变化误带 `+` 号**。

- 后端 `computation.service.ts` 的 `deltaNumber` 取值口径要求 `coverage === 'sufficient'`
  且 `observedCount >= 2`,**严于**客户端卡片的 `coverage != none && observedCount >= 2`,
  于是 `coverage: partial` 且观测 ≥2 时后端照发真实 delta,而卡片主值仍显示 `--`。
- `coverage_strip.dart:147` 的 delta 渲染条件只判 `delta` 非空,未纳入 `sparse`。
- `+0.0` 的 `+` 来自 `deltaNumber` 的 `delta >= 0 ? '+' : ''`,零变化被赋予正号。

### 变更

- `coverage_strip.dart`:delta 渲染条件补 `!sparse`(主值已显示 `--` 时给出确定的变化量
  与「数据不足」自相矛盾)。
- `computation.service.ts`:`deltaNumber` 符号条件由 `delta >= 0` 改为 `delta > 0`,
  零变化输出 `0.0`。负号与正号行为不变。
- 两侧各补回归断言:客户端「sparse 隐藏 delta」「非 sparse 仍渲染 delta」;
  后端「零变化无正号」「真实增减保留符号」。

### 验证

- Luminous:`coverage_strip_test.dart` 6 项通过。
