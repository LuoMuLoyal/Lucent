## fix(medicines): searchText 不再进入 matchedBy,查询改两层 OR

（来源：2026-09-17 审查报告 W1/S5，报告 `plans/Lucent-review-09-17.md` 保留中。）

### 背景

搜索响应的 `matchedBy` 此前会把预拼接的内部索引字段 `searchText`（import 脚本已含
name/CAS/UNII/ids/groups/前 20 synonyms）一并上报，命中任一业务字段时同时返回
`[name, searchText]` 等重复键，前端无法判断真实命中字段。

### 变更

- `src/modules/medicines/adapters/drugbank.service.ts` / `cn.service.ts`：
  `toSearchItem` 不再把 `searchText` 喂给 `detectMatchedBy`，只保留业务键
  （drugbank：name/casNumber/unii + synonyms；cn：name/brandName/approvalNumber/
  barcode/nationalDrugCode）。
- 同文件 `buildWhere` 由 4~6 个并列 OR 改为「searchText 主发现 + 业务字段嵌套 OR
  兜底导入遗漏」的两层结构（消除 searchText 覆盖 name/CAS/UNII 的冗余匹配路径）。

### 验证

- 新增单测：两个 adapter 各增「matchedBy 只含业务键、不含 searchText」用例，
  buildWhere 断言更新为两层 OR 结构。
- 全量 `pnpm test`：322 files / 3821 tests 全绿；`pnpm typecheck`、`pnpm build`、
  `pnpm lint:check` 通过。

## fix(medicines): 缓存读写失败降级而非抛错

（来源：2026-09-17 审查报告 W2，报告 `plans/Lucent-review-09-17.md` 保留中。）

### 背景

`cacheGet` / `cacheSet` 的 try/catch 只 `logger.warn` 后直接 `throw`，catch 实质冗余：
缓存抖动会把药品读请求变成 500，与「缓存故障应当被捕获降级」的注释意图不符。

### 变更

- `src/modules/medicines/cache/store.service.ts`：`cacheGet` 失败返回 `undefined`，
  `getOrSet` 把它当 miss 走 `load()` 穿透读；`cacheSet` 失败 swallow（读已成功，
  写失败只影响下次请求）。保留 try-catch + warn（AGENTS 要求 cache 调用必须保护）。

### 验证

- `store.service.spec.ts` 增两用例：cache get 抛错时仍返回 load 结果、cache set
  抛错时业务返回不受影响。

## build(docker): 生产镜像瘦身 —— 去掉 chown 重复层,并把运行时资产剪到必需

### 背景

镜像 pull 体积已从 6 月的 248 MB 涨到 589 MB(本地未压缩 3.63 GB),逐层实测发现其中
逾四成与依赖增长无关:`RUN chown -R lucent:lucent /app`(2026-07-11 d2fe01ba 引入)
把整份 `/app`(含 1.35 GB `node_modules`)重新落地成一个新层,即白送一份 264 MB(压缩后)
的重复内容。生产依赖本身没有问题——镜像内 `.pnpm` 的 1529 个包与干净
`pnpm install --prod` 逐条一致,`pnpm prune --prod` 生效。`dist/` 里也没有多余静态资源
(仅编译 JS + i18n JSON);真正的大块静态资产藏在生产依赖里(字体包、Scalar 图标源码、
Prisma Studio、AdminJS 设计系统等)。

### 变更

- `Dockerfile` 生产阶段改为全部 `COPY --chown=lucent:lucent`(entrypoint 用
  `--chmod=755`),删除 `RUN chown -R /app`;仅保留 `RUN chown lucent:lucent /app`
  改工作目录属主——`AdminJS.initialize` 要在 cwd 下建 `.adminjs`,`/app` 归 root 时
  容器启动即 `uncaughtException: EACCES: permission denied, mkdir '.adminjs'`。
- builder 阶段 `pnpm prune --prod` 后新增一步运行时瘦身,只删运行期读不到的东西:
  - `node_modules`/`dist` 下的 `*.map`(只有调试器 / `--enable-source-maps` 会读);
  - 包内 `*.md`(保留 `LICENSE*`/`NOTICE*`/`COPYING*` 以合规);
  - `@prisma/client` 中非 postgresql 的 query compiler `wasm-base64` 副本
    (本项目只用 PostgreSQL);
  - `@fontpkg` 自带的 `SourceHanSansSC-VF.ttf.woff2`(`pdf-fonts.ts` 只 resolve OTF);
  - `swagger-ui-dist`(`@nestjs/swagger` 仅在 `SwaggerModule.setup()` 内 require,
    本项目用 Scalar 提供 `/api/docs`,从未调用 setup);
  - `@scalar/icons` 与 `@phosphor-icons/core`(图标源码组件,已编译进
    `@scalar/api-reference/dist/standalone.js`);
  - 删除包后清理悬空的 pnpm 符号链接(busybox `find` 没有 `-xtype`,改用 shell 判存)。

## 校验失败可诊断性:保留 Standard Schema issue 的 path

来源:2026-09-15 UI 巡检中「3 条 dose_log 同步失败永久卡在队列、`VALIDATION_FAILED`/400
无法定位字段」的问题。核实结论:`.strict()` schema 拒绝未知键时,内置
`StandardSchemaValidationPipe` 的默认 exception factory 只把 issue 压平成
`["unrecognized_keys"]` 之类的 message 字符串,`ApiExceptionFilter.resolveErrors` 对
`Array.isArray(message)` 走 `{ general: [...] }` 分支,`issues[].path` 被彻底丢弃,
客户端拿不到任何字段线索。

### 改动

- 新增 `src/common/filters/validation-exception.ts`:`ValidationException`
  (继承 `BadRequestException`),把 issue 列表结构化为 `errors.issues[] = {path, message}`;
  `message` 保留人类可读摘要供日志使用。
- `src/setup-app.ts`:`StandardSchemaValidationPipe` 传入 `exceptionFactory`,
  将 `path`(含 Standard Schema 的 `PathSegment.key` 解包)与 `message` 映射为
  `ValidationIssue`。status 仍为 400、code 仍由 filter 回落为 `VALIDATION_FAILED`,
  线上行为只在 `errors` 字段上变丰富,不改变既有 status/code 语义。
- `src/common/filters/api-exception.target.spec.ts`:新增用例断言 `errors.issues[0].path`
  到达 problem+json body。

### 验证

- `pnpm typecheck` 通过;`vitest run src/common/filters/api-exception.target.spec.ts`
  10 项通过。
- `@standard-schema/spec` 的 `Issue` 类型只有 `message`/`path?`,不含 zod 私有的
  `code`,故 `ValidationIssue` 不声明 `code`,避免绑定 zod 实现细节。

## 服药记录匹配失败改用独立错误码

`dose-logs.service.ts` 的 `validationFailed()` 原本发 `VALIDATION_FAILED`,而该码是所有
400 的通用兜底(`api-exception.filter.ts` 的 `defaultCode`),客户端无法据此区分「请求体
格式非法」与「请求体合法但无法定位目标 slot」——前者重试无意义、后者可提示用户补标识。
两处调用点(无 `reminderId` 且无 `currentMedicineId`;`reminder` 与 `currentMedicineId`
互相矛盾)语义一致:请求体通过 schema 校验,但不足以确定要写入哪条服药记录。

### 改动

- `problem-catalog.ts`:新增 `DOSE_LOG_TARGET_UNRESOLVED`(400,`retryable: false`)。
- `i18n/{en,zh-CN}/common.json`:补 `problem_dose_log_target_unresolved_{title,detail}`。
- `domain-failure.ts`:`DOMAIN_FAILURE_KIND_BY_CODE` 登记该码 → `validation`
  (该映射表是 kind/code 一致性的唯一事实源,`createDomainFailure` 依赖其穷尽性)。
- `dose-logs.service.ts`:`validationFailed()` 改发新码,并注明与通用 400 的区分意图。
- `dose-logs.service.spec.ts`:两处断言同步为新码。

### 验证

- `pnpm typecheck` / `pnpm lint:check` 通过;`pnpm test` 全量 3822 项通过。
