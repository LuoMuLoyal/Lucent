## DrugBank 多值 JsonB 字段提升为关系表

`DrugbankDrug` 上有 6 个 JsonB 列只是"按药取整块"的实现方式，但它们的真实查询需求是**反查**与**横向筛选**，JsonB 下只能全表扫描 + 逐行解析。本次把其中需要关系语义的字段落成表，并删除对应 JsonB 列（留着会变成不再更新的第二份事实源）。

判断标准沿用「结构由查询方式决定，而不是数据形状」：只要一件事需要「哪些药和 X 有关系」或「哪些药满足某个内部字段条件」，就建表；只做「取一个药、看整块」的保持 JsonB。

## refactor(logger): 日志底座迁回 Pino（nestjs-pino），移除 Winston 适配债

### 为什么现在做

ADR-0007 初版（2026-07-12）把日志从 Pino 迁到 Winston，决定性理由是「pino transport 用
worker 线程直写 stdout fd，测试框架拦不住」。本次核实后确认两点前提都变了：

1. **日志不再写文件系统**：部署口径是「只写 stdout + VictoriaLogs，不挂日志卷」，
   `winston-daily-rotate-file` 早已移除。Winston 当初的文件轮转优势归零。
2. **那条决定性理由是 `transport` 的锅，不是 pino 的**：pino 的 `destination` 接受任意
   `WritableStream`，`pino-pretty` 支持「作为 stream」用法，`nestjs-pino` 的 `pinoHttp`
   直接接受 `[options, DestinationStream]`。进程内流不会被 worker 线程绕过。
   原判「非配置可修复」不成立。
3. `nestjs-pino` 在初版之后发了 v5（2026-08-31），`Logger` 与 NestJS `LoggerService`
   兼容，双 logger / API 风格两条理由也随之消解；同期 `winston` 停在 3.19.0（2025-12）。

### 改动

| 项           | 原（Winston）                                      | 新（Pino）                                                                   |
| ------------ | -------------------------------------------------- | ---------------------------------------------------------------------------- |
| 集成         | `nest-winston` `WinstonModule.forRootAsync`        | `nestjs-pino` `LoggerModule.forRootAsync` + `app.useLogger(app.get(Logger))` |
| 依赖         | `nest-winston` / `winston` / `winston-transport`   | `nestjs-pino` / `pino` / `pino-http`                                         |
| 开发格式     | `winston.format.printf` 组合                       | 进程内自定义 `Writable`（`createPrettyStream`）                              |
| 生产 sink    | `winston.transports.Console`                       | pino → stdout（fd 1）                                                        |
| VictoriaLogs | `VictoriaLogsTransport extends TransportStream`    | `VictoriaLogsStream extends Writable`                                        |
| trace 注入   | 自定义 `otelTraceFormat`                           | pino `mixin`                                                                 |
| Error 归一化 | `errorNormalizeFormat`（拼数组 stack、删空 error） | `serializers.error: stdSerializers.err`                                      |
| 级别热更新   | 改写 `winston.level` + 每个 transport              | `PinoLogger.root.level`                                                      |

JSON 字段契约保持不变：`level` 仍是字符串标签、`message`/`timestamp`/`context` 同名、
调用方元数据在顶层、活跃 span 内注入顶层 `trace_id`/`span_id`。

### 破坏性变更：调用点参数顺序

pino 方法是 `(obj, msg, ...interpolation)`。迁移前大量调用写成 `logger.error('msg', stack)` /
`logger.warn('msg', meta)`，在 pino 下第二实参会被当作插值值，**消息里没有占位符时静默丢弃**。
共迁移 **43 处**调用点（16 处 `(msg, meta)` 换序 + 27 处 `(msg, stack|error)` 改成
`({stack|error}, msg)`），并用脚本扫描确认无残留。这是本次唯一需要改业务代码的地方。

同时更新 4 处断言旧参数顺序的单测。

### 刻意的两个取舍

- **`base: null`**：不输出 `pid` / `hostname`，与旧形状一致（容器平台已带）。
- **`serializers.req/res` 返回 `undefined`**：不启用 pino-http 的请求绑定。应用已用 OTel
  trace id 关联并自建访问日志；pino-http 的 `req` 序列化器还会复制请求头（含凭据）。
