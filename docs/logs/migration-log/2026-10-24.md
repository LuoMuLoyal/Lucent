# 2026-10-24

## refactor(auth): cookie 会话端点改名，删除 /auth/me，设备清单改走 /auth/devices

- 背景：三处命名问题累积到该处理的程度——`/auth/me` 与 `/account` 是同一份用户资料的
  两个入口；`/auth/session/*`（登录会话）与 `/auth/sessions`（设备清单）只差一个字母，
  operationId `listSessions` 也没体现资源类型；Bearer 与 cookie 两条出口一个单数一个
  复数，看不出是「同一件事的两种投递方式」。
- 路径变更（**破坏性**，Lumine 与 Luminous 需同步重新生成客户端）：
  - `POST /auth/session/{register,login,refresh,logout}` → `POST /auth/sessions/{...}`。
    cookie 会话是**集合上的动作**（refresh 换一个成员、logout 删当前成员），单数读起来像
    「某一个具名会话」。
  - `GET /auth/sessions` → `GET /auth/devices`；`DELETE /auth/sessions/:sessionId` →
    `DELETE /auth/devices/:sessionId`。与登录会话彻底分开，也和运营侧
    `/admin/users/:id/sessions/:sessionId` 分开（用户自助 vs 运营）。
  - **删除 `GET /auth/me`**。账户资料的唯一读入口改为 `GET /account`（account 模块），
    它本来就更全：多 `hasPassword` / `lastLoginAt` / `linkedIdentities`。
- operationId 改为在 `@ApiOperation` 上显式声明，不再靠方法名推导：
  `registerWithCookie` / `loginWithCookie` / `refreshWithCookie` / `logoutWithCookie` /
  `listDevices` / `revokeDevice`。`plans/_naming-lookup.json` 同步（移除已删除的 `getMe`）。
- 响应形状取舍：会话响应里的 `user` 块**保持独立**，不与 `AccountDto` 合并。`hasPassword`
  需要额外查一次 `account` 表（`AuthIdentityService.hasPassword`），登录响应不该为一个
  布尔位多打一次库。两者字段交集一致，会话侧额外有 `emailVerified` 布尔位供登录态直接判断。
- 删除 `CookieSessionUseCase.currentUser()`：唯一调用方是已删除的 `/auth/me`。
- `SessionController.listSessions`/`revokeSession` 改名 `listDevices`/`revokeDevice`
  （控制器方法名跟随端点）；`AuthTokenService.listSessions` **保持不变**——那是仓储层
  概念，与 HTTP 资源名解耦。
- 契约变化：`openapi.json` paths 150→149，schemas 388 不变。Luminous 生成客户端新增
  `SessionResponse` / `SessionResponseUser` / `LoginWithCookieRequest` /
  `RegisterWithCookieRequest` 四个模型。
- 测试：`test/e2e/auth/session-cookie.e2e-spec.ts` 路径常量与断言同步（原 `/auth/me`
  用例改读 `/account`，并断言 `hasPassword`）；`test/security/authorization.e2e-spec.ts`
  的设备端点路径同步。
- 验证：`pnpm typecheck`、`pnpm lint:check`（0 error）、`pnpm arch:check`（205 entries，
  基线未新增）通过；`pnpm test` 全绿，`src/modules/auth` 406 passed；
  `pnpm export:openapi` 重生成（149 paths / 388 schemas）。

## feat(auth): `users.email` 改为可空，允许无邮箱的 OAuth 账号

- 背景：契约一直宣称 `AccountDto.email` 可为 null（注释「OAuth-only accounts may not
  have one」），但 `users.email` 是 `String @unique` 非空，且
  `AuthOAuthService.createOAuthUser` 对无邮箱的 profile 直接抛 `VALIDATION_FAILED`。
  **契约描述了一个 schema 禁止的能力**——微信等提供商不总是返回邮箱，这条路径从来
  走不通。本次让 schema 与契约一致。
- 模型：`prisma/models/user.prisma` 的 `email` 改为 `String?`，`@unique` 保留。
  PostgreSQL 的唯一索引把 NULL 视为互不相等，因此任意多个无邮箱账号可以共存，
  真实地址仍然唯一。迁移 `20261024160000_user_email_nullable` 只做
  `ALTER COLUMN email DROP NOT NULL`，无需回填（存量行都有邮箱）。
- OAuth：`createOAuthUser` 去掉「必须提供邮箱」的拒绝分支，改为 `...($profile.email != null && { email })`
  ——**省略字段**而不是写 null，让 Prisma 不产生列值。
- 查询陷阱（已写进 prisma 注释与迁移注释）：Prisma 的
  `where: { email: undefined }` 会**丢掉过滤条件**、`where: { email: null }` 会匹配
  任意无邮箱行。按邮箱查必须先用非空类型/守卫挡住 null。现有
  `AuthIdentityService.createLocalUser` 的入参是 `email: string`，类型层面已安全；
  `PasswordManagementService` 已有 `if (!user.email)` 守卫。
- 管理员侧取「必须有邮箱」的设计决定，不是数据问题：
  - `AdminAdminsService.toSummary` 遇到无邮箱的受让人抛
    `RESOURCE_CONFLICT`（无法投递、无法审计的管理员不应存在）；
  - `AdminAccessService.getIdentity` 把「无邮箱的管理员」视为无身份（返回 null →
    403），因为这道门在写入时已经拦过，走到这里说明是带外写入。
- 契约：`sessionUserSchema.email` 同步改为可空（它此前是 `z.string()`，与数据库及
  `AccountDto` 都不一致）。`openapi.json` paths 149 不变，schemas 388 不变。
- 测试：新增 `should create a user without an email when the provider discloses none`，
  钉住「省略 email 字段」而非写 null；e2e `sessions.e2e-spec.ts` 的设备端点路径上一批
  漏改，本次一并修正（此前 7 例因 `/auth/sessions` → `/auth/devices` 而红）。
- 验证：`pnpm db:migrate:all` 应用到 dev 与 test 库；`pnpm typecheck`、`pnpm lint:check`
  （0 error）、`pnpm arch:check`（205 entries）、`pnpm docs:verify` 通过；
  `pnpm test` 全绿，`src/modules/auth` 407 passed；`pnpm test:e2e:ci` 592 passed。

## feat(medicines): 风险检查的交互项补上图证据（机理解释）

- 背景：上一批只做了**查询能力**，`POST risk-check` 的 finding 仍然只说「A 与 B 有冲突」，

- 领域：`domain/services/risk-model.ts` 新增 `MedicineRiskMechanism`（kind / geneSymbol /

  字段 `mechanism`。
- 映射：`domain/services/risk-mechanism.ts`（纯函数，零依赖）
  - `buildMechanismOutcome`：图通路 → 机制证据。**只认当前 finding 涉及的两个药**——
    多药查询返回所有两两通路，不过滤就会把别处的通路贴到这条发现上，那是错误归因，
    比没有机制更糟。

## feat(medicines): 半衰期解析与漏服判定领域逻辑

- 背景：现在的漏服提示是「到点没吃就提醒」，同一条规则套在两类药上说反话——
  半衰期 3 小时的药漏 6 小时（两个半衰期，浓度掉到 25%）**该提醒**；
  半衰期 102 小时的依那西普漏 6 小时（6% 一个半衰期）浓度几乎没动，提醒只制造焦虑。
  判定依据应是「缺口占半衰期的比例」，而半衰期来自药品知识——这是有药物数据才做得出、
  通用提醒 App 做不到的提示。
- `domain/services/half-life.ts` — 文本解析（纯函数，零依赖）
  - 覆盖实测样本里的全部写法：`4-5 hours`、`8.4-19.3 hrs`、`112 minutes`、`3 days`、
    `25 ± 10 hours`（按中心±偏差展开，**不是**区间 25..10）、`>20 hours`（标记 openEnded）、
    `three hours`（英文数词）、以及整段叙述（取**第一次**出现的值，那通常是主句结论）。
  - **在真实数据上验证覆盖率：78 条非空 `half_life` 解析出 76 条（97%）**。
    剩下 2 条是语义上就没有半衰期的（somatotropin 文本被截断、pancrelipase 明确
    「不被吸收」），返回 `null` 是正确行为。
  - 返回 `[lowHigh]` 区间而非单值：33/78 条原文是区间，取中点会把不确定性伪装成精确。
  - 解析失败返回 `null`，**不回落到默认值**——那等于给一个我们自己编的生理参数。
- `domain/services/half-life-gap.ts` — 判定逻辑
  - 阈值用**上界的一半**（偏晚触发）。这是有意的取舍：区间宽的药（`8.4-19.3 hrs`）
    用下界口径时阈值 4.2 小时、缺口 5 小时就提示；用上界口径阈值 9.65 小时、不提示。
    **误报的代价更高**——一个每天多弹几次的提醒会让用户对整个提醒系统失去信任，
    比少提示一次贵得多。

## refactor(common): E0 事件总线与队列重做（ADR-0025）

领域事件从「进程内 `emitAsync` 广播」改为「outbox 持久化 + 按订阅表扇出到各消费者队列」。
`domain_events` 表此前已实现但零生产者零消费者，真正在跑的是 `EventEmitter2` 的
`emitAsync`（7 个事件名、23 处 `@OnEvent`）。本次把它接成真正的扇出器。

- **`domain_events` 定型**：新增 `dedupe_key`（唯一索引，可空）与 `dispatched_at`。
  `dispatched_at` 表示「扇出完成」，`published_at` 表示「已结算」；`published_at IS NULL`
  仍是轮询认领条件，因此崩溃在两者之间只会重新结算、不会重复投递。`dedupe_key` 由生产者
  拼成 `<event-name>:<aggregateId>:<fingerprint>`，**不加 `context` 前缀**——事件名本身
  已是跨上下文唯一的命名空间，且唯一索引防不住「忘了带命名空间」的拼法，那是靠约定与
  测试保证的。迁移 `20261024180000_domain_events_dedupe_and_dispatch`。
- **订阅表是纯数据**（`common/events/subscriptions.ts`）：`eventName → [{queue, job}]`，
  不含函数引用，`common/` 只认队列名不 import 业务模块。**一行只允许指向已存在的消费者**，
  按已迁移的消费者逐条填；**没有消费者的事件不写行**（`risk-assessment.completed` 即如此）——
  空数组声称「确认过没人听」，而这句话之后无法复核。
- **扇出服务**（`domain-events-fanout.service.ts`）：一条 outbox 行 → 每个订阅者一条独立
  job。`EventConsumerRegistry` 承载无 Redis 时的进程内回收，本地开发与 e2e 不需要 Redis。
- **生产者统一入口**：新增 `DomainEventPublisher`，生产者只调 `publish()`；第 7 步去掉
  进程内 `emitAsync` 后，`DomainEventOutboxService` 已从 `common/index.ts` 摘掉
  （模块内部仍注入它），「只用一半」在类型上不再可能。`EVENT_ORIGINS` 补上计划未提及的
  缺口：`domain_events` 的 `context`/`aggregate_type`/`aggregate_id` 三列由事件名推导，
  避免各生产者拼出三种写法。
- **三个消费者迁到队列**：`reports`（`report-cache-invalidation`）、
  `today-suggestion`（`suggestion-recompute` 的 `event-trigger` job）、
  `medicines`（`medicine-risk-refresh`）、`today-analysis`（`today-analysis` 的
  `event-trigger` job）。删除了全部 23 处 `@OnEvent`。
- **`reminder-dispatch` 移出 `common`**：落到
  `medicine-reminders/services/dispatch-queue.service.ts`，自注册 repeatable job；
  `cron-jobs.service.ts` 不再 import `medicine-reminders`，并清理 cron 队列上残留的
  reminder scheduler（BullMQ 的 scheduler 会留在 Redis 里继续触发）。
- **共享内核词汇**：`RiskLevel`（`common/risk/risk-level.ts`）确立为发布语言，
  `RiskAssessmentCompletedPayload.severity` 改为 `riskLevel`；与

  `scripts/arch/risk-level-mirror.spec.ts` 锁定一致（领域层不能 import `common/`，
  故两份必须共存；守卫放 `scripts/` 是因为 `common-no-module-imports` 覆盖 `src/common/`
  下所有文件含 spec）。
- **消费者幂等**：job 带 `eventId`（outbox 行 id）。job id 为 `eventId:job:queue`
  确定性生成，能吸收扇出重跑，但**覆盖不了「消费后崩溃重放」**；有副作用的消费者须自行
  持久化已处理 `eventId`。不设公共去重存储是有意的（各消费者对「已处理」定义不同）。

## fix(auth): 登录验证码失败折叠进反枚举桶

- **这是一个安全修复，不是重构**。`CredentialAuthService.verifyLoginCredentials`
  的验证码分支把 `VerificationCodeService.verify` 的失败**原样抛出**：

  ```ts
  return this.verificationCodeService
    .verify(email, dto.code as string, 'login')
    .map(() => user); // 失败直接返回，既没折叠、也没 recordLoginFailure
  ```

  对比密码分支：那里 `.orElse` 明确把非依赖类错误折进 `recordLoginFailure(email)`。
  于是 `POST /auth/login` 上出现一个**不限速的账号存在性预言机**：
  `{email: <已注册>, code: '000000'}` → 401 `AUTH_VERIFICATION_CODE_MISMATCH`，
  `{email: <未注册>, code: '000000'}` → 401 `AUTH_WRONG_PASSWORD`。
  两处加重因素：(a) 该路径**不记限流**，10 次锁号永不触发，可无限次枚举；
  (b) 客户端按 `code` 分支，差异是契约可见的。方法上的 docstring 写着
  「Every failure path returns the same generic `AUTH_WRONG_PASSWORD`」——
  注释描述的是设计意图，实现漏了；本次把实现改对，并让 docstring 与之一致。

- 修复：验证码分支加 `.orElse(...)`，`kind` 为 `internal`/`dependency` 的原样上抛
  （不变量 #2），其余（`AUTH_VERIFICATION_CODE_MISMATCH` /
  `AUTH_VERIFICATION_CODE_EXPIRED`）折进 `recordLoginFailure(email)` →
  `AUTH_WRONG_PASSWORD`。**过期与不匹配折进同一个桶**：两者对攻击者的信息价值相同
  （「这个邮箱存在，且曾经请求过验证码」），只折叠一个等于把预言机换个出口；
  且从用户视角两者的操作都是「重新获取」，没有区分价值。
- **注册路径不改**：注册必须先拿到有效码才能走到邮箱判重，不构成预言机。
  `AUTH_VERIFICATION_CODE_*` 现在只剩发码冷却/限流与邮箱验证 token 三条出口，
  都不泄露账号存在性。
- 契约影响：**破坏性**。`POST /auth/login` 不再返回
  `AUTH_VERIFICATION_CODE_MISMATCH` / `AUTH_VERIFICATION_CODE_EXPIRED`；
  Lumine 与 Luminous 按 `code` 分支的验证码错误提示会落到「密码错误」分支，
  客户端需同步调整文案/逻辑。端点、DTO、operationId 均未变。
- 测试：`credential.service.spec.ts` 新增 4 条（mismatch 折叠 + 计限流、
  expired 同桶、缓存故障仍是 `DEPENDENCY_UNAVAILABLE` 且不计限流、
  「已注册错码」与「未注册错码」结论逐字相同）；`test/e2e/auth/auth.e2e-spec.ts`
  新增 3 条（错码 → 401 `AUTH_WRONG_PASSWORD`、已注册与未注册响应
  `code`/`status`/`title` 完全一致、连续 10 次错码后第 11 次 429
  `AUTH_LOGIN_RATE_LIMITED`）。修复前登录路径的验证码失败**没有任何测试覆盖**
  ——这正是漏洞存活至今的原因。

## refactor(auth): 凭据判定不再区分验证码错误与过期

- 背景：S2（`7e75b674`）的 `CredentialRejectionReason` 里 `code-mismatch` 与
  `code-expired` 是两个 reason。**这是错的**：领域层的职责是回答「这个凭据有效
  吗」，答案只有有效或无效；**「为什么无效」在反枚举语境下必须被丢弃**。
- 具体风险：只要这个区分在领域类型里存在，将来有人加日志、加指标、加审计时就会
  自然地把 `reason` 记进去。而 **reason 一旦进了日志或指标标签，它就以另一种渠道
  泄露了**——攻击者拿不到 HTTP 响应，但能从运维看板的分布上推出来。
- 改动：两个 reason 合并为 `credential-code-mismatch`。同时 `CredentialFacts` 的
  `codeOutcome: 'valid' | 'mismatch' | 'expired' | null` 收窄为
  `codeValid: boolean | null`——**校验器的三态不再透传进领域层**，因为透传就等于
  把「为什么无效」这个词汇带进了领域结论。`credential.service.ts` 的
  `verifyByCode` 因此不再读 `error.code` 区分 EXPIRED/MISMATCH（`CodeOutcome`
  类型一并删除）。
- **行为等价性已核实**：S2 的映射表里 `rejected` 本来就是**一个**
  `case`（`git show 7e75b674:.../credential-failures.ts` 确认），六种 reason 全部
  走 `credentialsInvalidFailure()`。所以合并 reason 不改变任何可观察结果——
  合并前后都进 `AUTH_WRONG_PASSWORD`，且都不产生独立日志字段。
- 分层约定（S3 继续遵守）：**聚合/校验层可以有自己的 reason 词汇**
  （`VerificationChallenge` 返回 `{ usable: false, reason: 'expired' }` 是合理的，
  S3 内部需要它），但**那个词汇不该流到凭据判定层**——交界处做一次投影，
  `CredentialDecision` 里没有 expired。
- 测试：`credential-verdict.spec.ts` 新增两条——「未执行校验（`codeValid` 为
  `null`）也按无效处理」与「**领域层不区分码错与过期**：断言序列化后的结论里
  不含 `expired`」（把这条约定钉成测试，而不是只写在注释里）；拒绝原因表与
  `countsAsLoginFailure` 的遍历清单同步收敛到五种。
- 验证：`pnpm typecheck`、`pnpm lint:check`（0 error）、`pnpm arch:check`（204 entries，
  基线未新增）通过；`src/modules/auth` 35 文件 / 451 passed（原 450）。

## refactor(auth): 验证码生成与比对落 domain/challenge

- 背景：S3（码类挑战）的第一步——先落**纯函数**（生成、指纹派生、比对），

- 新增 `domain/challenge/verification-code.ts`，从
  `services/identity/verification-code.service.ts` 提出三件事：
  - `generateCode(length)` —— 用 `randomInt`（**不是 `Math.random()`**：
    后者的内部状态可从少量输出推断，预测出下一个码就等于绕过验证）；

    拿到存储指纹就能离线枚举。

## feat(auth): 验证码挑战聚合化并加尝试次数上限

- **这是行为变更（`feat` 不是 `refactor`）**：迁移前验证码**没有失败计数**——
  `verify()` 比对不匹配就返回错误，该码仍然有效，可以无限次尝试。
- 背景：S3（码类挑战）切片。`services/identity/verification-code.service.ts`
  的判定逻辑下沉为聚合，并补上缺失的尝试次数上限。
- 新增 `domain/challenge/challenge.ts` —— `VerificationChallenge` 聚合，守四条
  不变量：**单次消费**、**过期不可用**、**尝试次数上限**（新增）、
  **指纹绑定场景与邮箱**。
  - `MAX_CHALLENGE_ATTEMPTS = 5`。取值理由：合法用户拿到的码是邮件里的 6 位数字，
    输错通常来自看错或多按，**连续错 5 次几乎必然意味着这不是本人**；而攻击者
    只有 5 次机会，10^6 / 5 在 5 分钟 TTL 内命中概率约 0.0005%。
  - **作废码而不是锁定邮箱**。作废码是聚合内的事（改自己的状态）；锁定邮箱是
    跨聚合副作用。更重要的是**反噬**：锁定邮箱意味着攻击者可以用你的邮箱制造
    锁定，把防爆破变成 DoS 手段。作废码没有这个问题——用户重新获取即可。
  - **用尽优先于指纹比对**：放在最前，否则攻击者猜满 5 次后仍能靠第 6 次命中
    （若实现成「作废但仍比对」，上限就白做了）。
  - `verify()` **不修改自身**，返回 `{ verdict, nextState }`：聚合保持纯粹
    （可脱离存储单测），「写回」这个 IO 留给应用层。
  - 聚合**不返回「还剩几次」给上层**：`remainingAttempts` 只在 `mismatch` 分支
    出现供内部判断，且不进响应、不进日志（告诉攻击者剩余次数等于给进度条）。
- `verification-code.service.ts` 改为「读 → 重建聚合 → 判定 → 写回」：
  - 缓存值从**裸指纹**改为**聚合状态**（`{scene, email, codeHash, attempts,
issuedAt}`）。`attempts` 与码必须同时成立，放在同一条目里，作废与清零就是
    同一个原子操作——这正是「尝试次数」属于本聚合的原因（拆成独立计数器要处理
    「计数与码不同步过期」的一致性）。
  - 写回用**剩余 TTL**（从 `issuedAt` 算起）而不是完整 TTL：否则攻击者可以靠
    不断猜错把码永远留住。
  - 删除了三个已下沉的私有方法（`generateCode`/`hashCode`/`safeCompareCode`）。
- **错误码映射**：聚合 verdict 有 `mismatch`/`exhausted`/`expired`/`absent` 四种，
  对外只映射两个既有码——`mismatch` → `AUTH_VERIFICATION_CODE_MISMATCH`，
  其余（含 `exhausted`）→ `AUTH_VERIFICATION_CODE_EXPIRED`。
  **猜爆不新造错误码**：新码会告诉攻击者「你把这码猜爆了」，那是进度反馈。
  缓存层保留条目（不删除）让运维能在日志里区分「猜爆」与「过期」，
  而两者对用户和攻击者都是同一件事。
