### 订正：`pred0` 不是 0–1 概率

原 §2.2 写「`pred0` ≥0.9 占 35.6%，<0.5 占 53.8%」并据此论证「不能按 0.5 过滤」。抽样
10 万行实测后发现口径本身有问题：

- `pred0` 值域 0–5.05，**>1 的行占 36.0%**；`==0` 占 **44.5%**（是「未给出分数」而非低置信）。
- `pred1` 值域 3.26–6.02（未归一化对数几率），**97.3% 的行 `pred1 > pred0`**，
  两者相关系数 **−0.952**。

因此原结论「保留原始 `pred0` 落库、阈值交给展示层」**改为**：阈值一律走 `pred1`；
`pred0` 只作溯源，并以可空列 `pred0_raw` 落库，避免与真实低分混在一起。§4.2 的
Prisma 模型、§五 第 8 步、§六 风险表、§八「不做什么」同步改写。

### 三个必须记录的口径

1. **置信度用 `pred1`，不用 `pred0`。** 抽样 10 万行实测 `pred0` 有 44.5% 为 0
   （表示未给出分数）、36% 大于 1，不能当 0–1 概率；`pred1` 值域 3.26–6.02 且连续。
   `pred0_max` 仅作溯源，可空列，不参与排序与过滤。计划 §2.2.1 已同步。
2. **`label_sections` / `sources` 用 JSONB，不用 `TEXT[]`。** 共享导入器
   （`scripts/shared/db-upsert.ts`）把数组绑成 JSON 文本，Postgres 对真数组列会以
   22P02 拒绝 `'["AR"]'`。本 schema 的所有多值列都是这个形状。
3. **CSV 必须 `all_varchar`**。`vocab_rxnorm_ingredient_to_product.product_id` 混有
   `OMOP4985567` 这类前缀值，DuckDB 的类型推断会按整数解析并抛 ConversionException。

### 顺带修掉的存量缺陷

`DATA_ROOT` 的解析从 `REPO_ROOT/../DrugDataBase` 改为三级上跳：
2026-11-17 单体迁入 `apps/monolith` 后 `REPO_ROOT` 指向了 `apps/monolith`，原表达式
解析成 `Lucent/apps/DrugDataBase`，**每一次** `import:medicine:*` 都会以 ENOENT 失败。
新增 `DRUG_DATA_ROOT` 覆盖口，数据集不在仓库旁边时用。这个 bug 与 OnSIDES 无关，

## feat(medicines): OnSIDES 不良反应查询端点（详情与反向查询）

### 变更范围

继续 `plans/2026-10-17-drug-adverse-reaction-data-sources.md` 的 Phase 2，把昨天
导入的两张表接到读路径上。**OnSIDES 作为独立知识源**，不并进 DrugBank 详情：
它的键是 RxNorm 成分 CUI + MedDRA 术语，没有药名 / 适应症 / 相互作用图；并进去会让
`GET /medicines/:id` 的响应形状取决于某个药恰好有没有 RxCUI 映射。

- **端口** `application/ports/onsides.ts`：`OnsidesReactionsReader`
  （`getByIngredient` / `getByDrugbankId` / `getReactionDrugs`）+ limit 三个常量。
- **持久化** `infrastructure/persistence/onsides.ts`：三条查询都是两跳，经既有的
  `drugbank_external_identifiers (resource = 'RxCUI')` 桥接。**不建映射表**。
- **端点** `adapters/http/onsides.controller.ts`（3 个，全部 `@Public()`）：
  - `GET /medicines/ingredients/:rxnormCui/reactions`
  - `GET /medicines/drugs/:drugbankId/reactions`
  - `GET /medicines/reactions/:meddraId/drugs?limit=`
- **DTO** `adapters/http/dto/onsides.ts`：两个响应组件 + limit 查询 schema。
- 模块注册、`export:openapi`（165 paths / 426 schemas）与 medicines README 同步。

### 三个刻意的取舍

1. **没桥就是 404，不是 200 + `[]`。** DrugBank 只有 8.2% 的条目带 RxCUI（配对级
   92.62%），所以 `drugs/:id/reactions` 对大多数药返回 404 是常态。返回空数组会把
   「没有桥」说成「桥上了但没反应」，是两句不同的话。e2e 固化了这条。
2. **`limit` 越界是 400，不静默钳制。** 与 `/network` 端点同一口径：
   `limit=0` 只可能是调用方的 bug，用空列表回答它等于把 bug 藏起来。
3. **不合并同一药物经多个 CUI 的结果为多条。** 一个成分 CUI 可桥到多个 DrugBank 行
   （盐型、复方），一个药也可经多个 CUI 出现。反向查询按**药物**去重，
   `labelCount` 相加、`confidenceMax` 取最大。

### 修掉的两个缺陷

- **`prisma format` 会凭空补出关系列。** 在 `DrugSourceImport` 上保留
  `onsidesAdverseReactions OnsidesAdverseReaction[]` 时，Prisma 认为该关系无字段承载，
  自动在 `OnsidesAdverseReaction` 上补 `drugSourceImportId` 列并生成对应 SQL，
  于是 Prisma Client 查询一个数据库里不存在的列，接口 500。
  **MedDRA 字典是跨导入共享的词表，本来就不该有 `import_run_id`**；两边一起删才对
  （只删字段侧，`prisma format` 会立刻加回来）。
- **test 库漏应用本次迁移**，e2e 报 `table does not exist`。已 `migrate deploy` 补齐。

## docs(todo): 撤掉 OnSIDES 成分别名表项（实测判定不做）

### 为什么撤

原计划与 TODO 都写「补一张 191 行的成分别名表即可回收 7.38% 未映射配对」。用全量数据
（不是 dev 库的 200 行样量）实测后，这个判断有两处错，结论是**不做**：

1. **OnSIDES 自身数据能救的部分几乎为零。** 直觉上 DrugBank 存的临床药品 CUI 应该
   能经 `vocab_rxnorm_product` + `vocab_rxnorm_ingredient_to_product` 回溯成成分 CUI。
   实测：5,793 个带 RxCUI 的药里只多救回 **8 个**，其余 4,162 个的 CUI 不在 OnSIDES
   的 product 词表内。
2. **缺口不是 191 个成分，是 22 个。** 按配对量计：总计 2,134 万配对，覆盖 91.83%，
   未覆盖 8.16%（174 万）。未覆盖中 **90% 只由 22 个成分贡献**——dasatinib、atorvastatin、
   tacrolimus、lisinopril、azithromycin、valproate、amoxicillin、piperacillin、risedronate、
   docetaxel、clavulanate 等常用药。根因确认是粒度（DrugBank 记 `1546019`，OnSIDES 记
   `475342`），且**两边药名逐字一致**——真要做也该是导入时按名称精确匹配生成映射，
   不是手工维护一张表。

### 不做的理由

这不是「做不到」，是「现在不该做」：三个端点目前**没有任何调用方**（客户端尚未接线），
先给一个尚未被消费的查询补覆盖率，换不到用户可见行为。等客户端接上、确认这个数据源
真的有人用，再按实测结论重启——前提是走名称匹配生成，别手工维护别名表。
