### 说明

目录名用 `monolith` 而非 `legacy`：该目录是「还没拆走的单体」，不是废弃代码，
`legacy` 会让读的人误以为它只配维护不配修改。

`infra/` 而非 `deploy/`：这里除了部署还有契约基线、数据所有权与 CI 门禁，
按部署命名会让「契约基线该放哪」反复成为问题。

目录搬迁与命名硬切分开执行的依据：搬迁不改任何公开契约，不需要契约基线比对与客户端
同步发版；合并执行会让排查时同时面对「路径变了」与「名字变了」两种噪音。

`semantica-service` 归属明确为 `Lucent/apps/ontology`：它与 Lucent 领域强耦合，
只是语言不同；业务归属不该因语言分裂到两个仓库。语言隔离靠 uv workspace 边界，
不靠仓库边界。**本次只改计划，未移动任何文件。**

## feat(workspace): semantica-service 收编为 apps/ontology

### 变更范围

- `semantica-service/` 以 `git subtree` 收进 `apps/ontology/`，保留其 50 条提交历史
  （原仓无 remote，是本地仓）。
- 根 `pyproject.toml`：`[tool.turbo] name = "lucent-python"` 与
  `[tool.uv.workspace] members = ["apps/ontology"]`；根 `uv.lock` 由 `uv lock` 生成，
  成员自带的 `uv.lock` 删除（workspace 只有一份锁）。
- `turbo.json`：开 `experimentalTaskCommand`，覆写 `semantica-service#check` 为
  `uv run --frozen --package semantica-service mypy --config-file pyproject.toml src tests`。
- 修正两处可执行命令：`compose.dev.yaml` 与 `docs/reference/environment-variables.md`
  的 `cd semantica-service` → `cd apps/ontology`。
- 计划文档同步：`services/ontology` → `apps/ontology`；`plans/README.md` 的
  `apps/legacy` → `apps/monolith`。
- 删除根目录误建的 `NUL` 文件（Windows 保留名，导致 turbo 哈希直接失败）。

### 说明

**目录放 `apps/` 而不是 `services/`**：`apps/` 的语义就是「可部署单元」，ontology 正是
一个自带 Dockerfile 的 FastAPI 服务。为标记语言而单开顶层 `services/`，只会让「哪些
东西要部署」这个问题变得难回答，且没有换来任何隔离——隔离由每个成员自带
`pyproject.toml` 保证。因此 uv workspace 用**显式成员**而非 `apps/*` 通配：通配会让 uv
去每个 TS 应用里找一个永远不存在的 `pyproject.toml`。

**为什么覆写 `check`**：Turbo 内置的 mypy 映射会把成员目录整体传给 mypy，于是
`scripts/` 也进严格检查（项目约定只查 `src tests`，14 个既有错误出在那里）；而且从仓库
根运行会丢掉成员自己的 `[tool.mypy]`（`ignore_missing_imports` 对 `semantica.*` 的豁免），
表现为 `import-untyped`。覆写后范围与配置都与项目 README 一致。
