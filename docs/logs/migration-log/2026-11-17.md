### 变更范围

  成员自带的 `uv.lock` 删除（workspace 只有一份锁）。
- `turbo.json`：开 `experimentalTaskCommand`，覆写 `semantica-service#check` 为
  `uv run --frozen --package semantica-service mypy --config-file pyproject.toml src tests`。
- 修正两处可执行命令：`compose.dev.yaml` 与 `docs/reference/environment-variables.md`
  的 `cd semantica-service` → `cd apps/ontology`。
- 计划文档同步：`services/ontology` → `apps/ontology`；`plans/README.md` 的
  `apps/legacy` → `apps/monolith`。
- 删除根目录误建的 `NUL` 文件（Windows 保留名，导致 turbo 哈希直接失败）。

### 说明

**目录放 `apps/` 而不是 `services/`**：`apps/` 的语义就是「可部署单元」，ontology 正是
一个自带 Dockerfile 的 FastAPI 服务。为标记语言而单开顶层 `services/`，只会让「哪些
东西要部署」这个问题变得难回答，且没有换来任何隔离——隔离由每个成员自带
`pyproject.toml` 保证。因此 uv workspace 用**显式成员**而非 `apps/*` 通配：通配会让 uv
去每个 TS 应用里找一个永远不存在的 `pyproject.toml`。

**为什么覆写 `check`**：Turbo 内置的 mypy 映射会把成员目录整体传给 mypy，于是
`scripts/` 也进严格检查（项目约定只查 `src tests`，14 个既有错误出在那里）；而且从仓库
根运行会丢掉成员自己的 `[tool.mypy]`（`ignore_missing_imports` 对 `semantica.*` 的豁免），
表现为 `import-untyped`。覆写后范围与配置都与项目 README 一致。

### 说明

Go 绑定是它的纯函数派生。随后的代价是「构建前必须先 generate」，因此每个消费点

**为什么不自己跑 oapi-codegen 而走 `go generate`**：版本钉在 `go:generate` 指令里，
两处跑法只有一个事实源。

## fix(workspace): oapi-codegen 改为模块工具，生成不再联网

### 变更范围

- `packages/contracts/go/go.mod`：新增 `tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen`。
- `contract.go` 的 `go:generate`：`go run ...@v2.8.2` → `go tool oapi-codegen`。

### 说明

原来用的是 `go run github.com/oapi-codegen/...@v2.8.2`，这种写法**每次生成都要求
Go 代理可达**，而且版本解析走 `@version` 语义——本机 `proxy.golang.org` 不通，
pre-push 的 `lint:check` → `contracts#generate` 因此失败，push 被挡。

改成 go 1.24+ 的 module tool 指令后，生成器与其他依赖一样由 `go.sum` 锁定，
**已下载过的机器上 `GOPROXY=off` 也能生成**，且不会静默升版。

代价：`go.mod`/`go.sum` 里多了 oapi-codegen 及其依赖（间接依赖已由 `go mod tidy`
收拢）。这是「把一个构建工具变成可复现依赖」的正常成本。

### 验证

- `GOPROXY=off` + 删除生成物后 `go generate ./...`：exit 0，`openapi.gen.go` 重新产出。
- `GOPROXY=off` 下 `go vet ./...`、`go test ./...` 通过。
- 不再需要开发者或个人环境里设 `GOPROXY`（此前 PR 里写的那条提醒随之作废）。

## fix(assistant): 工具路由补上对话历史，修复追问不绑任何工具

### 变更范围

- `application/services/intent-router-prompt.ts`：用户提示词新增历史区块，
  顺序固定为**候选工具目录 → 历史 → 本轮消息**；单条超
  `ROUTER_HISTORY_MESSAGE_MAX_CHARS`（400）字符截断并加省略号。
- `application/services/intent-classifier.ts`：`AssistantToolRoutingContext` 增加
  `history`；`selectTools` 第五参数**必填**（不给默认值）。
- `adapters/agent/state.ts`：新增 `conversationHistory` 通道与
  `AssistantConversationTurn` 类型。
- `adapters/agent/graph.ts`：`routeTools` 传入历史；`classify_intent` 的
  `cachePolicy` 改为显式 `keyFunc`（`buildClassifyIntentCacheKey`）。
- `adapters/agent/deps.ts`：`routeTools` 输入加 `history`（必填）；新增
  `routingPromptFingerprint`。
- `adapters/agent/runtime.ts`：入图输入带 `conversationHistory`；两条
  `selectTools` 调用点补历史；注入 prompt 指纹。
- `application/ports/agent-runtime.ts`、`application/use_cases/stream-message.ts`：
  端口签名加 `conversationHistory`；从 `dto.messages` 取最近 6 轮、排除末条、
  丢弃空内容。
- 新增测试：`intent-classifier.spec.ts` 3 条、`graph.spec.ts` 2 条。
- `README.md` 的工具路由小节与 Tests 小节、计划 §3 同步。

### 说明

**缺陷形态**：第一轮问「布洛芬有什么副作用」，第二轮问「那你查一下」，
第二轮没有任何工具可用。`classify_intent` 每轮只把**当前这一条**消息交给路由模型，
四个字脱离上下文无法判定工具 → 返回空集 → `deriveIntent([])` 塌成 `simple_chat`
→ 条件边直达 `respond` → 一个工具都不绑。叠加 `cachePolicy` 后这类短语还会稳定
命中同一个「无工具」结果，错误可复现且不自愈。

**三处与计划的偏离**（原计划写的是「从 state.messages 取最近 N 条」）：

1. 历史取自**请求体**而非 checkpoint：无状态对话（无 `conversationId`）没有
   checkpoint 可读，而两条路径都必须能用。
2. 缓存键用**显式 `keyFunc`** 而非「含历史摘要的 hash」。LangGraph 默认键是
   `XXH3(JSON.stringify([packet.args]))`（`pregel/algo.js:447`），哈希的是节点输入：
   「输入里含历史」不等於「键里含历史」，reducer 合并与通道子集都会改变实际参与
   哈希的内容。显式键把契约写死，并纳入提示词指纹——运行时 prompt 覆盖不能复用
   旧提示词下的判断。
3. `selectTools` 的 `history` **必填**。写成 `history = []` 会让调用点漏传时静默
   退化成无历史且测试全绿，正是原缺陷的形态。必填后编译器一次性报出全部 6 处漏传。

## refactor(assistant): 删除意图路由与子图，改为单一 ReAct 循环

### 变更范围

删除：

  `intent-routing.ts`、`intent-eval.fixture.ts`（各含 spec）。

- `arch-warning-baseline.json` 中指向已删文件 `intent-routing.ts` 的条目（基线只减）。

新增 / 改写：

- `graph.ts`：`START → prepare_context → agent ⇄ tools → validate → respond → END`，
  外加 `capped` 与 HITL 分支。
- `validate.ts`：三个子图的 `*_validate` 合并为单一节点，新增 `createValidateNode`。
- `state.ts`：新增 `loopCapped` 通道。
- `prompts.ts`：单一 `buildAssistantSystemPrompt`，按 DSH `tool-design` 规则重写。
- env key + 运行时 schema：`ASSISTANT_MAX_TOOL_LOOPS`（默认 8，min 1 / max 32）。
- `tool-constants.ts`：`MAX_TOOL_LOOPS` 3 → 8。
- `respond.ts`：缓存命中点扩展到 agent 直答路径；`stopReason` 改为不覆盖上游判定。

### 说明

**为什么删。** `classify_intent` 用一次模型调用选出工具子集，再投影成 `intent`，
再切进固定子图。三个后果都是生产实测的：路由只看当前那条消息（追问绑不到工具）；
子图是硬边界（读记录途中要查药品时同一个 turn 内出不去）；工具选择本来就是
function calling 在做的事，预先决定再把结果当硬约束是为同一个决定付两次钱。

**实现逼出的三个真实缺陷**（计划未预见）：

1. `tool_cap_reached` 原本不可达——`tools` 每次迭代清空 `pendingToolCalls`，
   `validate` 分不清「自然结束」与「被截断」。修法：`loopCapped` 通道 + `capped`
   节点，并在 `tools` **执行之后**判上限（在 `agent` 之前判会砍掉模型请求的最后一轮）。
2. `respond` 无条件写 `stopReason: 'answered'`，把 `tool_cap_reached` 与
   `no_evidence` 全盖掉。修法：只在上游无判定时回落。
3. `agent` 收到空文本时写 `finalContent: ''`，让 `respond` 走「已有内容」分支并抛错。
   修法：空文本视为未作答（`finalContent: null`），交给 `validate` 解释原因。

另有 HITL 语义收窄：`validate` 只在**有 checkpointer** 时写 `pendingReview`。
无 checkpointer 时没有东西会挂起，写它等于谎称「有待确认的提案」。

**提示词合并的取舍。** 四份提示词按 intent 选择，删掉路由后没有选择依据：一个
同时读记录与查药的 turn 四份都不匹配。合并时按「每条事实只说一次」重写，
参数规则留在参数上。`prompts.spec.ts` 原有安全断言一条未减，只是改成对唯一
提示词断言。

## feat(infra): mem0 建库与 pgvector 初始化改由 entrypoint 自动完成

### 变更范围

- 新增 `apps/monolith/scripts/db/ensure-mem0-databases.ts`：建 `mem0` /
  `mem0_app` 两个 database 并在其中 `CREATE EXTENSION IF NOT EXISTS vector`。
- `entrypoint.sh`：`MEM0_ENABLED=true` 时在 `prisma migrate deploy` 之后、应用启动
  之前调用它。
- `Dockerfile`：把该脚本 COPY 进镜像（`/app/apps/monolith/scripts/db`）。
- `docs/reference/environment-variables.md`：Mem0 小节补建库自动化、镜像选择、
  healthcheck 路径与 history 卷四处事实。

### 说明

**为什么必须是自动的。** 之前这两个库是我手工 `psql` 建的，那只存在于 shell 历史里；
换一台机器或重建卷就没了，后果是 sidecar 在 `relation "request_logs" does not exist`
上崩溃循环——Alembic 迁移不会自己建库。

**为什么不放 `docker/postgres` 的 initdb 目录。** 那套**只在数据目录为空时执行**。
dev 与三台生产机的卷都已初始化，放那里会被静默跳过，正是最需要它的地方失效。
放在 entrypoint 里每次启动都跑一遍，代价是 4 条幂等查询。

**为什么脚本放 `apps/monolith/scripts` 而不是 `infra/`。** 它 import `pg`，是
`monolith` workspace 成员的依赖；pnpm 不提升到仓库根，`infra/` 下解析不到。
生产镜像里 `apps/monolith/node_modules` 本来就在（entrypoint 经由它调用 prisma）。

**为什么交付 `.ts` 而不是 `.js`。** Node 26 原生剥离类型，仓库 pre-commit 的
`check-no-js` 禁止 `.js`。

**顺带修的两处（此前已提交但不可用）：** 官方 `mem0/mem0-api-server:latest`
只有 arm64，amd64 宿主拉不下来，且自 2025-09 起未再推送（早于 auth/dashboard）；
两个 compose 改为 pin `amerenda/mem0-server` 的 digest（官方源码的 amd64 重建，
已验证能起到 healthy）。healthcheck 由 `/health`（实测 404）改为 `/docs`；
新增 `mem0-history` 卷，否则首启 `unable to open database file`。

- 删库后跑脚本：两个库创建成功，两库均有 `vector` 扩展。
- 重复跑：全部 `already exists; skipping`（幂等）。
- `MEM0_ENABLED=false`：无输出、exit 0（不碰数据库）。
