    等同 `apps/monolith` + 旧库；全部替换反而降低可读性。

### 说明

目录名用 `monolith` 而非 `legacy`：该目录是「还没拆走的单体」，不是废弃代码，
`legacy` 会让读的人误以为它只配维护不配修改。

`infra/` 而非 `deploy/`：这里除了部署还有契约基线、数据所有权与 CI 门禁，
按部署命名会让「契约基线该放哪」反复成为问题。

目录搬迁与命名硬切分开执行的依据：搬迁不改任何公开契约，不需要契约基线比对与客户端
同步发版；合并执行会让排查时同时面对「路径变了」与「名字变了」两种噪音。

`semantica-service` 归属明确为 `Lucent/apps/ontology`：它与 Lucent 领域强耦合，
只是语言不同；业务归属不该因语言分裂到两个仓库。语言隔离靠 uv workspace 边界，
不靠仓库边界。**本次只改计划，未移动任何文件。**

### 验证

- 术语计数：`infra/` 16 处、`apps/monolith` 11 处、`apps/legacy` 0 处；单 H1。

## feat(workspace): semantica-service 收编为 apps/ontology

### 变更范围

- `semantica-service/` 以 `git subtree` 收进 `apps/ontology/`，保留其 50 条提交历史
  （原仓无 remote，是本地仓）。
- 根 `pyproject.toml`：`[tool.turbo] name = "lucent-python"` 与
  `[tool.uv.workspace] members = ["apps/ontology"]`；根 `uv.lock` 由 `uv lock` 生成，
  成员自带的 `uv.lock` 删除（workspace 只有一份锁）。
- `turbo.json`：开 `experimentalTaskCommand`，覆写 `semantica-service#check` 为
  `uv run --frozen --package semantica-service mypy --config-file pyproject.toml src tests`。
- 修正两处可执行命令：`compose.dev.yaml` 与 `docs/reference/environment-variables.md`
  的 `cd semantica-service` → `cd apps/ontology`。
- 计划文档同步：`services/ontology` → `apps/ontology`；`plans/README.md` 的
  `apps/legacy` → `apps/monolith`。
- 删除根目录误建的 `NUL` 文件（Windows 保留名，导致 turbo 哈希直接失败）。

### 说明

**目录放 `apps/` 而不是 `services/`**：`apps/` 的语义就是「可部署单元」，ontology 正是
一个自带 Dockerfile 的 FastAPI 服务。为标记语言而单开顶层 `services/`，只会让「哪些
东西要部署」这个问题变得难回答，且没有换来任何隔离——隔离由每个成员自带
`pyproject.toml` 保证。因此 uv workspace 用**显式成员**而非 `apps/*` 通配：通配会让 uv
去每个 TS 应用里找一个永远不存在的 `pyproject.toml`。

**为什么覆写 `check`**：Turbo 内置的 mypy 映射会把成员目录整体传给 mypy，于是
`scripts/` 也进严格检查（项目约定只查 `src tests`，14 个既有错误出在那里）；而且从仓库
根运行会丢掉成员自己的 `[tool.mypy]`（`ignore_missing_imports` 对 `semantica.*` 的豁免），
表现为 `import-untyped`。覆写后范围与配置都与项目 README 一致。

### 验证

- `uv lock --check` 通过（79 个包）。
- `pnpm exec turbo ls`：4 个包 —— `lucent apps/monolith`、`lucent-python`、
  `semantica-service apps/ontology`、`shadcn-admin admin`。
- `turbo run lint check test --filter=semantica-service`：3/3 成功 —— ruff 全通过、
  mypy 0 error（`--config-file` 指向成员 pyproject）、pytest **323 passed**。
- 单体未受影响：`pnpm --filter lucent typecheck` 通过、`lint:check` 0 error。
- `pnpm install` 正常（3 个 npm 工作区项目，`apps/ontology` 无 package.json 被正确跳过）。

## feat(workspace): 接入 Go 工具链与契约绑定

### 变更范围

- 根 `go.work`（`use ./packages/contracts/go`）。
- 新增 `packages/contracts/go`：`go.mod`（module 末段为 `contracts`，Turbo 按此命名包）、
  `oapi-codegen.yaml`（只生成 `types`）、`contract.go`（`go:generate` 指令钉
  oapi-codegen v2.8.2）、`contract_test.go`、`go.sum`。
- `turbo.json`：开 `experimentalGoWorkspaces`；`contracts#generate` 用
  `go generate ./...`；`globalPassThroughEnv` 放行 `GOPROXY`/`GOFLAGS`/`GOMODCACHE`
  等（Turbo 默认过滤未声明变量，不放行会导致生成步骤拿不到 Go 代理配置）。
- 新增 `packages/contracts/go/turbo.json`：包级 `build`/`lint`/`test` 都 `dependsOn: generate`。
- `.gitignore`：忽略 `packages/contracts/go/openapi.gen.go`。
- CI 增 `go-contract` job：generate → vet → test。
- 计划文档三条 Go 裁决（原「不引入 Go/Rust 服务」）改为「工具链与契约绑定已就绪，
  业务服务语言待定」。

### 说明

**生成物不提交**，与 Prisma client、compodoc 同一处置：`openapi.json` 是契约源，
Go 绑定是它的纯函数派生。随后的代价是「构建前必须先 generate」，因此每个消费点
（`build`/`lint`/`test`）都显式 `dependsOn: generate`，而不是依赖人记得先跑。

**为什么用包级 `turbo.json` 而不是根级 `dependsOn`**：`dependsOn: ["generate"]` 写在
根任务里会要求**每个包**都有 `generate` 任务，实测直接报
`Could not find "lucent#generate"`。包级配置只约束真正需要的包。

**为什么不自己跑 oapi-codegen 而走 `go generate`**：版本钉在 `go:generate` 指令里，
两处跑法只有一个事实源。

### 验证

- `turbo ls`：6 个包，含 `contracts packages/contracts/go` 与 `go-workspace`。
- 删掉生成物后 `turbo run build lint test --filter=contracts`：4/4 成功
  （generate 被自动前置）。
- `turbo run build --filter=lucent` 正常，不受包级 generate 约束影响。
- `go vet ./...`、`go test ./...` 通过；测试钉住 ADR-0012 的错误体字段
  （`code`/`detail`/`title`/`type`/`retryable`）与契约声明的一致性。
- CI YAML 结构无误（e2e job 未受影响）。

## fix(workspace): oapi-codegen 改为模块工具，生成不再联网

### 变更范围

- `packages/contracts/go/go.mod`：新增 `tool github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen`。
- `contract.go` 的 `go:generate`：`go run ...@v2.8.2` → `go tool oapi-codegen`。

### 说明

原来用的是 `go run github.com/oapi-codegen/...@v2.8.2`，这种写法**每次生成都要求
Go 代理可达**，而且版本解析走 `@version` 语义——本机 `proxy.golang.org` 不通，
pre-push 的 `lint:check` → `contracts#generate` 因此失败，push 被挡。

改成 go 1.24+ 的 module tool 指令后，生成器与其他依赖一样由 `go.sum` 锁定，
**已下载过的机器上 `GOPROXY=off` 也能生成**，且不会静默升版。

代价：`go.mod`/`go.sum` 里多了 oapi-codegen 及其依赖（间接依赖已由 `go mod tidy`
收拢）。这是「把一个构建工具变成可复现依赖」的正常成本。

### 验证

- `GOPROXY=off` + 删除生成物后 `go generate ./...`：exit 0，`openapi.gen.go` 重新产出。
- `GOPROXY=off` 下 `go vet ./...`、`go test ./...` 通过。
- 不再需要开发者或个人环境里设 `GOPROXY`（此前 PR 里写的那条提醒随之作废）。
