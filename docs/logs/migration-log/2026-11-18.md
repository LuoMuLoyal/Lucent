## feat(assistant): 知识检索组暴露为 MCP server（Streamable HTTP）

### 变更范围

新增 `adapters/mcp/`：

- `server.ts` —— 会话表、`StreamableHTTPServerTransport`、Origin 校验、
  JSON-RPC 错误映射。
- `routes.ts` —— Fastify 路由 `/api/v1/mcp`（`POST`/`GET`/`DELETE`，
  `reply.hijack()` 交出发送权）。
- `tool-schema.ts` —— JSON Schema → zod（入参交给 SDK 校验）。
- `execution.ts` —— 端口 → 既有 `executeMany` 的薄适配。
- `auth.ts` —— bearer 鉴权，常量时间比较。
- `mcp.module.ts` —— Nest 装配，`onModuleInit` 注册路由。

新增 `domain/mcp/exposure.ts`（导出名单 + 命名契约 + 反解）与
`application/ports/mcp.ts`（执行端口 + 调用方身份）。

`app.module.ts` 注册 `McpModule`；`env-keys.enum.ts` 增 `MCP_ENABLED` /
`MCP_API_KEY` / `MCP_ALLOWED_ORIGINS`；依赖加 `@modelcontextprotocol/sdk@^1.32.2`。

### 说明

**只做 Streamable HTTP。** 不做 stdio：stdio 由客户端拉起子进程，而工具执行需要
Nest DI（Prisma、Redis、sidecar 客户端、指标），子进程里没有容器。

**暴露范围是领域决策，用不着过滤器。** `MCP_TOOL_NAMES` 手写 8 个知识检索工具；
不导出用户私有数据（`get_records_*` 等，与 `userId` 强绑定，跨进程只会放大越权面）
与写入提案（`propose_*`，离开 confirm 端点会把状态机劈成两半）。手写而非从
`TOOL_NAMES` 过滤，是因为过滤会在将来加入用户数据工具的那天静默开始导出它。

**安全三条按规范落地**（不是可选项）：校验 `Origin`、只绑回环（部署侧决定）、
所有连接鉴权。`Origin` 缺失时放行——CLI 与其它服务不发这个头，拒绝它们会切断主要
用例。`MCP_API_KEY` 未设置时启动打 `warn`，静默的无鉴权模式正是内网端点被暴露的
方式。

**工具名 `lucent__<rawName>` 是纯函数**，不掺运行时值。反解时前缀存在但工具未导出
仍然拒绝，否则调用方可以自拼前缀绕过名单（`exposure.spec.ts` 钉住）。

**执行走既有 `executeMany`**。提案信封、单工具超时、缓存、指标都在里面；第二份
执行器必然漂移，而漂移的表现是「提案被描述成已执行的写入」。

**两处 lint 规则需要 disable 并说明理由**：`tool-schema.ts` 的两处裸 throw 是工具
定义本身畸形（编程错误，不是 API 失败）；`server.ts` 的静默 catch 是因为该类的
logger 挂在 `options` 上，自定义规则只认字面量 `this.logger.error`，日志就在下一行。

### 验证

- `typecheck` 0 error；`lint:check` 0 error（4 个既有 warning）。
- `arch:check` 无新增条目（唯一告警 `medicine-relations.e2e-spec.ts` 在本轮之前已存在）。
- MCP 相关 **4 files / 27 tests 全过**，其中 `server.spec.ts` 是**真 Fastify + 真
  SDK client** 的端到端：tools/list 精确匹配、tools/call 走执行器、参数原样透传、

- 未验证：真实 sidecar 的工具执行（需 LightRAG/Semantica 起来）。

## fix(assistant): MCP 配置改走三层读取，补齐 env 模板

### 变更范围

- `mcp.module.ts`：删掉自造的 `readEnv`（`ConfigService ?? process.env`），改为
  `readSetting`：**运行时快照 → `ConfigService` → 兜底**，与 `lightrag-client.ts`
  等既有 sidecar 同形。注入 `RuntimeConfigService`。
- `retrieval.schema.ts`：`MCP_ENABLED` / `MCP_API_KEY` / `MCP_ALLOWED_ORIGINS`
  登记为运行时字段（`booleanField` / `stringField`，family `retrieval`）。
- `docs/reference/runtime-config.example.txt`：补三个键（这是 `docs:verify`
  按 schema 对账的文件）。
- `.env.development.example` / `.env.test.example` / `.env.production.example`：
  新增「11 · MCP 端点」段，其后各段编号顺延。
- `docs/reference/environment-variables.md`：补热更语义与「只作用于新会话」的边界。

### 说明

**`readEnv` 是我发明的，且是错的。** 它只做 `ConfigService ?? process.env`，
漏掉运行时快照层——那正是 rnacos 发布热键所依赖的一层。后果是 `MCP_ENABLED`
成了整个仓库唯一「改开关要重启」的 sidecar。仓里既有写法是三层
（见 `lightrag-client.ts` 的 `LIGHTAG_*` 读取）。回退到 `process.env` 的理由
（「兼容不注入 ConfigService 的测试」）也不成立：`ConfigModule.forRoot({ isGlobal:
true })`，`ConfigService` 一直在。

**热更的边界要写清。** 三个键都能热更，但路由在 `onModuleInit` 注册，所以
`false` 只阻止新会话；已注册的路由要重启才消失。中途摘路由会掐断在途 SSE 流。
操作顺序：置 `false` → 排空 → 重启。

**三份 `.env.*.example` 之前全漏了**（`MCP_` 条目数为 0）。`docs:verify` 只对账
`runtime-config.example.txt`，不检查 `.env.*.example`，所以门禁没拦住——这是门禁的
已知盲区，不是本次才有的。

### 验证

- `typecheck` 0 error；`lint:check` 0 error（4 个既有 warning）。
- `arch:check` 无新增条目（唯一告警 `medicine-relations.e2e-spec.ts` 系既有）。
- `docs:verify` 通过（含 `runtime-config.example.txt` 按键对账）。
- MCP 相关 3 files / 19 tests 全过（`server.spec.ts` 端到端不受影响）。
- 三份 env 模板 `MCP_` 条目数均为 3，段落编号 01–18/19 连续无重号。

## refactor(assistant): 工具名去除前缀并压短描述（24 个工具全量）

### 变更范围

- 24 个工具名统一为「动词_对象」短名，去掉 `_by_date` / `_by_range` / `_recent`
  这类把调用形态写进名字的后缀，也去掉 `medicine` / `passages` / `over` 这类可由
  领域推断的中段。知识检索组：`search_cn_products`、`get_cn_product_detail`、
  `search_cn_knowledge`、`resolve_drugbank`、`get_drugbank_detail`、
  `search_drugbank`、`reason_ontology`、`reason_rules`。
- 工具描述压到 400 字符以内，并把「该改调哪个邻居工具」写进描述（
  `tool-schema.spec.ts` 断言两者）。
- `domain/mcp/exposure.ts`：移除 `lucent__` 前缀与 `mcpToolName` / `parseMcpToolName`。
  命名空间冲突是**客户端**的职责（代理挂多个 server 时才加前缀，为的是没有 server
  能抢占别人的名字）；server 自加前缀在已加前缀的客户端上会变成双重前缀。
- `assistant.module.ts`：`exports` 补 `AssistantToolService`——`McpModule` 的执行
  适配器以它为唯一依赖，缺这条导出时 Nest 容器在启动期就抛
  `UnknownDependenciesException`。
- 契约链路重生成：`openapi.json`（工具名 enum）、Luminous
  `assistant_capabilities_response_tools.dart`、Lumine `lucent-api.ts`。

### 说明

**MCP 的两处接线从未被契约导出覆盖过。** MCP 是在 11-18 当天两次提交里落地的，
两次都没跑 `pnpm export:openapi`，而契约上次生成是 11-16——所以 `AssistantModule`
漏导出 `AssistantToolService` 这件事一直没暴露。本次导出第一次让它现形。

**导出脚本吞掉了这个错误。** `NestFactory.create` 默认 `abortOnError: true`，配合
`logger: false` 时 `ExceptionsZone` 先 `handle` 再 `process.exit(1)`，而 logger 是关的，
于是既没有栈也没有关键字。定位时临时把它改成 `abortOnError: false` 才拿到完整
`UnknownDependenciesException`；该调试改动已还原，脚本行为不变。这个静默退出值得
日后单独修（导出失败不该是零输出）。

**ADR 就地修订**：ADR-0008 与 ADR-0020 正文里提到的旧工具名已同步，各自标题下加了
`2026-11-18 修订` 注记；决策本体未动。`docs/TODO.md` 里「工具名如需改名在评测前定」
那条已随本次改名完成，按约定整行删除。`plans/2026-08-28-medicine-risk-graph-plan.md`
的引用同步更新。
