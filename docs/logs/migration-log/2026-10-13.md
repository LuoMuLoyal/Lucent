## fix(openapi): 导出改用 openapi-3.0 target，消除 spec 长期漂移

- 现象:`pnpm export:openapi` 产出与已提交的 `openapi.json` 长期不一致(481+/536−),且每次
  重导出都会复现。此前一直当作「既有的生成器行为」搁置。
- 根因:`scripts/contract/export-openapi.ts` 调 `z.toJSONSchema(schema)` **未传 `target`**,
  zod 因而按默认的 JSON Schema draft-2020-12 输出可空类型为 `type: ["string","null"]`;
  而本仓库的契约是 **OAS 3.0**,该形态在 3.0 里非法。两处叠加:
  1. 可空字段写成 2020-12 的 `type: [..., "null"]`,而非 3.0 的 `nullable: true`;
  2. 因输出是 `anyOf: [{type, description}, {type: "null"}]`,本地 `openApiSchema()` 的
     nullable 折叠分支把 `anyOf` 压平为 `{type, nullable:true}`,**顺带丢掉了 `description`**。
- 变更:`z.toJSONSchema(registration.schema, { target: 'openapi-3.0' })`(一行)。zod 直接产出
  3.0 形态,不再走 `anyOf` 折叠,描述得以保留。
- 验证:
  - 归因实验:把 zod 降回 `4.4.3` 后重导出,与已提交 spec **零 diff**;升回 `4.6.5` 则复现
    漂移 → 漂移由 zod 版本的行为差异触发(4.4.3 起 `toJSONSchema` 默认目标变化),而非某次
    业务改动。经查**与「事件回顾 null 崩溃」修复无关**:该提交(`3a64d0f5`)仅在
    `event-review-response.dto.ts` 加了一行注释,未改任何 schema。
  - 语义等价:新旧 spec 的 **operation 集合(154)与 schema 名集合(370)完全一致**,无端点增删;
    差异仅为可空编码与描述。
  - 输出合法:新 spec 内 `"type": [` 出现 **0** 次(原为 259 处),`nullable: true` 共 414 处,
    `info`/`openapi: 3.0.0` 不变。
  - 幂等:连续两次 `export:openapi` 产物稳定。
  - 门禁:`pnpm typecheck`、`pnpm lint:check`、`pnpm test:ci`、`pnpm export:openapi` 全部通过。
- 影响:`openapi.json` 本次纳入变更(它现在是正确形态)。修复后描述字段净增(此前被静默丢弃),
  对下游 Dart 客户端是**信息增加**,无字段增删或类型收紧。
