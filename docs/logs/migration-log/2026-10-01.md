# 2026-10-01

## Better Auth 全面移除,身份层回归 Lucent 自持

### 背景

`better-auth` 于 2026-09-21 由 Dependabot 从 1.7.1 升到 1.7.5(`82e3db5b`)。该 patch
在 `@better-auth/prisma-adapter@1.7.5` 中新增了 Prisma schema 自检:启动后调用
`introspectPrismaDataModel(prisma._runtimeDataModel)` 并与期望 schema diff。Prisma 7 的
`prisma-client` generator 把 `_runtimeDataModel` 生成为 `{"models": {}, "enums": {}, "types": {}}`,
自检因此判定所有表缺失,抛 `SchemaMismatchError`("Missing tables User"),导致**整个 auth
域 100% 返回 503**——生产调用点只有 4 处(`signUpEmail` ×1、`signInSocial` ×2、
`verifyEmail` ×1),其中 `verifyEmail` 实际为死路径(客户端从不签发其 token)。

评估结论:引入该库未覆盖 Lucent 已有的 JWT 签发、argon2 哈希、`user_sessions` 会话、
验证码与错误映射;其 `sessions` 表在 `src/` 中零读取方;一个 patch 升级即可打挂全模块。
故整体移除,身份层由 Lucent 自持。用户明确要求不新增 ADR。

### 变更范围

- **schema**:新增 `prisma/models/account.prisma`,以 Lucent 语义重建 `accounts`
  (issuer / providerId / accountId / password / providerUnionId / providerEmail /
  rawProfile 等),`id` 改为数据库侧 `gen_random_uuid()` 默认值;删除
  `prisma/models/better-auth.prisma`(附带 `sessions`、`verifications` 两表)。
- **迁移**:`prisma/migrations/20260930120000_lucent_owned_identity_accounts`
  删除 `sessions` 与 `verifications`,并为 `accounts.id` 补数据库默认值。
- **新增服务**:`services/identity/identity.service.ts`(`AuthIdentityService`,argon2
  哈希与 accounts 读写、本地用户创建/凭据校验)与
  `services/identity/email-verification.service.ts`(验证 token 签发与消费,
  消费采用先删后写,重复提交即失效)。
- **改写调用点**:凭据注册/登录、密码管理(改/重置/设置密码)、敏感操作重验、
  token 撤销、OAuth facade 与 account 自助管理全部改为调用上述自持服务;
  OAuth 社交登录不再走 `signInSocial`,Apple/Google 分别由各自 provider 完成
  identity token 校验(`GoogleOAuthProvider.fetchProfileFromIdToken` 新增,
  签名走 Google JWKS,复用 `@nestjs/jwt`,不引入新依赖)。
- **删除**:`adapters/better-auth.adapter.ts`、`scripts/spike/better-auth*`、
  依赖 `better-auth` 与 `@better-auth/prisma-adapter`(共移除 21 个包)。
- **环境变量**:`BETTER_AUTH_SECRET` / `BETTER_AUTH_URL` 从 `EnvKey`、校验 schema
  与全部 `.env*` 模板移除(已无任何读取方)。
- **文档**:`docs/reference/environment-variables.md`、`docs/howto/deploy.md`、
  `docs/TODO.md`、`src/modules/auth/README.md` 同步改为自持身份层口径。
  历史迁移日志按 append-only 规则不改写。

### 验证结论

- `pnpm typecheck`、`pnpm lint:check` 通过。
- 单元测试 324 文件 3866 例全通过(改写前先复现了 4 处适配器 mock 与
  2 处 schema 断言失败,逐一改为自持服务语义)。
- auth 与 account 域 e2e 共 95 例全通过;其中 auth 域此前 38 例失败(100% 503)
  归零。Apple 回调对不可验证 identity token 由 503 改判 400——属客户端校验失败
  而非依赖不可用,断言随之更新。
- 全量 e2e 仍有 6 例失败,集中在 CORS 预检、medicines 检索与 testing-support,
  相关文件均在 09-03~09-16 定稿且不引用 auth,与本次变更无关,另行跟踪。
- `pnpm docs:verify` 通过。

### 后续跟踪

- 全量 e2e 的 6 例既有失败(CORS 预检 404、medicines 中文源检索、
  testing-support 校验语义)未在本轮修复。

## 修复 CI 全量 e2e 失败并清零遗留用例

### 背景

上一节记录了 6 例既有 e2e 失败为「与本轮无关,另行跟踪」。`lucent-ci` 随后在 `main`
上确认红(单元、lint、Docker、OpenAPI 均绿,仅 `E2E Tests + Build + OpenAPI` 失败),
失败集合与本地复现完全一致,故本轮将其视为阻塞项逐一定因修复。

### 一、`startup-order` 套件 DI 失败

`CronJobsService` 新增第 6 个依赖 `MealAnalysisSweeperService`(meal-analysis 滞留
分析回收),但 `test/e2e/core/startup-order.e2e-spec.ts` 的测试模块未同步,`compile()`
抛 `Nest can't resolve dependencies ... at index [5]`,套件 `beforeAll` 失败——表现为
3 例全部 skipped,`afterAll` 再因 `moduleRef` 未赋值抛
`Cannot read properties of undefined (reading 'close')`,把套件记为 failed。

修复:测试模块补 `MealAnalysisSweeperService` stub;`SCHEDULER_IDS` 补第 5 个调度器
`meal-analysis-reap`,使断言覆盖该服务真实注册的全部调度器。

### 二、`medicines` 中文源检索用例

用例向 `cnMedicineProduct.create` 传入 `indications`,而该字段并不存在于
`CnMedicineProduct`(`indications` 属 `CnMedicineLeaflet`),CI 报
`Unknown argument \`indications\`` 使套件失败。用例断言只覆盖 id/source/name/
subtitle/imageUrl,该字段是从未参与断言的残留,直接移除。

### 三、CORS 断言与 CI 允许列表不一致

`assistant` 的 SSE 用例发送 `Origin: http://localhost:9100`,CORS 预检守卫用例发送
`https://web.example.com`,而 CI 的 `CORS_ORIGIN` 只有 `http://127.0.0.1:3000`。
`parseCorsOrigin` 支持逗号分隔多源,故断言取不到
`access-control-allow-origin`(undefined)。修复:CI 的 `CORS_ORIGIN` 扩为三源并注明
两个来源出处。另删除工作流中已失效的 `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL`。

### 四、`testing-support` 共享密钥解析错位

三条用例均返回 403。`test/e2e/testing-support/testing-support.e2e-spec.ts` 在
`beforeAll` 里 `process.env['TESTING_SHARED_SECRET'] = 'e2e-test-shared-secret'`,
但 `AppModule` 的 `ConfigModule.forRoot({ envFilePath })` 会在模块初始化时加载
`.env.test` 并**覆盖** `process.env`,守卫经 `ConfigService` 读到的是
`.env.test` 的值(`...-change-me`),两边不等即 403。已实测确认:
`process.env` 为测试写入值、`ConfigService` 为 `.env.test` 值。

而 `.env.test` 未被 git 跟踪,CI 完全依赖工作流 `env:`,其中并无
`TESTING_SHARED_SECRET`——守卫对空密钥一律 403,这是 CI 红的直接原因。

修复:用例不再硬编码密钥,改为在模块编译后经 `ConfigService.getOrThrow` 取应用真正
解析到的值(本地与 CI 两种来源下均通过);工作流补 `TESTING_SHARED_SECRET`。

### 验证结论

- `pnpm typecheck`、`pnpm lint:check` 通过;`pnpm arch:check` 退出码 0(既有
  `endpoint-auth-posture` 告警维持 warn,不阻断)。
- 单元测试 3866 例全通过。
- **全量 e2e 30 文件 493 例全部通过**,上一节遗留的 6 例失败清零。
- `pnpm docs:verify`、`pnpm docs:links` 通过。

## 移除 Apache AGE 残余:镜像、元数据与文档

### 背景

ADR-0022 决定图后端由 Apache AGE 改为 Neo4j 后,AGE 资产按该 ADR 决定 7「暂不删除,
保留为回滚路径」被保留。实际检查发现**代码侧存在事实性错误而非单纯的历史遗留**:
`lucent_graph` 是 AGE 时代 Postgres 里的 database 名,而图早已迁到 Neo4j,
Lucent 侧的 8 处引用却仍把它当作数据来源名,并且还被拼上硬编码的 `(Neo4j)` 后缀
输出给模型当溯源元数据——即「用 AGE 的库名标注 Neo4j 的数据」。
观察期结束,连同镜像一起整体清理。

### 变更范围

- **镜像**:`docker/postgres-age/` → `docker/postgres/`(git mv 语义)。Dockerfile
  删除 AGE 构建阶段(`AGE_REF` 参数、AGE tarball 下载与编译)与最终镜像里的
  `age.so` / `age.control` / `age--1.7.0.sql` 三个 COPY,以及
  `CMD ["postgres", "-c", "shared_preload_libraries=age"]`(回落到基底默认 CMD);
  构建阶段改名 `builder`,继续保留 zhparser + SCWS 编译。README 同步重写为
  去 AGE 口径,并记录扩展集与「AGE 已移除」。
- **元数据**:`ontology-reasoning.service.ts` 的 `tables` 由
  `` `${graphSchema.graph} (Neo4j)` `` 改为 `[graphSchema.graph]`——该值来自 sidecar
  `/schema` 的 `graph` 字段,即 `settings.neo4j_database`(默认 `neo4j`),
  本身就是图库真名,拼引擎后缀已无意义。`rule-reasoning.service.ts` 的
  `tables: ['lucent_graph (Neo4j, rule-derived)']` 改为 `['neo4j (rule-derived)']`。
- **测试**:`ontology-reasoning.service.spec.ts`(fixture `graph` 与 `tables` 断言)、
  `semantica-client.service.spec.ts`(schema 解析 fixture ×2)、
  `core.service.spec.ts`(mock envelope ×2)全部由 `lucent_graph` 改为 `neo4j`。
- **文档**:`README.md` 本地基础设施段改为 zhparser 口径并指向 ADR-0022;
  `compose.dev.yaml` 注释同步;ADR-0022 的 Status 由「实施未开工」更正为
  「已实施完毕」,决定 7 追加后续说明(保留原文,符合 ADR 只增不改);
  `docker/postgres/README.md` 新增「AGE 已移除」小节。

### 验证结论

- **镜像实测**:重建 `lucent-db:18` 后,镜像内不再含 `age.control` /
  `age--1.7.0.sql`,剩余 `pg_trgm` / `vector` / `zhparser`;`CMD` 为基底默认 `postgres`。
  起容器实跑确认 `CREATE EXTENSION vector` / `zhparser` / `pg_trgm` 三者均成功,
  而 `CREATE EXTENSION age` 报 `extension "age" is not available`,装后扩展列表为
  `pg_trgm, plpgsql, vector, zhparser`。镜像体积 166,825,181 → 165,317,338 B。
- `tsc -p tsconfig.typecheck.json --noEmit` 退出码 0。
- 受影响单测 3 文件 65 例全通过(ontology-reasoning 27、core.service 38;
  semantica-client 含于前者的运行批次)。
- `pnpm docs:verify`、`docs/links.ts` 通过(62 个 markdown 无断链,67 个路径可解析)。
- 全量仓库范围复核:`.yaml/.yml/.ts/.json/.sh/.example` 中已无
  `postgres-age` / `shared_preload_libraries=age` / `lucent_graph` / `AGE_REF` 残留

### 后续跟踪

## 修复日志默认值被校验层覆盖

### 背景

`environment.validation.ts` 给 `LOG_LEVEL` 写了 `.default('debug')`、给
`LOG_FORMAT` 写了 `.default('pretty')`。两者都不该有默认值:默认值由环境决定,
解析在 `src/common/logger/logger.config.ts`。

`resolveLevel` 是 `if (logLevel) return logLevel` —— 显式值总是短路,于是按环境
解析的默认级别(development `debug` / test `error` / production `info`)成了永不
执行的死代码,生产实际按 `debug` 打日志。

`LOG_FORMAT` 在同一处失效:`logger.config.ts` 的意图是"未设置时,非 development
一律用 JSON",但 `logger.module.ts` 的 `?? ''` 永不触发,`useJsonFormat` 被钉死为
`false` —— 生产打的是 pretty 而不是 JSON,直接影响日志采集。

两个既有 spec 都没抓到:它们直接调 `createLoggerOptions`,绕开了 schema 这一层。

### 变更范围

- `src/config/env/environment.validation.ts`:`LOG_LEVEL` 与 `LOG_FORMAT` 的
  `.default(...)` 移除,改为 `.optional()`,并补注释说明为何刻意不给默认值。
- `docs/reference/environment-variables.md`:新增 `LOG_FORMAT` 条目,改写
  `LOG_LEVEL` 的默认值说明。

### 验证结论

- 临时 spec 跑通**端到端链路**(env 对象 → zod schema → `createLoggerOptions` 的
  transports):未设置时 production 解析为 `info`、test 为 `error`、development 为
  `debug`;显式 `warn` 仍然优先。修复前该链路在 production 下给出 `debug`,
  断言据此可回归。
- `LOG_LEVEL` 与 `LOG_FORMAT` 未设置时均不出现在校验结果中。
- `pnpm typecheck`、`pnpm lint:check`、`pnpm docs:verify`、`pnpm docs:links` 全部
  通过;全量单测 exit 0。

### 副作用

未显式设置 `LOG_FORMAT` 的测试环境,日志格式由 pretty 变为 JSON —— 这正是设计
意图(既有用例 `LOG_FORMAT=pretty overrides test to pretty` 的命名就以 JSON 为
测试默认)。三个模板都显式给出了各环境的 `LOG_FORMAT`,按模板重填后取值不变;
本机现有的 `.env.test` 未设置该项,重填前 e2e 日志会是 JSON。

## 跨云部署:Semantica 补 bearer 鉴权 + 比赛期端口全开

### 背景

两项改动都源自同一个事实:部署从"单机 compose 网络"变成**跨云**(app 在鲲鹏,
Neo4j 与 semantica sidecar 在腾讯云)。

1. **sidecar 原先不带任何凭据**,而且是刻意的:代码注释写明"sidecar 是我们自己的
   服务、只在内网 compose 网络上(不发布宿主端口、不挂 Traefik),要暴露给公网时
   必须先加鉴权"。跨云正好就是那句"暴露给公网"—— 两朵云的 VPC 不互通,流量走
   公网,该前提不再成立。
2. **`expose` 到不了另一台机器。** 生产 `compose.yaml` 里 semantica 与 neo4j 都只有
   `expose:`,即仅容器网络可达。跨云调用必须发布宿主端口。

副作用是暴露面从"整个容器网络"扩大到"宿主端口":无鉴权的 `/query` 会按调用方的
要求执行只读 Cypher,于是第 1 项从"可以有"变成"必须有"。

### 变更范围

- `semantica-service/`(独立仓):
  - `config.py` 新增 `api_token`;空值即"未配置"。
  - 新增 `security.py`:`HTTPBearer` + 常量时间比较,401 返回结构化
    `{"detail": {"kind": "unauthorized"}}`(与既有错误契约同形)并带
    `WWW-Authenticate: Bearer`。
  - `main.py`:`create_app()` 在 `api_token` 为空时抛错拒绝启动;鉴权依赖挂在除
    `/health` 外的每个 router 上 —— `/health` 保持免鉴权,因为 compose 的
    healthcheck 与负载均衡探针都调它,两者都带不了凭据。
  - `.env.example` 补 `API_TOKEN`;`pyproject.toml` 给 ruff 加
    `flake8-bugbear.extend-immutable-calls`(FastAPI 的 `Depends()` 惯用法,非
    B008 要防的可变默认值)。
- `Lucent/`:
  - `EnvKey.SEMANTICA_API_KEY` + schema 条目 + `assertSemanticaEnvironment`
    跨字段校验(仅 `SEMANTICA_ENABLED=true` 时强制,空串视为未配置)。
  - `semantica-client.service.ts` 每个请求带上 `Authorization: Bearer`(含 GET:
    sidecar 把鉴权挂在路由级,`/schema` 也要令牌)。
  - 三个 `.env.*.example` 与 `deploy/semantica/.env.example` 补该项。
  - `compose.yaml`:全部服务端口发布到宿主(见下),并改写了两处已经失效的注释
    (semantica 的"不鉴权"、node-exporter 的"不把 9100 暴露到网卡")。
  - `docs/TODO.md` 新增"比赛期临时发布的端口"条目,列出每个端口的目标形态。

比赛期端口:新增 `5432`(postgres)、`6379`(redis)、`3000`(app)、`9621`(lightrag)、
`7687`+`7474`(neo4j)、`8099`(semantica)、`9100`(node-exporter);`8428`/`3001`/`9428`
原本就已发布。这是**有意的临时姿态**,可调试性优先,由安全组按来源 IP 白名单收口;
正式生产的收回清单在 `docs/TODO.md`。

### 验证结论

- `semantica-service`:全量 pytest 通过(新增 `test_auth.py`:无令牌/错令牌/恶意前缀/
  畸形头全部 401、`WWW-Authenticate` 存在、`/health` 仍免鉴权、缺令牌时 `create_app()`
  抛错;并有一条**结构性**断言把 app 实际路由与"受保护 + 开放"两张清单对账,新增

  client spec 断言 POST 与 GET 都真的发出了 `Authorization`,且取的是配置值而非字面量。
- `docker compose -f compose.yaml config` 校验通过;`pnpm typecheck`、`pnpm lint:check`、
  `pnpm docs:verify`、`pnpm docs:links` 通过。
