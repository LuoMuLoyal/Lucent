# 迁移日志 2026-10-03

## CI/CD 规范化:workflow 按关注点拆分、双架构原生构建、镜像 tag 改为 `sha-<sha8>`

### 背景

`lucent-ci.yml` 一个文件装了 lint / 单测 / e2e / docker 构建 / Trivy 五件事,
`lucent-production.yml` 只构建 `linux/amd64` 且 tag 为 `<sha8>`(无架构后缀)。
问题有三:

1. **权限粒度粗**:一个文件里所有 job 共享 `permissions`,写权限只能整体给;
2. **失败不隔离**:镜像构建挂了等于门禁挂了,且无法独立触发;
3. **架构覆盖有洞**:生产主站跑 arm64,而 CI 与发布都只构建 amd64 —— **arm64 那一层从未被构建、也从未被扫描过**。

tag 用 `<sha8>-<架构>` 还把架构耦合进了引用,换机器必须改 tag。

### 变更

**workflow 拆分与重命名**(Lucent):

| 文件          | `name:`   | 职责                                         |
| ------------- | --------- | -------------------------------------------- |
| `ci.yml`      | `CI`      | lint / typecheck / 单测 / e2e + OpenAPI 契约 |
| `docker.yml`  | `Docker`  | 双架构构建 + Trivy(**不推送**)               |
| `release.yml` | `Release` | 发布 multi-arch 镜像(手动,限 main)           |

job 内容从旧文件逐字迁移;`lucent-ci.yml` / `lucent-production.yml` 已 `git rm`。
新增 `.github/workflows/README.md` 记录各文件职责与发布模型。

**双架构原生构建**:`ubuntu-24.04-arm` 对公开仓库免费(本仓库 public),因此
**每架构用原生 runner 构建,不走 QEMU**。这同时消除了一类真实风险 —— 模拟环境下的
工具链行为与原生不同(本项目此前实测 QEMU 下 `prisma` 会 panic),而 arm64 是生产架构。

**`release.yml` 发布两个镜像**,都用「按架构原生构建 → 各自按 digest 推送 →
merge job 用 `buildx imagetools create` 合成 manifest list」:

- `lucent` ← 仓库根 `Dockerfile`
- `lucent-db` ← `docker/postgres/Dockerfile`(编译期产出 zhparser 原生 `.so`,天然架构相关)

**tag 规范化为 `sha-<git sha 前 8 位>`(不含架构)**:tag 指向 multi-arch manifest list,
Docker 按目标平台自动选层,于是换架构不必改 tag,只改 sha。
**不新增 secret**:DB 镜像从已有的 `REGISTRY_IMAGE` 派生同命名空间的 `<namespace>/lucent-db`。

**`docs/links.ts` 的路径校验补上 `.github/`**:此前 `PATH_TOKEN_RE` 只覆盖
`docs|src|plans|scripts|test|prisma|monitoring|deploy`,**不覆盖 `.github/`** ——
这正是 workflow 改名后文档引用悄悄腐烂的盲区(改完名后 `lucent-ci.yml` 已不存在,
但文档里指向它的引用不会被任何门禁拦住)。已加回归脚本证实该覆盖真的生效。

**文档同步**:`docs/reference/deployment.md`、`docs/howto/deploy.md`、
`docs/reference/environment-variables.md`、`compose.yaml`、`README.md`、
`docs/reference/adr/0023-*.md`、`docs/TODO.md` 中所有 `<sha8>-<架构>` 引用
改为 `sha-<sha8>`,并更新 workflow 名与 job 名引用。

### 本地 dry-run 逮到的三个真缺陷

YAML 语法检查全绿,但把 `release.yml` 的 bash 抽出来用桩输入实跑后暴露三处:

1. **跨镜像 digest 污染**:merge 原用 `digests-<image>-*` 通配,而 `digests-lucent-`
   是 `digests-lucent-db-` 的**前缀** → DB 层的 digest 会被合进 app 的 manifest。
   改为显式遍历 `$ARCHES` 逐架构取目录。
2. **假 reference**:空目录下 `("${dir}"/*)` 不展开时字面保留 `*`,生成
   `...@sha256:*` 这种假 reference 并静默推畸形 manifest。补 `shopt -s nullglob`
   并把「每目录恰好 1 个 digest」作为硬断言。
3. **校验形同虚设**:`docker.io/lucent`(有 registry 无属主)能通过校验,派生出的
   DB 镜像变成 `docker.io/lucent-db` —— 那是 Docker Hub 官方库的名字,推送必被拒。
   补「首段带 `.`/`:` 即视为 registry,此时必须还有属主段」的判断。

三处各留了回归断言钉住原因(含"去掉 nullglob 就复现"的反证),避免日后被"简化"回去。

### 验证

- 两仓库共 5 个 workflow 文件通过 YAML 解析与结构 lint(含 `needs`/`uses` 引用、
  matrix 键引用、workflow 名唯一性)
- `pnpm docs:verify` / `pnpm docs:links` 通过
- `docker compose -f compose.yaml config` 通过(临时目录 + 桩 `.env`)
- `release.yml` shell dry-run:命名空间派生 8 组输入(含 4 组应拒绝)、
  逐架构选层、缺失/多余 digest 拒绝、DB 隔离、旧通配复现污染 —— 全部符合预期

### 不做的事

**不重新部署**。现有三台服务器继续按原 tag 运行,新的 `sha-<sha8>` 方案只对后续
发布生效;因为 tag 已与架构解耦,将来换架构也不需改 `LUCENT_IMAGE`。

`Luminous` 侧同步做了同样的规范化(拆为 `ci.yml` / `deploy-web.yml`),
其自动触发条件(含 `refactor` 分支)原样保留。
