# 2026-09-14

## refactor(daily-records)!: 睡眠 payload 校验收敛,移除 start/wake 临时事件例外

### 背景

睡眠 payload 的时间键位此前是「双键并存」：DTO 把 `startedAt` / `endedAt` 描述为正式键，同时声明
「legacy `startAt` / `endAt` remain readable」，校验器与各读取方一律写 `payload['startedAt'] ??
payload['startAt']`。此外校验器专门为快速录入的两阶段睡眠流程开了一个逃生口：payload 带
`sleepEvent: 'start' | 'wake'` 时整段跳过校验，允许落一条没有 `durationMinutes` 的临时事实。

客户端已改为一次性录入（同一批改动的前一个提交），不再产生 `sleepEvent` 事实，也不再写 legacy 键，
因此这套兼容读取与逃生口整体删除——App 未上线，不设兼容窗口、不迁移旧记录。

### 变更

- `records-validator.service.ts`：删除 `sleepEvent === 'start' | 'wake'` 的提前返回；时间键只读
  `startedAt` / `endedAt`，不再回退 legacy 键。
- `sleep-trend-builder.service.ts`、`today-analysis/.../context.service.ts`、
  `assistant/tools/read/read.service.ts`：payload 读取统一为 `startedAt` / `endedAt`（内部上下文与工具输出
  的字段名保持不变，它们不是 wire 键）。
- `schemas/daily-record-candidates.schema.ts`：LLM 候选的结构化输出同样收敛到
  `startedAt` / `endedAt`（该 schema 是 `.strict()`，键位即契约）。
- 三处 DTO 描述串去掉 legacy 说明，`record-item.dto.ts` 的示例键位补上 `sleepType` 并改正键名。
- `docs/reference/generated/openapi.json` 重新导出。

### 验证

- `pnpm typecheck` 通过。
- 定向单测通过：`vitest run src/modules/daily-records src/modules/today-suggestion/services/collectors
src/modules/reports/services/event-review src/modules/today-analysis/services/pipeline
src/modules/assistant/tools/read`。
- 测试面同步：删除两条「允许无 durationMinutes 的 start/wake 临时记录」用例，新增一条
  「带 `sleepEvent` 但无 `durationMinutes` 的睡眠记录必须被拒绝」用例；其余睡眠 payload 夹具的键位改名。

## refactor(today-suggestion)!: 症状严重度改读 payload 码,删除文本启发式

（症状链路优化 Phase 1 服务端侧；计划文档见 Luminous `plans/2026-09-14-symptom-chain-optimization.md`，
执行完毕后删除。）

### 背景

客户端把症状严重度写进记录级 `value`，且是本地化字符串（`轻度` / `Mild`）；四个预置症状的 `payload` 为 null。
`deteriorating-trend.service.ts` 的 `extractSeverity()` 却只从 `value` / `note` 里猜：先试 `3/5`、`7/10` 这类
数字，再对 `note` 做「加重 / 严重 / 中等 / 轻微」关键词匹配，都失败就 `return 1`（默认最小严重度）。

于是快速录入的每条症状记录一律得 1 分：`checkDeterioration()` 要求严格递增，`deteriorating_symptom` 规则
**从未触发过**；`collectors/record.service.ts` 的 `observedValue`（`parseNumericValue(value)`）同样取不到值，
症状信号恒为 `coverage.sufficient: false`。此外规则按**标题**分组，而标题是客户端写入时的本地化文案，用户换语言
后同一条症状会被拆成两组。

### 变更

- 新增 `today-suggestion/constants/symptom-severity.constants.ts`：严重度码 → 分值（mild=1 / moderate=2 /
  severe=3）；`unknown` 与未知值一律返回 `null`（无观测），调用方必须跳过，不得回落成最小严重度。
- `deteriorating-trend.service.ts`：`SymptomEntry` 改带 `symptom`（目录码）与 `severity`（严重度码）；分组键由
  标题改为目录码；`extractSeverity()` / `parseSeverity()` 与 `note` 关键词分支整体删除；
  `checkDeterioration()` 先过滤 `null` 再比较（已知观测少于 2 条即不判定）；证据/文案里的 `symptomTitle` 取最新
  一条记录的标题，标题为空时回落目录码。
- `collectors/record.service.ts`：`buildSymptomTrend()` 输出码位（`symptom` / `severity`，去掉已不再使用的
  `note`）；`observedValue` 改由 `symptomSeverityScore(payload.severity)` 得到，顺带删除失去消费方的
  `parseNumericValue()`。
- `daily-records/services/records-validator.service.ts`：新增症状 payload 校验（`symptom` 非空字符串、
  `severity ∈ {mild,moderate,severe,unknown}`、`customLabel` 字符串；整体可选，NLP 候选无 payload 仍可创建）；
  目录成员资格不由这里定义。
- `create-record.dto.ts` / `record-item.dto.ts` 的 payload 描述串补症状形状，并注明「`severity` 是唯一结构化
  严重度来源，`title`/`value` 只是展示文案」；`docs/reference/generated/openapi.json` 重新导出。

### 验证

- `pnpm typecheck` 通过。
- `vitest run src/modules/today-suggestion src/modules/daily-records`：57 个文件、630 例通过。
- 规则 spec 重写为码位夹具，新增用例：按码分组（同标题不同码不误命中）、`unknown` 跳过而非记最小、已知观测不足
  两条不判定、以及「文本里的 `4/5` 不再被解析」；collector spec 补 `observedValue` 断言与 `unknown` → 无观测值
  两条。
- 破坏性：症状严重度的数据来源由 `value` 文本改为 `payload.severity`，不再从文本推断（产品未上线，不做历史数据
  迁移）。
