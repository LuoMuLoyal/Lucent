### 说明

**表名只改带模块名的那几个。** `user_profiles` / `user_sessions` / `user_allergies`
里的 `user_` 表示「这一行属于某个用户」，不是模块名；`medicine_*` 属于未改名的
`medicines` 模块。改名的是 `user_daily_records` → `records`、
`user_medicine_reminders` → `reminders`、`data_export_requests` → `export_requests`
等 10 张。

**迁移里索引与外键也要改名。** `ALTER TABLE ... RENAME` 不改索引名，而索引名会出现在
慢日志、`EXPLAIN` 与锁等待输出里；不改它们等于旧名换个地方继续存在。新索引名以
`prisma migrate diff --from-empty --to-schema prisma` 推导为准，注意 Prisma 对超过
63 字符的名字做了截断。

### 顺带修掉两个既有缺陷

1. **`prisma` 多文件 schema 未被 `migrate diff` 正确读取**：`schema.prisma` 只有
   generator 与 datasource，模型在 `prisma/models/`；`prisma.config.ts` 的
   `schema: 'prisma/'` 指向目录才生效。先前若有人按单文件路径调 `migrate diff`
   会得到「empty migration」，误以为模型未被识别。
2. **`scripts/contract/export-openapi.ts` 的 `logger: false` 会吞掉 DI 失败**：
   Nest 通过 logger 报告依赖解析失败然后 `process.exit(1)`，`main()` 的 `catch`
   根本收不到，命令表现为**零输出 exit 1**。改为 `logger: ['error']` +
   `abortOnError: false`，让失败抛回 `catch`，并在那里补一句「这是依赖注入失败，
   不是契约问题」+ 指向 `{ provide: 抽象类, useExisting }` 的提示。

## 本地数据库：test 合并进 dev 实例

### 变更范围

- `compose.dev.yaml` 删除 `postgres-test` 服务与 `pgdata-test` 卷；`postgres-dev`
  端口由 15432 改为 5432（原 test 占用）。
- 新增 `docker/postgres/init-test-db.sql`：空卷首次启动时建 `test` database，
  并装 vector / pg_trgm / zhparser 与 `chinese` 分词配置。
- `.env.development` 与 `.env.test` 指向同一实例：`lucent` 与 `test` 两个库。
- `AGENTS.md`、`README.md`、`docs/reference/environment-variables.md`、
  `docker/postgres/README.md` 同步。

### 说明

**隔离只到 database 粒度，这与 e2e 的要求一致。** e2e 清的是自己的表，从不碰
`lucent`；两个 database 之间没有跨库查询路径，`migrate reset` 也只作用于目标库。
原先两个容器的代价是同一台机器上两份 Postgres、两份卷、两套扩展与健康检查，
而故障域本来就相同（同一块盘、同一个 Docker）。

**`.env.test` 原先有两行 `DATABASE_URL`**，后者生效，读第一行的人会以为连的是
15432。合并时一并去掉重复行。

**旧的 `pgdata-dev` 卷不会重跑 initdb**，所以已在用该卷的机器要手工补建
`test` 库并装扩展，步骤写进 `docker/postgres/README.md`。

### 验证

- 迁移在合并后的实例上应用成功；全新 `test` 库从零重放 84 个迁移成功。
- `test/e2e/admin/admin-data.e2e-spec.ts` 18 tests 全过。

## 已应用迁移不再改写，槽位索引改名补进新迁移

### 变更范围

- `20260803110000_add_user_suggestions_locale` 与
  `20261124120000_add_dose_log_slot_uniq` 还原为应用时的内容（模块短名重构曾
  就地改过它们的注释与索引名）。
- `20261124150000_rename_tables_to_short_module_names` 的索引重命名表补上
  `user_medicine_dose_logs_slot_uniq` → `dose_logs_slot_uniq`。
- `admin/` 前端资源键与 legal 端点跟随后端改名（见下一条）。

### 说明

**已应用的迁移是不可变文件。** 模块短名重构把它们一并改写了：注释里的模块名
改了不算事，但 `20261124120000` 连 `CREATE UNIQUE INDEX` 的名字都换了，等于让
迁移历史和真实库记录的 checksum 分叉——任何已经应用过旧版本的库都会变成
"modified migration"。改名本身是合理的，问题只在于落点：索引改名属于
`20261124150000` 的职责（那一条本来就在处理表/索引/约束改名），把它挪过去，
历史迁移就能保持原样。

**`dose_logs_slot_uniq` 不是自动跟过来的。** `ALTER TABLE ... RENAME` 不改索引名，
`20261124150000` 的索引表逐条列举，漏一条就留下旧名。而
`PrismaDoseLogs.isSlotConflict` 按名字识别 P2002，名字对不上会让并发插入
冲突从"收敛到赢家那一行"退化成 409。

### 验证

- 临时库从零重放 85 个迁移成功，`dose_logs` 上索引名为 `dose_logs_slot_uniq`。
- `db:reset:test` 在 test 库从零重放 85 个迁移成功，同样得到短名索引。
- dev 库 `migrate deploy` / `migrate status` 均为 up to date。
- `dose-logs.spec.ts` 新增索引名与迁移文本的一致性断言（28 tests 全过）。

## admin 控制台跟随后端短名

### 变更范围

- `admin/src/config/data-resources.ts`：10 个资源键改为后端注册表的短名
  （`user-medicine-reminders` → `user-reminder`、`user-daily-records` →
  `user-record`、`user-today-analysis-materializations` →
  `user-analysis-materializations`、`data-export-requests` → `export-requests`
  等），并删除随 `20261122140000` 一起消失的 `assistant-memories`。
- legal 相关：资源键 `legal-documents` → `legal`，端点
  `/admin/content/legal-documents` → `/admin/content/legal`；路由目录
  `routes/_authenticated/content/legal-documents/` → `.../legal/`，侧栏与
  nav-access 权限表同步。

### 说明

**这类改名后端与前端是两份清单。** 后端 `constants/resource-registry.ts` 决定
`/admin/data/:resource` 认哪些键，前端 `config/data-resources.ts` 决定选择器里
列哪些——两边不一致时后端返回 404，而前端只是把那个入口显示得像能用。短名重构
只改了后端，所以控制台里 10 个资源会全线 404。legal 更隐蔽：它走的是
`/admin/content/*` 而不是通用数据层，端点名也跟着 `@Controller('admin')` 下的
`content/legal` 变了。

`routeTree.gen.ts` 是 TanStack Router 的生成物，改目录后要先跑一次
`vite build` 让它重写，`tsc -b` 才不会拿旧路由树报类型错。

### 验证

- `pnpm build`（含 `tsc -b`）通过；`pnpm lint`、`pnpm format:check` 通过。
- 前端 50 个资源键全部存在于后端注册表，无一 404。
