### 说明

**表名只改带模块名的那几个。** `user_profiles` / `user_sessions` / `user_allergies`
里的 `user_` 表示「这一行属于某个用户」，不是模块名；`medicine_*` 属于未改名的
`medicines` 模块。改名的是 `user_daily_records` → `records`、
`user_medicine_reminders` → `reminders`、`data_export_requests` → `export_requests`
等 10 张。

**迁移里索引与外键也要改名。** `ALTER TABLE ... RENAME` 不改索引名，而索引名会出现在
慢日志、`EXPLAIN` 与锁等待输出里；不改它们等于旧名换个地方继续存在。新索引名以
`prisma migrate diff --from-empty --to-schema prisma` 推导为准，注意 Prisma 对超过
63 字符的名字做了截断。

### 顺带修掉两个既有缺陷

1. **`prisma` 多文件 schema 未被 `migrate diff` 正确读取**：`schema.prisma` 只有
   generator 与 datasource，模型在 `prisma/models/`；`prisma.config.ts` 的
   `schema: 'prisma/'` 指向目录才生效。先前若有人按单文件路径调 `migrate diff`
   会得到「empty migration」，误以为模型未被识别。
2. **`scripts/contract/export-openapi.ts` 的 `logger: false` 会吞掉 DI 失败**：
   Nest 通过 logger 报告依赖解析失败然后 `process.exit(1)`，`main()` 的 `catch`
   根本收不到，命令表现为**零输出 exit 1**。改为 `logger: ['error']` +
   `abortOnError: false`，让失败抛回 `catch`，并在那里补一句「这是依赖注入失败，
   不是契约问题」+ 指向 `{ provide: 抽象类, useExisting }` 的提示。

## 本地数据库：test 合并进 dev 实例

### 变更范围

- `compose.dev.yaml` 删除 `postgres-test` 服务与 `pgdata-test` 卷；`postgres-dev`
  端口由 15432 改为 5432（原 test 占用）。
- 新增 `docker/postgres/init-test-db.sql`：空卷首次启动时建 `test` database，
  并装 vector / pg_trgm / zhparser 与 `chinese` 分词配置。
- `.env.development` 与 `.env.test` 指向同一实例：`lucent` 与 `test` 两个库。
- `AGENTS.md`、`README.md`、`docs/reference/environment-variables.md`、
  `docker/postgres/README.md` 同步。

### 说明

**隔离只到 database 粒度，这与 e2e 的要求一致。** e2e 清的是自己的表，从不碰
`lucent`；两个 database 之间没有跨库查询路径，`migrate reset` 也只作用于目标库。
原先两个容器的代价是同一台机器上两份 Postgres、两份卷、两套扩展与健康检查，
而故障域本来就相同（同一块盘、同一个 Docker）。

**`.env.test` 原先有两行 `DATABASE_URL`**，后者生效，读第一行的人会以为连的是
15432。合并时一并去掉重复行。

**旧的 `pgdata-dev` 卷不会重跑 initdb**，所以已在用该卷的机器要手工补建
`test` 库并装扩展，步骤写进 `docker/postgres/README.md`。

### 验证

- 迁移在合并后的实例上应用成功；全新 `test` 库从零重放 84 个迁移成功。
- `test/e2e/admin/admin-data.e2e-spec.ts` 18 tests 全过。
- `typecheck` exit 0；`lint:check` 0 error；`arch:check` passed；文档门禁 passed。

## admin 资源注册表残留已删模型

### 变更范围

`src/modules/admin/constants/resource-registry.ts` 删除 `assistant-memories`
资源与它在 `ADMIN_USER_RELATED_GROUPS` 里的引用。

### 说明

`assistant_memories` 表已由 `20261122140000_drop_assistant_memories` 删除，
但注册表仍引用 `model: 'assistantMemory'`。表现不是启动失败，而是
`GET /admin/users/:id/related` 返回 **400 `Unknown resource model: assistantMemory`**
——注册表把缺失模型当成查询参数校验失败，路径与措辞都指向错误方向。
是 e2e 在改完库之后才暴露出来的。
