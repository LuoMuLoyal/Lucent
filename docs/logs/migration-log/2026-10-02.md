## 修复药品导入余数批丢失（`readline was closed`）

`scripts/shared/db-upsert.ts` 的 `streamParseAndUpsert` 原先用
`for await (const line of readline.createInterface(...))` 读解析器 stdout。
循环体内 `await flushBatch()` 会在每批写入数据库时长时间暂停消费 stdout；
子进程输出完毕退出后，readline 的内部状态与其 `close` 事件竞争，在循环末尾抛出
`readline was closed`。后果有两层：

- 该次导入被记为 `status = failed`（`note` 字段留错误文本），但进程仍以 0 退出，
  上层只看到「导入完成」；
- `summary.rawRowCount` 赋值语句在抛错点之后，因此始终为 `0`；
- **最后一批（不足 `batchSize` 的余数批）没有写入**。

实测：`product_leaflet_links.parquet`（63,889 行）稳定只写入 63,800 行，
即 638 个整批，恰丢末尾 89 行（源索引 63800..63888）。同规模的
`products_dedup.parquet`（同为 63,889 行）因每批写入耗时不同未触发，
属于典型的时序相关丢数据，只在特定数据规模下显现。

改为在 `child.stdout` 的 `data` 事件上手工切行：读取同步完成、不依赖 await 时序，
行处理串到一条 promise 链上顺序执行，既保留逐批 await 写入又不阻塞读取。
配套处理：最后一行可能无换行符、显式等待流 `end`、捕获 `stdout` 的 stream error。

验证：清空 `cn_medicine_product_leaflet_links` 后全量重跑，`rawRowCount` 与
`importedRowCount` 均为 63,889，源表与目标表逐表对账一致，`readline was closed`
不再出现。`pnpm typecheck` 与 `pnpm lint:check` 通过。

同源问题也影响过 `drugbank_external_links` 的一次导入（同样 63,800 行 + `failed`），
修复后该表已重新导入为完整的 19,800 行。

新增 `scripts/shared/db-upsert.spec.ts` 钉住该行为：用桩解析器输出已知行数，
断言 `flushBatch` 收到的批次序列。核心用例取 `rows % batchSize !== 0` 的形状
（63,889 / 100 → 638 个整批 + 余 89），并单独断言 `rawRowCount` 非 0 ——
后者正是旧写法下 `drug_source_imports.raw_row_count` 恒为 0 的指纹。
用 `pnpm test:tools` 跑（`scripts/` 不走 Nest 测试面）。

## LightRAG 按说明书灌入器（可断点续传）

新增 `scripts/import/medicine/import-lightrag-leaflets.ts`（`pnpm import:lightrag:leaflets`）。

既有的 `rebuild-lightrag-index.ts` 以 **chunk 表** 为粒度，一份说明书被拆成几十个
独立文档，中断后只能回答"第 N 个 chunk 灌到哪"，无法回答"哪份说明书灌完了"；
且其 `--limit` 截的是 chunk 数，`--limit=10` 连一份说明书都不到。新脚本改以
**一份说明书 = 一个文档**（`file_source = leaflet:<leafletId>`）为原子单位，
chunk 交回 LightRAG 自己按 token 切，段序不再影响溯源——`leaflet:<id>` 前缀
已足够定位到说明书。

断点续传分三层，可信度递减：① 服务端 `doc_status`（`processed` 才算完成，在
Postgres 里，重启不丢）；② 本地账本 JSONL（每份追加一行，仅为避免全量拉服务端）；
③ `--force`。账本与①冲突时以①为准。同 `file_source` 重复提交时 LightRAG 返回
409，脚本视为"已完成"而非错误——这是续传可安全重跑的前提。
实测把账本改名后重跑，10 份仍被正确识别，服务端兜底有效。

## 修 LightRAG 嵌入维度不匹配（`EMBEDDING_SEND_DIM`）

首次按说明书试灌 10 份时 **10/10 全部 failed**，错误为
`Embedding dimension mismatch detected: total elements (10240) cannot be evenly
divided by expected dimension (768)`。

根因不在维度选错，而在**没把维度发出去**：`text-embedding-v4` 的默认输出是
1024 维，只有请求里显式带 `dimensions` 才返回 768。LightRAG 侧
`EMBEDDING_DIM=768` 已被正确读取并据此建表（`..._768d`），但决定"是否发送"
的 `EMBEDDING_SEND_DIM` 默认为 `false`，于是 API 返回 1024 维，
10 条 embeddings 共 10240 个数除以 768 除不尽，`PGVectorStorage[entities]`
flush 失败，整个 pipeline 批次中止。

启动日志里这行是提前可查的指纹，不必等到报错：

```
INFO: Send embedding dimension: False by env var (dimensions=768, has_param=True, binding=openai)
```

`deploy/lightrag/.env` 补 `EMBEDDING_SEND_DIM=true` 后该行变为 `True by env var`，
文档状态转为 `processed`。**`EMBEDDING_DIM` 与 `EMBEDDING_SEND_DIM` 是两个变量**：
前者是声明，后者是投递；只设前者在本 provider 上必然失败。

## 说明书实体类型：Drug 与 DrugInteraction 的划分

试灌后的类型分布里，`阿司匹林`、`乙酰水杨酸` 被判成 `druginteraction` 而非 `drug`。
这不是模型抽错，而是 profile 的规则本身有歧义：`DrugInteraction` 的释义写作
"相互作用的药物、食物或物质"，而阿司匹林确实出现在相互作用一节里，
模型按**所在章节**而非**实体本身**归类。

`deploy/lightrag/prompts/entity_type/lumos_medicine.yml` 增加一段划分口径
（按实体本身、能作为说明书主体药品的是 Drug；只能作类别泛称的是 DrugInteraction），
并补一条"相互作用一节里提到的具体药品仍是 Drug"的示例。

效果可量化：改前 `drug` 42 / `druginteraction` 68，改后 `drug` 79 /
`druginteraction` 48；抽查 10 个具体药品全部为 `drug`，`保钾利尿剂`/`抗凝剂`/`酒精`
仍为 `druginteraction`，`ACE抑制剂` 为 `drugclass`，均符合预期。

⚠️ prompt profile 在容器**启动时**读取，改文件后必须重建容器才生效，
否则静默沿用旧 prompt。

以上两项均写进 `docs/howto/run-medicine-import.md`。

## 说明书实体质量实测（200 份试灌的中间结论）

对已建图说明书的图做量化检查，结论是**不需要再调 prompt**：

- **实体名污染极低**。5,570 个节点里带数字的只有 3 个，且逐个看下来只有
  `格列齐特80mg` 是真污染；`肌酐清除率低于50ml/min患者`（带数值阈值的用药人群，
  类型为 population）与 `0.9%氯化钠注射液` / `维生素B12`（数字是专有名词的一部分）
  都是正确抽取。即"带数字"不等于"污染"，不能用正则一刀切做验收。
- **实体合并有效**。跨文档共享实体 1,348 个 —— 同一药名/人群/不良反应被多份说明书
  提到时确实合并到了同一节点，图是连通的而非按文档碎裂。
- **碎片化率约 1.1%**。把实体名归一化（去空格/连字符、统一"细胞色素P450"与 CYP 写法）
  后，5,353 个实体里只有 36 组、60 个冗余节点。最严重的是 CYP3A4 有 8 种写法
  （`CYP3A4` / `CYP 3A4` / `CYP-3A4` / `细胞色素P450 3A4` …），其次是 β受体阻滞剂
  有 7 种。这是 GraphRAG 的固有特性（合并依赖 LLM 判断），不是配置缺陷；
  剩余量级不值得为它付出重新建图的成本。

大度数节点也符合预期：`伏立康唑`(257)、`孕妇`(160)、`依非韦伦`(154)、
`氢氯噻嗪`(139)、`地高辛`(131) —— 高相互作用/特殊人群药物与人群实体度数最高。

## 修英文侧向量灌入链路（`scripts/shared/chunking.ts`）

审计 `rebuild-drugbank-rag-index.ts` 这条链路时发现它早已过时，且**过时得很隐蔽**：
运行时（`LlmRuntimeService` + `VectorStoreFactory`）与导入脚本对同一份配置的理解不同。

**缺陷一：脚本从不发送 `dimensions`。** 运行时
`createEmbeddingModel` 一直有 `...(dimension != null ? { dimensions } : {})`，
而脚本的 `createEmbeddingStore` 只读 `AI_EMBEDDING_API_KEY` / `_BASE_URL` / `_MODEL`
三个变量，**漏了 `AI_EMBEDDING_DIMENSION`**。`text-embedding-v4` 支持 64–2048
动态降维且不传时默认输出 **1024**，于是同一份语料：脚本写入 1024 维、
运行时按 768 维建索引与查询，向量彼此不可达。这与本次 LightRAG 侧踩的
`EMBEDDING_SEND_DIM` 是同一类错误——**「期望维度」与「投递维度」是两件事**。

**缺陷二：失败批次被计入总数。** `embedDocuments` 的 `catch` 里只
`console.error` + `sleep` 就继续循环（重试在语义上是假的），而
`embedded += batch.length` 写在 `try` 内、抛错点之前，最终打印的条数包含
从未写入的批次。与 `db-upsert` 曾经的「报满却丢行」同一形状。

**缺陷三：不建索引。** 运行时特意复核 HNSW 索引是否真的建成（注释写明
静默失败会让检索退化成全表扫描），脚本只 `ensureTableInDatabase()` 不建索引。
且不传维度时列类型是无维度 `vector`，**根本无法承载 HNSW 索引**。

修法：`createEmbeddingStore` 读并透传 `AI_EMBEDDING_DIMENSION`
（非整数直接抛错、未设置时告警），维度一并传给 `ensureTableInDatabase`，
按运行时同款建 HNSW 并复核是否建成；`embedDocuments` 改为单批最多
3 次尝试、仍失败则抛错中止并报出**真实的**已完成前缀数（嵌入按 id upsert，
重跑无害）。附带修掉 `--embed-force`：它在建表之前
`DELETE FROM`，首次运行必然报表不存在——现在建表发生在前。

新增 `scripts/shared/chunking.spec.ts`（9 例）钉住上述行为：
维度透传给 embeddings 客户端与建表、缺变量时告警、非整数抛错、
失败批次重试后成功、持续失败时抛错且前缀计数诚实、
以及「绝不返回包含失败批次的计数」这一条（旧实现会在此返回满值）。

**部署侧前置条件**：`lucent` 库此前**没有** `vector` 扩展
（只有 `pg_trgm` / `plpgsql`；`lightrag` 库倒是 LightRAG 自己建了）。
镜像 `luomuloyal/lucent-db:18-arm64` 自带 `vector.control`，故执行
`CREATE EXTENSION IF NOT EXISTS vector` 即可。这与 2026-10-01 迁移日志
「只需给 `lucent` 与 `lightrag` 两库建 `vector`」的待办一致——本次补上了 `lucent`。

实测：`pnpm test:tools` 91 例通过（新增 9）、`typecheck` / `lint:check` /
`docs:verify` / `docs:links` 全绿。灌入本身尚未执行（成本估算见
`deploy-secrets/estimate-en-embedding-cost.py`：约 1,387 万字符 / ~1.5 万 chunk，
按官方 0.5 元每百万 token 计约 **¥1.7**）。

### 实际执行：chunk 数超预估 3 倍（估算方法有误，结论不受影响）

执行后实测 **48,475 chunks**，而估算预测 ~15,416，差 3 倍。原因不是
`chunkText` 有 bug，而是**估算方法忽略了分段**：`chunkText` 先按空行分段，
每段各自成 chunk，然后才对超长段做滑动窗口。DrugBank 叙事字段里短段极多，
实测 23,142 个 chunk（48%）不超过 200 字符，平均仅 288 字符。所以
"总字符 ÷ (maxLen − overlap)" 这种算法只对**没有分段边界**的文本成立。

**但费用估算仍然有效**，因为它是按**字符总量**算的：预测 13,873,631 字符、
实际 13,953,934 字符，偏差 **0.6%**。chunk 数影响的是请求数（批次），不是
token 量。教训：估 embedding 成本要看字符/token 总量，不要用 chunk 数反推。

### 嵌入批大小默认值 20 是错的（provider 硬上限 10）

首跑 `--embed-batch-size 20` 时每一个批次都失败：

```
400 InternalError.Algo.InvalidParameter: Value error, batch size is invalid,
it should not be larger than 10.: input.contents
```

百炼 `text-embedding-v4` 单请求最多 10 条输入，而 `parseRebuildArgs` 的默认值
写的是 20——**默认配置必然首跑失败**。改为 10 并在常量上注明这是 provider 上限
而非调优参数（换 provider 后可上调，但要先确认对方上限）。

顺带一提，这次失败**正好验证了上一节的修复有效**：旧实现在这种情况下会
`console.error` 一句就跳过全部批次、最后报 `embedded=0` 而退出码仍为 0；
新实现重试 3 次后抛出
`Embedding failed for batch 0-20 after 3 attempts; 0/48475 chunks were embedded`，
错误里带**真实的前缀计数**，退出码非 0。

`chunking.spec.ts` 补 2 例钉住默认批大小为 10（共 11 例）。
