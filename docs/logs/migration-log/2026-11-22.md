什么」在那一刻才是定稿。

用户记忆；把一批无法归属的推断行倒进 Mem0，正是 WeKnora 那条要避免的「静默断言错误
猜测」。需要历史时从备份恢复，而不是让一张无主的表长期留在迁移域外。

## feat(assistant): deepagents 挂独立 checkpointer 并支持提案 interrupt

### 变更范围

- 新增 `adapters/agent/proposal-review.ts`：`afterAgent` 中间件，在工具全部执行完
  后 `interrupt`，把 `pendingReview` / `proposals` 写进 middleware state。
- `deep-agent.ts`：接受 `checkpointer` 与 `middleware`；新增
  `deepAgentThreadId()`（`deep-{conversationId}`）。
- `deep-agent-runner.ts`：透传 checkpointer、按 thread id 调用 `invoke`、读
  `pendingReview` 决定 `stopReason`（挂起即 `awaiting_review`）。
- `runtime.ts`：
  - `shouldUseDeepAgents` 改为读有效底座（用户模式优先），含 `*_draft` 的轮次
    只在 checkpointer 可用时走 deepagents（`deepAgentsSupportsProposals`）。
  - `resumeConversation` / `readPendingProposals` 支持两种挂起格式：先 graph 线程，
    再 deepagents 线程。

### 说明

**为什么不是 `interruptOn`。** deepagents 的 HITL 在工具**执行前**拦截，而提案是
draft 工具的**输出**（id、payload、`expiresAt` 都由工具产生）。执行前挂起等于拿不到
proposal id，confirm 端点没有可写的对象——正是「把提案描述成已执行的写入」那个失败。

**为什么不是 `wrapToolCall`。** 第一版实现用 `wrapToolCall`，类型检查暴露了根本问题：
该 hook 的返回值只能是 `ToolMessage` / `Command`，而把状态合进去需要返回一个形似
`ToolMessage` 的扩展对象。更要紧的是 LangGraph 恢复时会重跑被中断的节点，工具会**执行
两遍**。draft 工具当前无副作用，重复执行只是浪费；一旦工具写了审计行就变成正确性
缺陷。`afterAgent` 每次调用只跑一次，位置正对应 graph 的 `write_review`。

**两套 thread 命名空间是必须的，不是偏好。** 两个底座都写同一个
`AssistantCheckpointerService` schema；共用 thread_id 会让 `getState` 只回答「最后
写入的是谁」，而 `regenerateLastMessage` 依赖 graph 的 checkpoint id。

**resume 按「哪个线程真的挂着」分派**，不按当前开关：底座可以在挂起与确认之间被切换。

**两处类型断言并注明理由**：`ReactAgent.getState` 在发布类型里标 `@internal` 且返回
`never`；`invoke` 的入参联合类型不接受 `Command`，尽管 `Command({ resume })` 是官方
文档的恢复方式。两处都收在单个方法内，不扩散到调用方。

### 验证

- `typecheck` exit 0；`lint:check` 0 error（4 个既有 warning）。
- 全量单测 4567 passed / 1 failed——唯一失败是 `deep-agent-runner.spec.ts` 的
  tool-call 收集用例（`GraphRecursionError`，`docs/TODO.md` 已登记）。
- 未验证：真实模型下的子智能体委派与 deepagents 提案挂起（需模型凭据）。
