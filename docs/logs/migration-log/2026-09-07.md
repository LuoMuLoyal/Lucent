## fix(auth): resetPassword 密码变更通知改 fire-and-forget，补控制器异常分支测

按 `plans/Lucent-review-09-06.md`（实施完毕文件已删）#3 / #4 落实:

- `credential.service.ts`：`changePassword` / `setPassword` / `resetPassword` 三处的
  `_notifyPasswordChanged(userId)` 不再经 `lift()` 串进 ResultAsync 链，改为
  `void this._notifyPasswordChanged(userId)` fire-and-forget——通知失败只记 error
  日志、不影响成功路径（密码已写入 DB 且 JWT 已撤销后，通知失败不再让整个
  reset 变成 5xx，避免"用户被强制登出却收不到提示通知"的不一致被放大为主路径失败）。
- `local.controller.spec.ts`：`resetPassword` 新增两个断言——非 DomainFailure
  基础设施异常（如 DB 断开）经 `unwrapResult` 逃逸到全局 filter 转 5xx 且不丢失
  原始异常；验证码失效折叠为 `DomainFailureException`（`AUTH_VERIFICATION_CODE_EXPIRED`）。

注：#3 推荐的「把 verify 移到最后」与「先 cacheDel 主动消费」未采纳——当前
`verify` 成功后即删除缓存中的验证码（一次性消费），不存在"verify 未消费导致 token
仍有效"的 TOCTOU；把 account 查询提前到 verify 之前反而会破坏防枚举（OAuth-only
账号无需有效验证码即可被探测出 `AUTH_PASSWORD_NOT_SET`）。

验证：`pnpm typecheck` 通过；credential / local.controller / auth.service spec
全绿（53 + 13 + 27）。

## fix(auth): verification-code 构造期 TTL/限流参数 fail-fast 校验

按 `plans/Lucent-review-09-06.md`（实施完毕文件已删）#12 落实:

- `verification-code.service.ts` 构造函数从 yaml 读取
  `codeTtlMs` / `cooldownMs` / `rateLimitMax` 后做 sanity check：
  - `codeTtlMs <= 0` 抛错（否则验证码无限期有效）
  - `cooldownMs <= 0` 抛错（否则冷却永远失效）
  - `cooldownMs > codeTtlMs` 抛错（否则冷却超过验证码有效期，语义矛盾）
  - `rateLimitMax <= 0` 抛错（否则限流形同虚设）
  构造函数异常属 DI 初始化期，豁免 `error-handling/no-bare-throw-error`
  （Nest 启动即失败，fail-fast 而非带病运行）。
- `verification-code.service.spec.ts` 新增 4 个构造器校验用例（zero codeTtl /
  负 cooldown / cooldown 超 codeTtl / zero rateLimitMax）。

验证：`pnpm typecheck` 通过；verification-code.service.spec 21 tests 全绿。

## fix(auth): OAuth config 哨兵值 not-configured 统一归一化为空字符串

按 `plans/Lucent-review-09-06.md`（实施完毕文件已删）#13 落实:

`.env.development` / `.env.production` 中微信（web + mobile）与微博的
`APP_ID` / `APP_SECRET` 已填 `not-configured` 占位以消除启动告警
（前端已隐藏入口，见 09-06 migration log），但该字符串本身是非空值，若未来
有人误填入真实 env 或占位未清理，OAuth provider 的 `!config.appId` 判断会放行
并拿这个假值去请求第三方 API（静默失败或账户被锁）。

- `oauth.config.ts`：新增 `resolveCredential()` 私有函数——将 `not-configured`
  （case-insensitive，含前后空格）统一归一化为空字符串；所有 provider 的
  `appId` / `appSecret` 经此函数处理。`redirectUri` 维持原样（它是 URL，不会
  与 sentinel 混淆；且未配置时 provider 已有 `!config.redirectUri` 守卫）。
- `oauth.config.spec.ts`：新增 2 个用例——sentinel 原值归一为空（WeChat web
  + Weibo）、大小写 + 空格归一（WeChat mobile）。`keysToClean` 补充
  `WEIBO_*` 与 `WEIBO_REDIRECT_URI` 键以防止测试间污染。

验证：`pnpm typecheck`、`pnpm lint:check`（0/0）通过；`oauth.config.spec` 8
tests + 6 个 provider spec（61 tests）全绿。
