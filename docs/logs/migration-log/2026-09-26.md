## 中文说明书图谱建图成本分诊（新增只读脚本，无行为变更）

背景：此前要判断"LightRAG 建图慢是否该换 GraphRAG 框架"，依据一直是外部基准

- **分诊口径**：LLM 侧字段沿用 `rebuild-leaflet-index.ts` 的 10 个 `CHUNKABLE_FIELDS`，

  `ingredients` 走启发式拆分）按零 LLM 计。
- **一处自我订正（重要）**：初版按**整篇文档**做 md5 去重，得出"仅 0.6% 冗余"，
  这个口径是错的——10 个字段拼接后几乎每篇都唯一。抽取计费发生在**chunk**，
  改为按 chunk 去重后：`205,454 → 61,207` chunk（**-70.2%**），
  字符 `17,350,509 → 8,997,442`（**-48.1%**）。字段级唯一率差异极大，

- **实测结论**：确定性（零 LLM）侧可得 12,097 Drug / 4,388 Manufacturer 节点，

  在本项目实盘镜像上**已是正确值**（`lightrag.py:791` 默认 `True`；
  `.env` 已设 16），无需改动。
- **顺带核实**：本容器 `lightrag/kg/` **无 `age_impl.py`**，故 AGE 那张 DrugBank

## LightRAG 抽取缓存的键级验证（结论：chunk 内容级，可安全复用）

上一节的"70.2% chunk 重复"能否转化成省调用，取决于缓存键的粒度。若键含
`file_path`，则同一段文本在不同说明书下会被重复抽取，去重收益为零。**已实盘验证为
chunk 内容级，与文档归属无关**：

- `utils.py:5244` 抽取调用链的键输入是
  `compute_args_hash(_prompt, "<response_format>", response_format_key, "<llm_identity>", llm_identity_key)`，
  其中 `_prompt = user_prompt + system_prompt + history`；`_prompt` **不含 `file_path`**。
- `_prompt` 的 `user_prompt` 就是 chunk 正文：`operate.py:4152/4168` 以
  `"input_text": content` 渲染抽取模板（`content` 即该 chunk 文本）。
- 键为 `generate_cache_key("default", "extract", arg_hash)`（`utils.py:962`），
  即 `default:extract:<md5>`。
- **实盘验证**（容器内跑 `compute_args_hash` + `generate_cache_key`）：
  同一段 chunk 两次得 `default:extract:07d715e8…`（一致），换一段文本得
  `default:extract:b78c304c…`（不同）→ **同内容必然同键**。
- 命中路径确实读缓存并计数：`utils.py:5254` `handle_cache(...)` 命中即
  `statistic_data["llm_cache"] += 1` 并直接 return，未命中才 `llm_call += 1`；
  写回受 `enable_llm_cache_for_entity_extract` 门控（实盘为 `True`）。
- 现存 `lightrag_llm_cache` 中 `extract` 1,341 条，而 `left(original_prompt,400)`
  只有 **2 种前缀** —— 系统提示是共享的，**唯一性由 chunk 正文贡献**，与上述源码一致。

**结论**：同一 chunk 文本在任何说明书下都命中同一缓存条目。因此"命中缓存则复用抽取
结果、但仍按 leaflet 归属完整写入"的方案成立——**省下 70.2% LLM 调用，同时保留
每次提及（实体 description 正常累积）与全部溯源 chunk**。
按 chunk 跳过写入的做法会造成约 **69,264 条跨药品断言**丢失（`validity_period`
一句"24个月"横跨 7,368 种药品即 15,519 条），已判定不可取；
`validity_period` / `storage` 这类纯模板字段建议直接不建图。

## 抽取阶段与嵌入阶段分离（回答"确定性灌入是否也嵌入向量"）

**是，向量绕不开，但可以只对"值得检索的实体"嵌。** 已读源码确认两个阶段是分开的：

- **`extract_entities()` 全程不产生任何向量**（grep `vdb`/`embed`/`upsert` 无实质命中），
  它只做 LLM 抽取 + 写 `llm_response_cache`。所以**跳过 LLM 抽取与省略嵌入是两件事**，
  前者可省 70.2% 的调用费，后者不能一起省掉。
- **向量在图写入路径里**：`merge_nodes_and_edges()` 的签名同时收
  `entity_vdb` 与 `relationships_vdb`，并在 `_merge_nodes_then_upsert` /
  `_merge_edges_then_upsert` 中 `*_vdb.upsert(...)`。
  即：**只要把实体/关系写进图，就会被嵌入**，与它来自 LLM 还是确定性映射无关。
- chunk 级向量另有其路（`chunks_vdb`，`_merge_all_chunks`），对应实盘
  `lightrag_vdb_chunks_*` 表。

**对本项目的含义**：确定性灌入（`related_diseases` / `approval_codes` 等）能省掉
**全部 LLM 调用**，但仍会为两侧节点付嵌入费。按实盘统计，确定性侧实体规模为
`Drug` 12,097 / `Manufacturer` 4,388 / `Disease` 12,397 / `ApprovalCode` 88,548 /
`DrugCategory` 4 / `RegulatoryClass` 7 —— 其中 **`ApprovalCode` 88,548 个
（批准文号）不具检索价值**，且已有一一对应的关系型表可查，**不建议嵌入**；
`Drug` / `Disease` 才是需要语义检索的部分。

## 扩展：`storage` 纳入 p3c 归一化

`storage` 与 `validity_period` 的模式**不同**：它是自然语言而非封闭集合，
20,653 行里有 **1,496 种写法**，但绝大多数是**同一批语义槽位的排列组合**：

```
遮光，密封，在阴凉干燥处保存  |  密封、遮光，置阴凉干燥处  |  密封，置阴凉处。
```

做法是解析成槽位（避光 / 密封 / 冷藏 / 阴凉 / 凉暗 / 干燥 / 常温 / 温度上限）
再按**固定顺序**输出规范形，从而同时吸收词序差异与标点差异。实测 **99.1%**
（20,466 / 20,653）至少命中一个槽位。

**1,496 → 250 个唯一值**，改写 19,680 行，148 行原样保留。

三条刻意的保守边界：

- **含否定/告警语义的行整行保留**（`25℃以下，不得冻结` / `不能冰冻` / `避免潮湿`）——
  折叠成规范形会把「不得冷冻」误说成「冷藏」，语义反转。
- **无槽位或部分可解析的行原样保留**，不做拼装 —— 半解析出的规范形比原文更不可信。
- 仅温度条件（`30°C以下保存`）也算有效槽位，但必须有可识别槽位才输出。

过程中单测抓到一个真实 bug：`常温` 槽位最初写成 `凉处`，而 `阴凉处` 内含
`凉处`，导致 `密封，置阴凉处。` 被误归为「密封，阴凉，常温」。已用负向后顾修正。
