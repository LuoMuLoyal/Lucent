## fix(queue): worker 停机强制关闭,修复 reports afterAll 卡死

reports afterAll 卡死的**根因**不是 hookTimeout 太小,而是 `app.close()` 等待
BullMQ worker 优雅关闭时,一个卡在 exponential backoff 重试循环的 job 会无限
阻塞优雅停机(实测 CI 中卡 120s+)。测试触发的 suggestion-recompute job 因
`cleanupDatabase` 已删除用户而外键失败,反复重试(attempts 3 × backoff
5s/10s/20s),`worker.close()` 默认等当前 job 完成,导致关闭挂起。

修复:`BullmqQueueFactory.onModuleDestroy` 改为 `worker.close(true)` 强制关闭,
不等待当前 job 完成——停机语义应为尽快释放连接,挂起重试的 job 交给 job 自身的
attempts/backoff 兜底(应用重启后重新入队由可靠队列保证)。`hookTimeout`
从 120s 回调到 90s 仅作兜底。

验证:`pnpm test:e2e` 全量 30 个文件 / 491 tests 本地通过;queue 单测 55 tests
通过。

## fix(ci): staging 首发布 `pnpm install` 失败——prisma 配置读错环境文件

服务器首次 `pnpm i --frozen-lockfile` 在 postinstall 阶段失败:

```text
postinstall$ pnpm prisma:generate
◇ injected env (0) from .env.development
Failed to load config file "/opt/lucent" as a TypeScript/JavaScript module.
Error: Error: DATABASE_URL environment variable is required but not set.
```

**根因**:`prisma.config.ts` 经 `getDotenvLoadOrder()` 按 `NODE_ENV` 选择环境文件,未设
`NODE_ENV` 时回落到 `.env.development` / `.env.development.local`;服务器是全新 clone,只有
`.env.production`,于是 `DATABASE_URL` 为空,配置层在校验处直接抛出,Prisma 把该异常包成
「Failed to load config file … as a TypeScript/JavaScript module」,表象像配置加载器损坏。
`lucent-ci` 一直没暴露这个问题,因为它的 job 级 env 显式提供了占位 `DATABASE_URL`。

**修复**:发布命令串在安装前从 `.env.production` 取出 `DATABASE_URL` 导出到环境(并加
`grep -q '^DATABASE_URL='` 前置校验,把报错变成可读提示),Prisma 相关步骤显式带
`NODE_ENV=production`。`docs/howto/deploy.md` 的手动命令原文与
`docs/reference/deployment.md` 的发布链路同步更新,并写明漏掉 `NODE_ENV=production` 或安装前
`DATABASE_URL` 就会重现该报错。

验证:本机以不存在的 `NODE_ENV=staging` 复现出同一报错文案(确认根因);
`NODE_ENV=production pnpm prisma:generate` 通过(`Loaded Prisma config from prisma.config.ts`

- `Generated Prisma Client (7.9.1)`);workflow YAML 解析与远端 heredoc `bash -n` 通过。

## fix(compose): VictoriaMetrics 未知 flag 与 redis 健康检查

staging 首次 `docker compose up -d` 后两处异常:

1. `lucent-staging-victoriametrics-1` 反复重启,日志
   `flag provided but not defined: -reproducePrometheusSchema`。该 flag 在
   `victoriametrics/victoria-metrics:v1.128.0` 里**并不存在**(用官方镜像跑 `-help` 确认:
   无任何 `reproduce*` 入口),两处编排(生产 `compose.yaml` 与 staging)都带着它,
   Go 的 flag 解析遇到未定义参数直接退出——删掉即可,Prometheus 指标名/标签本来就是
   VictoriaMetrics 的默认行为,不需要该开关。
2. `lucent-staging-redis-1` 状态 `(unhealthy)`,但 redis 自身日志显示
   `Ready to accept connections tcp`。原因是健康检查
   `redis-cli -a "$${REDIS_PASSWORD}" ping` 依赖**容器内**的 `REDIS_PASSWORD`,
   而 staging 编排重写时把原有的 `environment: REDIS_PASSWORD` 删掉了(生产编排本来
   就没有这个变量——它的 app 有 `depends_on: service_healthy`,即 redis 永远不健康、
   app 永远等不到启动)。两处编排都补回 `environment: REDIS_PASSWORD`。

`docs/howto/deploy.md` 前置条件顺带补上 `sysctl vm.overcommit_memory=1`(消除 redis 的
low-memory 告警),`.env.production.example` 与文档的密码一致性提示不变。

验证:`docker compose config`(staging 与 production)通过;`REDIS_PASSWORD` 在渲染结果中
正确落入 redis 服务环境;全仓不再存在 `reproducePrometheusSchema`。
