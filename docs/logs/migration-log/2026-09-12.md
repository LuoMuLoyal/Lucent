## fix(deps): 依赖安全审计整改——升级至最新稳定版并消除高危漏洞链

背景:对 Lucent 全量依赖做安全与合规审计(见 2026-09-12 审计结论),发现 cos
SDK 引入的 `request`(SSRF critical 链)、多个弃用包(`@langchain/community`、
`prom-client`、`cache-manager-ioredis-yet`)及部分直接依赖的旧版本。本轮按
「升级到最新稳定版,破坏性变更跟进适配」执行。

### 依赖变更(均在 package.json / pnpm-lock.yaml)

- `@fastify/static` `^9.0.0` → `^10.1.3`(安装 10.1.3)。v10 破坏性变更:
  `setHeaders` 回调签名由 Response 改为 FastifyReply;Lucent 源码不直接使用
  `@fastify/static`(经 `@nestjs/platform-fastify` 消费),无适配需求。
  升级后反而满足 `@nestjs/platform-fastify@12.0.1` 的 peer 要求(`^10.1.2`)。
- `nodemailer` `^8.0.9` → `^10.0.8`。v10 要求 Node ≥20(项目 engines ≥24.15
  满足)并迁移至 TS 构建;代码仅用 `createTransport` / `sendMail`,API 兼容。
- `cos-nodejs-sdk-v5` `^2.15.4` → `^3.0.0`。v3 不再依赖
  `request` / `form-data` / `fast-xml-parser`(改用自研 `cos-request` /
  `cos-fast-xml-parser`),**消除 request SSRF critical 链**。`getObjectUrl` /
  `putObject` 签名与 v2 兼容(单元测试验证)。
- 移除弃用包 `@langchain/community`(官方弃用,langchain-ai/langchainjs-community
  #61)、`prom-client`(官方继任 `@prometheus-io/client`,原维护者迁移)、
  `cache-manager-ioredis-yet`(未维护)。
- 新增 `@langchain/pgvector@0.1.0`(仅 peer `@langchain/core@^1.0.0`,满足)。
- 新增 `@prometheus-io/client@0.16.1`。
- 新增 `@keyv/redis@5.1.6`(NestJS cache-manager 官方文档推荐 `createKeyv`,
  底层 node-redis v4;与项目 ioredis 客户端互不冲突)。

### 代码适配

  `@langchain/community/vectorstores/pgvector` → `@langchain/pgvector`。

- `src/common/storage/tencent-cos.runtime.ts`:未改(v3 签名兼容,测试验证)。

## docs: 迁移日志按月归档至 docs/archive/<YYYY-MM>,并修正 append-only 守卫的改名误报

### 归档

- `docs/logs/migration-log/2026-07-*.md`(31 篇)与 `2026-08-*.md`(28 篇)经 `git mv` 归入
  `docs/archive/2026-07/`、`docs/archive/2026-08/`;原 `docs/archive/03-archive/migration-log/`
  的 2026-05(4 篇)、2026-06(9 篇)一并整理到 `docs/archive/2026-05/`、`docs/archive/2026-06/`,
  空目录移除。文件名不变,9 月日志仍留在活跃账本目录。
- 日志内容零改动;归档面本就不参与链接完整性与新鲜度校验。
- `docs/README.md` 归档章节补齐按月归档约定,`AGENTS.md` migration-log 规则补一行归档路径。

### 守卫修正

- `scripts/docs/verify.ts` 的 `collectLogOverwriteProblems` 原以
  `git diff HEAD --numstat -- <日志目录>` 取 diff:pathspec 会破坏 git 的改名检测,
  使一次纯 `git mv` 归档退化成"整文件删除",被误报为 append-only 违规(本次 60 篇全部命中)。
  改为全树 `git diff HEAD --numstat -M`,先把改名条目解析为目标路径再判定 ——
  纯移动(0 删除行)不报;就地改写、直接删除、移动同时删行仍照旧报违规,严格性不降。

- `pnpm docs:verify`、`pnpm docs:links` 通过。

## fix(scripts,cache): 补齐依赖替换遗留——import 脚本 pgvector/keyv 适配,修回 medicines 缓存失效

承接本轮依赖审计整改:`@langchain/community` → `@langchain/pgvector`、
`cache-manager-ioredis-yet` → `@keyv/redis` 的替换当时只落在 `src/`,两处遗漏由
`pnpm typecheck:tools` 与运行期复核暴露。

### typecheck:tools 报错修复

- `scripts/shared/chunking.ts`:动态导入改 `@langchain/pgvector`。新包的 `PGVectorStoreArgs`
  仍接受外置 `pool`,`ensureTableInDatabase()` 与 `distanceStrategy` 用法不变。
- `scripts/import/medicine/import-medicine-knowledge.ts`:缓存失效改走 `@keyv/redis` 的

  二者已随替换消失。

  `docs/TODO.md` 中「上游类型补 `.del` 后回退」的台账条目(前提已不存在)。

`MedicinesCacheAdminService.listMedicineKeys()` 只经 `KeyvAdapter._cache` 取键;
`@keyv/redis` 的 `createKeyv()` 返回 Keyv 实例(NestJS 的 `isKeyvInstance` 直接透传,
不再包 `KeyvAdapter`),其 `.store` 是 `KeyvRedis`、没有 `_cache` —— 每轮都 warn 后跳过,
`invalidateAll()` 恒返回 0。

- 新增 `collectStoreKeys()`:`_cache`(旧 KeyvAdapter 形态,保留命名空间剥离)与
  `store.client`(`@keyv/redis`,按 `medicines:*` 扫描,键无命名空间)两条路径。
- 用真实 Redis 实测(cache-manager + `createKeyv` 装配):导入脚本侧失效命中 1 条且
  白名单外的键保留;管理服务侧装配为 `Keyv`→`KeyvRedis`、`_cache` 不存在、
  扫描命中并按裸键删除成功。
