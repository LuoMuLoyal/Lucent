# 2026-10-05

## fix(ci): 拆分 app 与 DB 发布 workflow，并修复 merge job 拉错 artifact

### 起因：release 首次运行失败（run 37295603463）

validate 通过、4 个构建 leg（`lucent`×2 + `lucent-db`×2）全部成功，
`Merge manifests` 挂在 `Download digests`：

```
Found 8 artifact(s)
- digests-lucent-arm64 (Size: 244)
- digests-lucent-db-arm64 (Size: 244)
- LuoMuLoyal~Lucent~VEW6UM.dockerbuild  (Size: 110425)   ← buildx 缓存
- LuoMuLoyal~Lucent~N3LMRA.dockerbuild  (Size: 258813)   ← buildx 缓存
...
##[error]Unable to download artifact(s): ... failed after 5 retries.
```

`download-artifact@v4` **没给 `name`**，于是把本次 run 的**全部 8 个 artifact**
都拉了 —— 4 个是真正要的 digest（各 244 B），另 4 个是
`docker/build-push-action` 自动上传的 buildx 缓存（每个 100–260 KB）。
其中一个缓存下载重试 5 次后失败，10 分钟超时的 merge job 因此挂掉。

原注释写的是「不用 `pattern` 过滤……过滤既不可靠也没必要」——防止前缀误匹配
（`digests-lucent-` 是 `digests-lucent-db-` 的前缀）这一步判断是对的，
但结论推错了：正解是**按 `name` 逐个精确下载**，而不是整个都不过滤。

**修法**：每个架构一个 `download-artifact` 步骤，写死
`name: digests-lucent-<arch>`，并把 `path` 直接给到
`/tmp/digests/lucent-<arch>`（精确 `name` 时 download-artifact 不再建
artifact 名那层子目录，路径必须跟着改，否则下面的 shell 找不到文件）。

### 拆分：`release.yml`（app）与 `release-db.yml`（DB）

`lucent-db` 的构建输入只有 `docker/postgres/**`，`git log` 实测 40 个提交里
只动过一次（2026-10-01），而 app 几乎每次发布都要发。合在一起的代价是
**每次 app 发布都白等两个 DB 构建 leg**（arm64 runner 更慢）。

拆开后两者 **tag 语义不同**：

| 镜像        | tag                                                          |
| ----------- | ------------------------------------------------------------ |
| `lucent`    | `sha-<sha8>`（不可变回滚锚点）+ `latest`，跟 app 提交走      |
| `lucent-db` | `pg<major>-<YYYYMMDD>-<sha8>`（不可变）+ `pg<major>`（浮动） |

⚠️ DB 镜像**不能**也标 `sha-<sha8>`：它的内容与 app 提交无关，同一个 tag 名字
在两个 workflow 里会指向不同 digest，回滚时极易搞混。`pg<major>` 用内容无关的
主版本前缀，比裸 `sha-` 更能表达「这是数据库镜像」。

两个 workflow 共用同一个 `REGISTRY_IMAGE` secret（DB 仓库名由它派生），
**未新增 secret**。

### 踩到的坑：buildx 不继承 dockerd 的代理

在生产机直接跑 `docker buildx imagetools inspect` 会
`dial tcp 159.138.20.20:443: i/o timeout`，但同一台机器 `docker pull alpine` 正常。
原因是 **`docker buildx` 是 CLI 插件进程，不继承 dockerd 的
`HTTP_PROXY`/`HTTPS_PROXY`**（那套配在 `docker.service.d/http-proxy.conf` 里，
供 dockerd 自己拉镜像用）；buildx 自己发 HTTPS 请求，于是直连超时。

修法是给 buildx 显式带上代理：

```bash
HTTPS_PROXY=http://172.17.0.1:7890 HTTP_PROXY=http://172.17.0.1:7890 \
  docker buildx imagetools inspect <registry>/<image>:<tag>
```

CI 里没有这个问题（GitHub runner 不需要代理），运维排查时记得即可。
`docker manifest inspect` 还额外需要 experimental 开关，检索用 `buildx imagetools`。
