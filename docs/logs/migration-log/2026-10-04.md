# 迁移日志 2026-10-04

## 模型思考开关提取为环境变量(语义化 `AI_THINKING`)

### 背景:线上思考开关其实一直是「无人控制」

生产主站 6 个 AI role 全部指向阿里云 MaaS(`...maas.aliyuncs.com`)上的
`deepseek-v4.1-flash`,而 `src/llm-runtime/llm-runtime.service.ts` 的两条硬编码
探测**一条都不命中**:

- DeepSeek 分支要求 baseUrl 含 `api.deepseek.com` —— 阿里云域名不含;
- 阿里云分支要求 model 以 `qwen3` 开头 —— 实际是 `deepseek-v4.1-flash`。

于是关不关思考既不取决于配置也不取决于意图,只取决于「域名与模型名的巧合」。
而 LightRAG sidecar 早有 env 化先例(`EXTRACT_OPENAI_LLM_EXTRA_BODY`),主站没跟上。

### 变更

**语义化开关**(`src/config/env/{env-keys.enum.ts,environment.validation.ts}`、
`src/config/services/llm.config.ts`):

```text
AI_THINKING                    # auto | enabled | disabled,默认 auto
AI_ANALYSIS_THINKING           # 按角色覆盖,未设则继承 AI_THINKING
AI_VISION_THINKING
AI_LANGUAGE_THINKING
AI_CHAT_THINKING
AI_CHAT_COMPRESSION_THINKING
```

- 值经 zod `enum` 校验,**写错即启动失败**,不会静默回落 auto 让运维误以为开关已生效。
- `LlmRoleConfig.thinking` 与 `LlmConfig.thinking` 都是可选字段,`undefined` 等同
  `auto` —— 这样既有的手写配置字面量(测试、port)无需同步改,语义也正好是「保持旧行为」。
- 嵌入 role 没有 chat model,故不设 `AI_EMBEDDING_THINKING`。

**请求形态仍按 baseUrl 决定**(`applyProviderQuirks` 拆出 `applyThinkingMode`):

| 场景                                 | 行为                                     |
| ------------------------------------ | ---------------------------------------- |
| `auto` + DeepSeek 域名               | `thinking: { type: 'disabled' }`(旧行为) |
| `auto` + 阿里云域名 + `qwen3*`       | `enable_thinking: false`(旧行为)         |
| `auto` + 其它组合                    | 不发任何字段(旧行为,如线上现状)          |
| 显式 `enabled`/`disabled` + 上述两族 | 按值下发,**即使 auto 本来不会命中**      |
| 显式值 + 无法识别的网关              | 不发字段                                 |

最后一行是有意的:未知网关收到未知推理字段会被严格 OpenAI 兼容服务判成请求校验错误,
「没有效果」比「请求报错」可诊断。第二行则是这次修复的落点 —— 线上那种组合现在可被显式控制。

### 验证

`llm-runtime.service.spec.ts` 断言 `modelKwargs` 实际值(而非仅「model 能构造出来」),
覆盖上表全部分支,含线上组合(`auto` 不发、显式 `disabled` 发 `enable_thinking:false`);
`llm.config.spec.ts` 覆盖全局默认、角色覆盖、非法值回落 auto、大小写不敏感。
`pnpm lint:check` / `pnpm typecheck` / `pnpm vitest run` 全绿。

### 部署前提

`.env.development.example` / `.env.production.example` 已补全部键(默认 `auto`=行为不变)。
**生产要真正关掉思考,需在部署侧显式设 `AI_THINKING=disabled`** —— 这一步是运维决策,
未在本轮代码改动中代设。参考 `docs/reference/environment-variables.md` 的
「Reasoning ("thinking") mode」小节。

## 「模型未配置」与「运行时 LLM 失败」拆成两个稳定码

### 背景

`DEPENDENCY_UNAVAILABLE` 同时承载两件相反的事:配置缺失(重试永远不会好,要运维去配)
与运行时上游失败(限流/5xx/熔断,稍后重试可能就好)。客户端只能笼统显示「服务不可用」,
风险检查 AI 页因此把永久配置缺口显示成可重试故障。

`requireChatModel` 原本抛带散文的 `ServiceUnavailableException`(「Set the corresponding
environment variables…」),而 `ApiExceptionFilter.resolveDetail` 的取值顺序是
`raw.detail → raw.message`,所以**运维指引句原样发给客户端**,还顺带绕过了注册表里已写好的双语 detail。

### 变更

**新增 `LLM_NOT_CONFIGURED`**(`src/common/api/problem-catalog.ts`、`src/common/result/domain-failure.ts`、
`src/i18n/{zh-CN,en}/common.json`):

- 与 `DEPENDENCY_UNAVAILABLE` 同为 503(对外语义仍是「暂时不可用」),区别在稳定 code:
  前者 `retryable: false`(去配置),后者 `retryable: true`(稍后重试)。客户端据此分流。
- 命名用 `LLM` 而非 `AI`:该 code 特指「某个 role 的模型没配」,不是泛指一切 AI 能力。

**`LlmNotConfiguredException`**(`src/common/llm/safety/llm-not-configured.exception.ts`):
不设 `message`,只在 `cause` 里留 role —— 这样出网 detail 回落注册表双语文案,role 仅进日志。
`requireChatModel` 与 `risk-check.service.ts` 的 `doRunLlmCheck` 改抛/改用它。

**风险检查的错误映射**(`risk-check.service.ts` 的 `toDomainFailure`):
这里**刻意不给 `ServiceUnavailableException` 加分支**。生成器用该异常宣告运行时模型失败,
而客户端把这个端点上的**任何 503**都渲染成「AI 分析未配置」
(`risk_check.dart` 的 `_isDependencyUnavailable` 匹配 code **或** `statusCode == 503`)。
若把它映射成 `DEPENDENCY_UNAVAILABLE`(503),可重试的故障就会被呈现为永久配置缺口
——正是本轮要消除的那种混淆。故运行时失败维持 `INTERNAL_ERROR`(500),客户端仍按真实
失败提示;只有 `LlmNotConfiguredException` 才映射为 `LLM_NOT_CONFIGURED`。

### 验证

`api-exception.target.spec.ts` 断言两条码各自的 status/code/retryable,并断言 role 不出现在 detail 里;
`risk-check.service.spec.ts` 覆盖未配置(含 detail 未被散文覆盖)与运行时失败**不落 503**两条路径。
`pnpm lint:check` / `pnpm typecheck` / `pnpm vitest run` 全绿。
OpenAPI 无变化(仅新增错误码,不改 HTTP 契约),`pnpm export:openapi` 产物未变。

### 客户端配套(同轮完成)

`LLM_NOT_CONFIGURED` 与 `DEPENDENCY_UNAVAILABLE` 同为 503,而 Luminous
(`risk_check.dart`)此前把 503 一律当「未配置」(用 `statusCode == 503` 兜底)。已在同轮改为
**只认 `LLM_NOT_CONFIGURED`**,并新增「裸 503 运行时故障保持可重试空态」用例;
见 `Luminous/docs/logs/migration-log/2026-10-04.md`。
两端必须同时上线:只升后端会让运行时 503 被判成缺配置;只升前端会让旧的
`DEPENDENCY_UNAVAILABLE` 未配置应答不再显示「未配置」。

## 助手 simple_chat 提示词改为如实描述 + 记忆类提问补读规则

### 背景

真机反馈:能力面板显示工具全部可用,但问「你在吗」时助手回答「这次运行里我也没有可用的记录类工具」。
两处独立缺口叠加:

1. `prompts/system.prompt.ts` 的 simple_chat 提示词字面写着「No server-approved data tools are
   available in this run」——**把「本轮没选工具」说成了「本产品没有工具」**。模型如实转述,
   于是一次路由未命中就变成产品级的能力否认。
2. `tool-keyword-rules.ts` 的 `get_user_settings` 读规则缺记忆类关键词,「你拥有记忆吗」只命中
   写入侧的 `/记忆/`;而写意图分支仅在读规则零命中时才走,于是同样掉进 `simple_chat`,
   本可回答的能力/设置问题答不出。

### 变更

**提示词**(`agent/prompts/system.prompt.ts`):改为「本轮未选取数据工具,因此本轮读不到记录」,
并显式禁止反推「产品没有该能力」——`Do not state or imply that such tools are unavailable in
this product — the toolset is chosen per message`。spec 同步改为锁定新语义,并新增一条断言
旧措辞不再出现。

**读规则**(`agent/runtime/tool-keyword-rules.ts`):`get_user_settings` 补 `/记忆/`、`/记住/`、
`/隐私/`、`/授权/`、`memory`、`remember`、`privacy`。

**关于写/读互斥**:本轮评估后**维持互斥判定**(`classify.ts` 仅在读规则零命中时才看写意图)。
理由是既有行为已把设置类改写正确路由到 `propose_update_user_settings`(写工具在 `router.ts`
里优先级更高),改成并行判定会改变多类既有路由;故只补关键词,并用回归测试锁住两侧:
记忆类提问 → `read_data`/`get_user_settings`,而「关闭AI记忆」仍 → `write_proposal`。

### 验证

`router.spec.ts` 新增两条(记忆提问走读、记忆开关仍走写);`classify.spec.ts` 新增两条锁
intent 分桶;`system.prompt.spec.ts` 断言新措辞与旧措辞的消失。
`pnpm lint:check` / `pnpm typecheck` / `pnpm vitest run` 全绿。

### 未在本轮解决(仍登记在 Luminous)

能力面板只表达「全局可用」、缺少「本轮实际提供的子集」这一维度,属客户端契约诉求,

## S3 公共基址补 bucket 段(生产上传成功却拿不到可访问 URL)

### 背景

真机反馈头像上传后不显示。客户端侧根因此前已修(`fileName` 被传成 `avatars/{userId}/...`
被 schema 拒收 400);但即使上传成功,产出的公开 URL 仍会 404。

根因:`s3.runtime.ts` 用 `forcePathStyle: true`,对象实际落在 `{endpoint}/{bucket}/{key}`;
而 `buildPublicUrl`(`object-key.utils.ts`)拼的是 `{publicBaseUrl}/{key}`,**缺 bucket 段**。
生产 `STORAGE_S3_PUBLIC_BASE_URL=https://s3.cn-south-1.qiniucs.com`、`STORAGE_S3_BUCKET=lucent`,
于是下发的 URL 指向 `.../files/...` 而非 `.../lucent/files/...`。

### 变更

`S3StorageRuntime.getConfig()` 新增 `resolvePublicBaseUrl()`:在 `publicBaseUrl` 后补 bucket 段。

- **在 runtime 里补,而不是要求改环境变量**:`forcePathStyle` 是 S3 runtime 自己的事实;
  另两个 provider(COS/OSS)是虚拟主机/CDN 风格,base 里**不能**追加 bucket,而
  `publicBaseUrl` 是三者共用的 provider-agnostic 字段。规则与 `forcePathStyle` 放在一起,
  部署侧就无法与之漂移。
- **幂等**:已含 bucket 的 base(即 TODO 里记的那个临时绕法)原样保留,不会拼成
  `.../lucent/lucent`。
- 空 base 仍返回空(`dev`/本地该变量未设,由客户端按设计报错)。

### 验证

`s3.runtime.spec.ts` 新增 4 条:补 bucket、去掉尾斜杠后补、已含 bucket 不重复、空值保持空。
`pnpm typecheck` / `pnpm lint:check` / `pnpm vitest run` 全绿。
真机 HEAD 验证待部署后进行(本轮未部署)。

## DrugBank 搜索名实测:不加 displayName,改由客户端给展开出口

真机反馈搜索结果的标题是一整串系统命名(如 `DB07380` 的
`1,1,1-TRIFLUORO-3-ACETAMIDO-4-PHENYL-BUTAN-2-ONE(…)`),客户端截断到两行后用户读不出是哪个药。
TODO 原方案是「搜索响应补可读展示名(首选泛名/INN,或 synonyms 中第一个非系统命名)」。
本轮先做数据实测再决定是否落字段,**结论是落字段解决不了主要 case,故本轮不加字段**。

### 实测(唯一事实源与口径)

对 `DrugDataBase/derived/drugbank/drugbank_drugs.parquet`(19,842 行 × 59 列 = 源
`full database.xml` 的全字段超集)统计,并对报告条目 `DB07380` 回源 XML 交叉验证(结论一致):

- **DrugBank 的 `name` 本身就是通用名**,系统命名(IUPAC)不在该字段。抽查:`Acetylsalicylic acid`
  (阿司匹林)、`Warfarin`、`Metformin`、`Ibuprofen`、`Naproxen`。
- **78.1% 的行名 ≤ 25 字符**;长名(>50 字符)仅 **12.1%**,且集中在 `groups=experimental` 的
  **未上市研究化合物**——本就没有通用名/品牌名,不是数据缺失。
- 长名那批里**只有 14.7% 存在更短的替代文本**(synonyms 短名或 product/brand 名,如 `BeneFIX`、
  `Quadramet`)。`DB07380` 属于无替代那类:synonyms 里唯一一条就是同一个系统命名,
  products/brands/atc 全空。
- 因此「取 synonyms 中第一个非系统命名」覆盖不到主要 case;给这类条目「生成可读药名」也无依据。

### 处置

- **不加后端字段**。「品牌名 → 短同义词 → 原名」的 `displayName` 只能让上市药更通俗(约 330 行),
  **消灭不掉约 1,900 行只有系统命名的条目**;这点覆盖率差异不足以支撑契约变更。
- 改由客户端做长名呈现:默认两行 + 省略号,**溢出时**提供「展开全名/收起」原地展开。
  见 `Luminous` 2026-10-04 迁移日志。
- 台账该条已删。若将来仍要统一各来源的展示口径,`displayName` 仍是候选,但需连同上述覆盖率
  一起评估期望值(不能在"能变短"的假设下立项)。

### 未做

未跑真实 DrugBank 检索的端到端验证(仅数据层统计 + 单测);搜索排序/匹配仍走 `name`,
本轮无改动。

## Today 建议卡三处服务端缺口:动作 label 读路径、路由、文案语言

真机反馈(英文 App):「健康档案信息不完整」卡的主按钮显示原始 id `complete_profile`,
次级按钮却是英文标签;点主按钮落到 go_router 的 "Page Not Found";同卡标题/原因仍是中文。
三者根因相互独立,本轮一并修。

### ① 动作 label:读路径漏本地化

`persistActive` 存的 `primaryAction` 是**规则里的原始结构**,其 `label` 是内部模板 key
(`complete_profile`),不是展示文案。`toDto` 会本地化,但只在 recompute/内联路径生效;
`getActiveSuggestions`(结果缓存过期后的读路径)直接把持久化行透传下发。
后果是**同一张卡**:结果缓存命中时按钮是「Complete profile」,缓存过期后变成
`complete_profile` —— 取决于缓存是否命中。

- 抽出 `services/action-label.ts`(`resolveActionLabel` / `localizeEvidenceLabel` /
  `localizeEvidenceValue` / `humanizeActionLabel`),由 `toDto` 与
  `getActiveSuggestions` **共用**,两条路径不可能再各自漂移。
- `LifecycleService` 注入 `I18nService`,`getActiveSuggestions` 新增 `locale` 参数并
  本地化 action / secondaryActions / evidence。
- `readCurrent` 不再丢弃 locale:之前参数名是 `_options`(未使用),现在归一化后传给
  `getActiveSuggestions`。客户端发的 `Accept-Language: en` 终于被用到。

### ② 路由指向不存在的 location

`coverage.service.ts` 下发 `/mine/profile/edit`,而客户端路由表只有 `/profile`
(`Routes.profile`,由 settings 的 `ProfileRoute` 声明)。改为 `/profile`;
`escalation.service.ts` 透传的是同一个 `candidate.primaryAction.route`,随规则一并修正。

### ③ 文案语言在重算时被固定为 zh-CN

通知/卡片的 title/reason 在**重算时刻**写入 DB,而 `recompute/worker.service.ts` 硬编码
`locale: 'zh-CN'`,`suggestion.service.ts` 的 `recompute` 再兜一次同值。英文用户因此拿到中文卡片。

- worker 在生成文案前读 `profile.locale`(客户端会把语言上传到这里),经 `resolveLocale` 归一。
- 用户未设语言时(客户端对「跟随系统」上传 `''`)用新增的
  `constants/locale.constants.ts` 的 `SUGGESTION_DEFAULT_LOCALE`(zh-CN),
  与 `recompute` 原有兜底一致 —— **不是** `resolveLocale` 的 `en`。
- locale 查询失败**不阻断**重算,只记 warn 并回落默认。
- `recompute` 的入参保持透传语义不归一:文案生成/持久化本来就按调用方给的值工作
  (`copy-fallback.ts` 甚至以 `en-US` 为键),归一化只发生在需要喂给 `I18nService` 的读路径。
