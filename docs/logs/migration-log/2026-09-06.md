## fix(api): CORS 预检放行 PATCH/PUT/DELETE，修复 Web 端删除记录"删除失败"

Web 端（浏览器跨源）删除日常记录时后端日志只见 `OPTIONS url=*`（预检 204）而
不见实际 `DELETE`，前端始终提示"删除失败"。根因：`@fastify/cors` 的
`Access-Control-Allow-Methods` 默认仅 `GET,HEAD,POST`（CORS-safelisted），
浏览器在预检通过后因缺少 `DELETE` 放行而直接阻断实际请求。

- `src/setup-app.ts` 的 `app.enableCors()` 显式设置
  `methods: 'GET,HEAD,POST,PATCH,PUT,DELETE,OPTIONS'`（后端实际使用的全部
  HTTP 方法）；`origin` 逻辑不变。

验证：`pnpm build` 通过；对
`OPTIONS /api/v1/user/daily-records/:id`（Origin + Access-Control-Request-Method:
DELETE）预检响应 `Access-Control-Allow-Methods` 已含 `DELETE`；真实 `DELETE`
请求可到达后端（无 token 时返回 401，证明不再被 CORS 拦截）。

## fix(assistant): 持久化轮次用户消息显式 createdAt 消除历史会话消息乱序

用户报告：assistant 页面发消息后切换会话再切回，助手回复出现在用户提问之上。

根因：`doPersistTurn` 事务内用户消息通过 `createMany` 写入时未显式赋 `createdAt`，
走数据库默认 `now()`（事务起始时刻）；assistant 消息使用应用侧 `assistantTimestamp`。
`Timestamptz(3)`（毫秒精度）下两者几乎共享同一毫秒，而所有读取都按 `createdAt asc`，
同毫秒时排序不稳定——assistant 回复被排到用户提问之前。

修复：用户消息逐条分配显式 `createdAt`，严格落在 assistant 时间戳之前
（第 i 条 = `assistantTimestamp - (N - i) ms`），保证 user 永远在 assistant 之前。
`conversation.repository.spec.ts` 补充断言：createMany 调用里每条 createdAt < assistantTimestamp。

验证：`pnpm test` 全量单测通过（conversation.repository.spec.ts 及其余 315 文件）。
