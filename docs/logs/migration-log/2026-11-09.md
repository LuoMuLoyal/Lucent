# 2026-11-09

## Langfuse LLM 可观测性接入（Cloud）

Langfuse 作为**与既有 OTLP 链路并行的第二个 trace 出口**接入，用于排查 assistant 的工具
调用死循环、回答质量与 token 成本。原有 Jaeger / VictoriaTraces 链路行为不变。

### 改动

- 新增依赖：`@langfuse/langchain@6.1.1`、`@langfuse/otel@6.1.1`、
  `@opentelemetry/sdk-trace-base`（后者是 `BatchSpanProcessor` 的显式依赖，
  原先只以传递依赖存在）。
- `src/tracing.ts`：新增 `LangfuseSpanProcessor`。**两个出口都改为显式
  `spanProcessors` 条目**——`NodeSDK` 对 `traceExporter` 与 `spanProcessors` 是 if/else
  关系（`build/src/sdk.js`），若只追加 `spanProcessors`，原 `traceExporter` 会被静默
  丢弃、Jaeger 链路断掉。这是本次接入最容易踩的坑。
- 新增 `src/common/llm/tracing/langfuse-callback.ts`：`CallbackHandler` 的懒加载单例、
  启用判断与 trace 标识注入（`langfuse.user.id` / `langfuse.session.id` / `langfuse.tags`）。
- `src/modules/assistant/adapters/agent/runtime.ts`：`runConversation` 与
  `resumeConversation` 两处 `graph.invoke` 挂上 callback；session 取 conversationId，
  user 取 userId。
- `src/common/llm/generators/base-llm-generator.service.ts`：`generate` 的 `model.invoke`
  与 `generateStream` 的 `model.stream` 挂上 callback；基类以 `@Optional()` 注入
  `ConfigService`，子类构造签名不变。
- 环境变量：新增 `LANGFUSE_ENABLED`（默认 `false`）、`LANGFUSE_PUBLIC_KEY`、
  `LANGFUSE_SECRET_KEY`、`LANGFUSE_BASE_URL`；同步
  `.env.development.example` / `.env.production.example` / `.env.test.example` 与
  `docs/reference/environment-variables.md`。

### 设计取舍

- **凭据与开关走 `ConfigService`**：`langfuse-callback.ts` 只接收
  `ConfigService`，不读裸 `process.env`——这些调用点都在 ConfigModule 之后，
  校验层给的默认值才是准的。只有 `src/tracing.ts` 读裸环境变量，因为它必须在
  Nest 存在之前运行。
- **默认关闭**：与 `OTEL_ENABLED` 默认开启相反。没有凭据时开启只会产生注定失败的
  导出；且 Cloud 方案会把会话原文送出境外，必须显式 opt-in。
- **不做内容脱敏**：按需求决定，prompt / tool 入参与结果原样上报。
  会随会话内容带上用户 UUID（`langfuse.user.id`），但不含邮箱或姓名。
- **`CallbackHandler` 只产 span，导出依赖 processor**：两者缺一不可，
  只接 handler 会得到"有 span 但什么都没发出去"的静默失效。

### 验证

`pnpm typecheck`、`pnpm lint:check`、`pnpm test:ci` 全绿。

两处测试断言随之更新：`summary-generator.spec.ts`、`analysis-generator.spec.ts`
的 `expect(invoke).toHaveBeenCalledWith(...)` 由单参改为双参——base generator 现在
总会把 config 作为第二个实参传入（关闭时值为 `undefined`）。
