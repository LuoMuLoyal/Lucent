# 2026-11-08

## refactor(queue): 队列适配层收敛为端口，移除空转的 `@nestjs/event-emitter`

### 为什么

队列适配器此前有三处（`medicine-reminders`、`medicines`、`reports`）直接注入
`BullmqQueueFactory`，而 `today-analysis`、`daily-records`、`data-export` 早已各自
声明了 `application/ports/` 下的队列端口。同一层抽象存在两种写法，意味着换传输
层（微服务化时走向消息总线或独立调度进程）需要逐个改适配器，而不是只换绑定。

`@nestjs/event-emitter` 是历史遗留：`app.module.ts` 里 `EventEmitterModule.forRoot()`
是它在本仓库的**唯一引用**，全项目没有任何 `@OnEvent` 订阅者或 `EventEmitter2`
注入点。ADR-0025 已把跨上下文事件统一到 outbox + 队列投递，进程内同步派发不再
是合法路径，因此这个依赖实际在空转。

### 落地

- 新增三个端口（Symbol 令牌 + 接口，沿用既有 `TODAY_ANALYSIS_QUEUE_PORT` 约定）：
  - `src/modules/reports/application/ports/cache-invalidation-events.ts`
    —— `ReportsCacheInvalidationPort.invalidate(userId)`
  - `src/modules/medicines/application/ports/risk-refresh-queue.ts`
    —— `MedicineRiskRefreshQueuePort.schedule(userId)`
  - `src/modules/medicine-reminders/application/ports/reminder-dispatch-scheduler.ts`
    —— `ReminderDispatchSchedulerPort.registerSchedule()`
- 三个适配器改为 `implements` 对应端口，模块里用 `useExisting` 把令牌绑到实现；
  原有事件消费路径（`invalidateFromEvent` / `refreshForEvent`）保留，内部改为调用
  端口方法，语义不变。
- `ReminderDispatchQueue.onModuleInit` 委托给 `registerSchedule()`，并补了幂等判断：
  重复调用只更新已存在的任务定义，不产生第二条节奏。
- `MedicineRiskRefreshQueueService.enqueueRefresh` 不再透传原始事件载荷——worker
  只需要 `userId`，因此 `schedule()` 从非事件路径调用时也能构造出合法载荷。
- 移除 `@nestjs/event-emitter` 依赖与 `app.module.ts` 中的 `EventEmitterModule.forRoot()`。

### 验证

- `pnpm typecheck`、`pnpm lint:eslint`、`pnpm format:check`、`pnpm build` 通过；
  `pnpm lint:oxlint` 的两条 warning 与本次改动无关（`meal-vision.ts` 控制字符正则、
  `domain-events-outbox.service.ts` 深拷贝）。
- 受影响模块单测：63 个文件 / 823 条用例全部通过。
- `pnpm deps:unused` 无新增未用依赖。
- `pnpm arch:check` 报出的唯一新增观测点
  （`test/e2e/medicines/medicine-relations.e2e-spec.ts` 的 `no-explicit-any`）在本次
  改动前即存在，该文件未被修改，属于既有基线漂移。

## refactor(db): 表结构与命名标准化

实施 `plans/2026-10-30-database-schema-consolidation.md`（实施完毕文件已删）。

### 为什么

骨架构（表名复数 snake_case、`@map` 映射、时间戳类型）已经一致，但**列级命名不统一**：
20 个布尔列中 12 个不带 `is`/`has` 前缀，同一张表里 `isApproved` 与 `emailVerified`
并存，读代码必须先查模型才能判断哪个是布尔列。另外 4 个 schema 文件跨上下文，
`platform.prisma` 一个文件挤了 5 个上下文；导入脚本还自建了一张已由迁移管理的表。

### 落地

- **约定成文**：`docs/reference/database-conventions.md` 纳入版本库，并补「表结构只由
  Prisma 迁移创建」一节。
- **消除脚本自建表**：`import-medical-qa.ts` 的 `CREATE TABLE IF NOT EXISTS` 改为
  「表不存在就报错并提示跑迁移」；删除零引用的 `scripts/sql/create-suggestion-tables.sql`。
- **schema 按上下文重切**（纯文件移动，零迁移）：`platform.prisma` 拆为
  `notifications` / `data-export` / `legal-documents` / `product-events` / `clinic-summary`；
  `user.prisma` 拆为 `identity` / `user-profile` / `audit`；`admin.prisma` 并入 `audit`；
  `medicine-user.prisma` 拆为 `medication-tracking` / `medication-safety`。
  拆分前后 `prisma migrate diff` 输出逐字一致，确认零结构变化。
- **布尔列标准化**（12 列，迁移 `20261108100000`）：全部 `ALTER TABLE ... RENAME COLUMN`。
  Prisma 自动 diff 会把它识别成 DROP + ADD（会清空存量数据），迁移文件为人工手写。
- **表名词根统一**：`medical_qa_chunks` → `medicine_qa_chunks`，与同族
  `medicine_leaflet_chunks` 一致。同步改了导入脚本 5 处、迁移里的索引名。
- **`DomainEvent` 补 `createdAt`**：与 `occurredAt` 语义分开（前者是行写入时间，后者是
  事实发生时间）。回填用 `occurredAt` 而非 `now()`，避免伪造历史时间戳。

### 破坏性契约变更

12 列中有 7 列已在 OpenAPI 契约里（`isEmailVerified`、`isNotificationEligible`、
4 个通知开关、`isStale`）。按计划的方案 A 一并改 API 字段名，`openapi.json` 已重新导出。
**客户端必须同步重新生成并一起发版**：`Luminous` 跑 `cd Luminous && dart run scripts/contract/bootstrap.dart`，
`Lumine` 跑 `cd Luminary/apps/lumine && pnpm contract`。旧客户端读不到这些字段。

### 风险控制

改名前按计划要求区分「数据库列」与「普通英文词」：`stale`（154 处命中）、`generic`
（50 余处）、`approved` 在代码里大量作为通用英文词出现在注释与测试描述中，因此**没有
用全局替换**，而是逐文件确认 `db.<model>.<col>` 访问点后按行修改。Python 解析脚本里
DrugBank 的**源字段键**（`product.get("generic")`）保持原样，只改了输出键。

### 验证

- `pnpm typecheck`、`pnpm typecheck:tools`、`pnpm lint:eslint`、`pnpm build` 通过。
- 单测 403 文件 / 4527 用例全部通过（含 12 文件 / 101 条工具测试）。
- e2e 45 文件 / 673 用例中 672 通过。唯一失败的
  `test/contract/openapi-metadata.e2e-spec.ts` 报 9 个 `medicines/relations/*` 端点缺
  response example——**已通过回退到改动前代码复现，确认是既有问题**，与本次无关。

## refactor(assistant): LangGraph checkpoint 表迁出 public schema

### 为什么

`PostgresSaver.setup()` 会在启动时自建并迁移 `checkpoints` / `checkpoint_blobs` /
`checkpoint_writes` / `checkpoint_migrations` 四张表。它们原本落在 `public`，成为全仓
**唯一一处表结构不由 `prisma/models/**`定义**的地方——Prisma schema 里看不到它们，
迁移评审也覆盖不到，而`database-conventions.md` §3.0 对所有其它表都是禁止的。

给第三方表开一条豁免是错的：豁免留在 `public` 里，等于豁免了整条规则。正确做法是把
它们隔离到独立 schema，让 `public` 维持「只由 Prisma 定义」这个不变式。

### 落地

- `@langchain/langgraph-checkpoint-postgres` 原生支持 `schema` 选项，且 `setup()` 会
  自己 `CREATE SCHEMA IF NOT EXISTS`，因此隔离成本只有一行构造参数，不需要手工 DDL，
  也不产生新的 Prisma 迁移。
- 新增环境变量 `LANGGRAPH_CHECKPOINTER_SCHEMA`（默认 `langgraph`），zod 按 PostgreSQL
  标识符规则校验，避免拼错的 schema 名被静默建出来。
- `AssistantCheckpointerService` 把 schema 传给 `PostgresSaver`，并在就绪日志里带上
  实际 schema，便于确认没有回落到 `public`。
- `database-conventions.md` §3.0 补「第三方库自建表移出 `public`，不开豁免」的判据，
  并说明 LightRAG 这类独立进程走独立 **database** 而非 schema 的原因。
- 三个 `.env.*.example` 与环境变量参考文档同步新变量。

### 影响

切到非 `public` schema 后，`public` 里旧的 `checkpoint_*` 不再被读取，assistant 从空
会话起步（无状态的降级路径本就存在）。不保留兼容、不做数据迁移。

### 验证

- `pnpm typecheck`、`pnpm lint:eslint`、`pnpm format:check` 通过。
- `checkpointer.spec.ts` 新增两条断言：默认 schema 为 `langgraph` 且**不是** `public`；
  配置项生效时使用配置值。6 条用例全部通过。
