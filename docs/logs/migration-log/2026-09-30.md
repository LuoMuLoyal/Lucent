## fix(config): 修复 `pnpm export:openapi` 无法运行，并重导出 stale 契约

- **现象**：`pnpm export:openapi` 静默失败——无任何输出，exit 1。长期被当作
  「Node 24 TS 类型剥离不兼容」的环境问题搁置（先前的迁移日志与提交里就是这么写的），
  **该判断是错的**。

- **真实原因（三层叠加，前两层各掩盖了下一层）**：
  1. **失败被静默吞掉**：`@nestjs/core` 的 `ExceptionsZone.asyncRun` 捕获异常后先调
     `exceptionHandler.handle()`（走 Nest `Logger`）再 `process.exit(1)`。导出脚本用
     `NestFactory.create(..., { logger: false })` 建应用，而校验失败发生在 `create` 期间，
     Logger 尚未就绪 → 报错文本丢掉，只剩 exit 1。**这是"看起来像环境问题"的根源。**
  2. **真正的错误是配置校验**，不是类型剥离：`Config validation error: AI_ANALYSIS_BASE_URL:
Invalid URL`（共 7 项）。`NODE_ENV=development` 会加载 `.env.development`，而该文件把
     整个 AI 段落**以空值列出**（`AI_ANALYSIS_BASE_URL=`）。空串到了 schema 里是「存在」，
     于是 `z.url().optional()` 判定失败——`.optional()` 只豁免 undefined。
  3. 校验组规则正确地拒绝了把 URL 填占位值的做法：`AI_ROLE_GROUPS` 要求一组三个键
     **要么全有要么全无**，只补 URL 会变成「半配置」并触发新的报错（实测复现）。
     故修复方向是**让空值合法**，而非补占位。

- **修复**：把 `.env.*` 中约定为空值的 URI 键由 `optionalUri`（`z.url().optional()`）
  改为既有的 `optionalEmptyUri`（`z.union([z.literal(''), z.url()]).optional()`）——
  该原语本就是为此存在（`VICTORIALOGS_URL` 等已在用）。改 6 个 `AI_*_BASE_URL`
  与 `QQ_REDIRECT_URI`。`TENCENT_COS_PUBLIC_BASE_URL` 用的 `httpUrl` 本已接受空串，
  `GOOGLE_REDIRECT_URI` 不在任何 env 文件中出现，两者不动。
  消费侧本就按空值处理（`llm.config.ts` 的 `readOptionalEnv` 把空串 trim 成 `null`），
  故这是**校验与消费语义对齐**，不是放宽规则；「一组全有或全无」的约束仍在 superRefine 中。
  另给 `setIfMissing` 补注释说明它为何刻意用 falsy 判断。

- **重导出契约**：`docs/reference/generated/openapi.json` 自 2026-09-24 起已 stale——

## build(docker): 修复 Node 26 基础镜像下 corepack 缺失导致的镜像构建失败

### 背景

用 `gh` 核查 CI 发现 `lucent-ci` 在 main 上持续失败，其中 `Docker Build + Trivy` 阶段报：

```
#11 ERROR: process "/bin/sh -c corepack enable" did not complete successfully: exit code: 127
```

`exit 127` 是「命令不存在」。根因是 `ca3e949c`（Dependabot）把基础镜像从
`node:24.20-alpine` 升到 `node:26.9-alpine`：**Node 26 起不再随发行版捆绑 corepack**，
`corepack` 可执行文件因此不在 PATH 中。

判据：Node 官方仓库的 `doc/api/corepack.md` 在 v24、v25 均存在，v26 已移除（实测 HTTP 200 / 200 / 404）。
另注：CI 自身仍用 `node-version: 24.20`，所以这个升级只影响 Docker 构建，不影响 CI 的测试任务。

### 改动

两个使用 pnpm 的构建阶段（`deps`、`builder`）在 `corepack enable` 之前先从 npm 安装 corepack：

```dockerfile
RUN npm install --global corepack@latest && corepack enable
```

corepack 在这里只负责引导 pnpm，而 pnpm 的具体版本仍由 `package.json` 的
`packageManager: pnpm@12.0.0` 决定，与 CI 的 `pnpm/action-setup`（同样读该字段）保持一致，
因此不固定 corepack 版本不会引入 pnpm 版本漂移。`production` 阶段不使用 pnpm，无需改动。

### 验证

- `docker build --check` 成功加载并解析 Dockerfile（本机 registry 拉取受限，镜像层解包报
