# 2026-11-01

## feat(reports): findings 增加稳定规则标识 id

### 为什么

生成式 UI 的 `finding` catalog item 只接受 `findingId`，agent 只能选「展示哪一条」，
文案由后端原文透传。但 `ReportFindingDto` 此前只有 `kind` / `title` / `body`，
没有可引用的稳定标识——客户端只好拿 `kind` 当 id，而 `kind` 是四值枚举
（`medication` / `hydration` / `sleep` / `general`），多条规则共用同一个 kind，
无法唯一标识一条 finding。

### 落地

- `report-dashboard-response.ts`：`reportFindingSchema` 增加 `id`（required，带
  `describe` + `example`，满足 openapi 元数据契约）。
- `dashboard-presenter.ts`：新增 `FINDING_IDS` 常量，三条规则各带 id——
  `hydration_low` / `medication_stable` / `sleep_insufficient`。取值与
  `reports-dashboard.findings.<id>_title/_body` 的 i18n key 后缀同源，但两者是
  独立的东西：id 是跨语言稳定的引用键（进 API 契约），i18n 后缀是实现细节。
- `report-pdf.spec.ts`：测试 fixture 的 findings 补 id。

### 为什么不用 kind 当 id

`kind` 是展示维度（用药/饮水/睡眠/综合），`id` 是规则标识。同属 `hydration`
的有「饮水偏低」等规则，将来还会有别的；拿 kind 当引用键会让 agent 无法指定
具体哪一条，也会让「同 kind 多条 finding 同时出现」时引用歧义。

### 验证

`pnpm typecheck` 通过；单元测试全绿；`pnpm lint:check` 0 error；
`test/contract/openapi-metadata` 通过；`pnpm export:openapi` 后
`ReportDashboardResponseFindings` 含 `id`（带 description 与 example）。

## fix(medicines): 关系图与用药全景端点补响应 schema，契约不再把 body 落成 void

### 为什么

十个端点（`relations/*` 九个 + `medication-overview`）此前只有
`@ApiResponse({ status: 200, description })`，没有响应 schema。Swagger 不内省
`@SerializeOptions`，所以导出物里这些 operation 的 200 根本没有 `content`，
`openapi_retrofit_generator` 于是把生成客户端的返回值落成 `Response<void>`——
前端「接了」也拿不到任何字段，只能绕开生成客户端手写 Dio 取原始 JSON。
本次改动对应可组合 tab 计划（`plans/2026-10-28-composable-tabs.md`，Luminous 仓，计划文件已删
指该仓执行完毕后删除；本次仅为 Lucent 侧前置契约）A5-1 的前置部分。

### 落地

- `dto/relations.ts`：九个明细 schema 原本就有，缺的是信封。新增
  `graphEnvelopeSchema(key, value)` 工厂产出 `{ status, <数据键?> }`，并为九个端点
  各导出一个 `*ResponseSchema`，另导出 `GRAPH_RESPONSE_DATA_KEYS` 供 e2e 复用，
  避免数据键名在测试里再抄一遍而漂移。
- `medicines-relations.controller.ts`：每个端点加 `@SerializeOptions({ schema })`，
  文件末尾按既有惯例补十处 `registerResponseSchema`（provider 端的
  `MedicationOverviewController` 保持不动，登记集中在这一处）。
- `medication-overview.controller.ts` 未改动：它早就有 `@SerializeOptions`，
  只是从未登记，因此同样返回过 `void`。登记放在关系控制器末尾是因为注册表是
  进程级全局的，位置不影响结果。

### 信封为什么不是判别式联合

「`status: 'ok'` 才带数据键」在语义上是一组互斥分支，写成 `z.union` 更精确。
但 OpenAPI 3.0 的 `oneOf` 会让 dart-dio 生成器产出把**两个分支字段全部标成
required** 的包装类 —— 本仓在 medicine `detail` 的 `oneOf` 上已经踩过这个坑
（见 `lib/features/medicine/README.md` 关于 `MedicineDetailResponseDetail` 的记录）。

所以信封改写为「`status` 必填、数据键 `.optional()`」的宽松对象：失败态下控制器
根本不写数据键，线上响应里也确实没有它，生成的模型不会在**最需要安静降级的那条
路径**上解析失败。互斥语义改由 e2e 断言承接。

### 验证

- `pnpm typecheck` 通过；`pnpm lint:check` 0 error。
- `pnpm export:openapi`：Paths 161 / Schemas 417，十个 operation 的 200 均
  `$ref` 到具名组件；`MedicineMechanismPathsResponse` 的 `required` 只有 `status`。
- `test/e2e/medicines/medicine-relations.e2e-spec.ts` 30 项通过，其中新增两组断言：
  响应信封在失败态**只有** `status` 一个键；九个端点各自的 200 引用了正确的组件名，
  且组件把数据键声明为可选。
