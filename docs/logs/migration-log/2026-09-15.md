## refactor(daily-records): 新增餐食分析 v2 契约与规范化

（餐食分析链路重构 P0-1 第 1 步；计划文档在 Luminous 侧，实施完毕后该文件删除。）

### 背景

现有餐食链路是「视觉识别菜品 → 菜品分解 → 成分接地对照食物成分表 → 算热量」，实测在真实照片上行不通：
误差逐段放大成没有意义的数字，且要维护一张覆盖真实饮食的成分表。已核实的硬缺陷还包括：坏 JSON 被降级成
「空结果」却按成功写入、LLM 抛错无 catch 导致记录永久 `analyzing`、幂等只在调用前检查、
`confirmed` 完全由客户端 payload 决定、`defaultRatio` 不参与营养计算。

### 变更

- 新增 `src/modules/daily-records/schemas/meal-analysis.schema.ts`：v2 契约（zod）与服务端规范化。
  - `analysisStatus` 收敛为 `analyzing | analyzed | analysis_failed`（删除 `confirmed` / `unconfirmed`）；
  - `calorieRange` 独立字段 `{min,max,unit,bucket}`，`bucket` 由数值推导、区间取整并 clamp、
    `min<=max` 自动纠正、非法区间落 `null`——**不给伪精确单值**；
  - `items[{rank,kind,polarity,headline,detail}]` 按 `rank` 重排并重编号、丢弃空文案、封顶 5 条，
    `kind`/`polarity` 非法值回落到 `other`/`neutral`；`kind` 为封闭词表（carb/fat/protein/vegetable/fruit/
    fried/sugar/sodium/portion/balance/other）；
  - `dishes[{name,source}]` 只存菜名（去空、按名去重、封顶），`source` 区分模型识别与用户改名，**不存营养成分**；
  - `facets` 收敛词表与档位（`low|ok|high`），是规则/聚合用的机器语义唯一来源；
  - 生成器 `buildAnalyzingMealAnalysis` / `buildFailedMealAnalysis` 与稳定失败原因码
    （`image_count_invalid` / `vision_unavailable` / `model_failed` / `model_timeout` / `invalid_output`）；
  - `mealAnalysisHeadline()` 供列表条目取「最重要的一条」。
- v1 的 `coverage` / `mealInput` / `recognizedDishes` / `resolvedIngredients` / `compositionMatches` /
  `nutritionEstimate` 等成分级结构一概不再存在，不做兼容读取。

### 验证

- `pnpm typecheck` 通过。
- 新增 `src/modules/daily-records/schemas/meal-analysis.schema.spec.ts`（12 例）：schema 接受规范化结果、
  拒绝 v1 版本号与已删状态；`items` 重排/去空/封顶/非法枚举回落/未排序项置后；区间纠正、档位推导与非法区间；
  菜名去重与 `source` 回落；`facets` 过滤未知键；三种生成器形状与 `mealAnalysisHeadline`。
- 后续步骤见下方「餐食分析产出侧切换」条目。

## refactor(daily-records)!: 餐食分析改由一次多模态调用产出

（餐食分析链路重构 P0-1：产出侧切换；计划文档在 Luminous 侧，实施完毕后该文件删除。）

### 背景

承接上一条：v2 契约已就位，但**没有任何消费方**，旧管线（识别 → 分解 → 接地 → 算热量 → 人工确认）
仍在运行。这一刀把产出侧整体换掉：删除成分表链路与人工确认，改为一次多模态分析直出区间与排序结论，
并让失败成为可重试的终态（旧链路会把坏 JSON 降级成「空结果」写入，用户永远停在「分析中」）。

### 变更

- **`vision.service.ts` 重写**：一次多模态调用（`withStructuredOutput` + `functionCalling` + `strict`，
  20s 超时）直出 `{calorieRange, dishes, items, facets}`；输出再过一遍服务端 schema 校验（兼容不支持
  function calling 的端点）。提示词独立到 `prompts/meal-analysis.prompt.ts`（封闭词表、条数与字数上限、
  按用户语言生成、不给单值热量、不下医疗断言）。清洗后若既无结论、又无菜名、又无区间，落 `invalid_output`。
  **失败以原因码返回，不抛异常**——异常会在队列里变成重试与永久 `analyzing`。
- **`worker.service.ts` 重写**：落库用 `updateMany` 把 `mealSourceRevision` 写进 `where`，分析期间用户
  再编辑（revision 已递增）时本次结果自动作废；失败（附件数不对、视觉角色未配置、模型报错/超时/输出不可用）
  一律写 `analysis_failed` + 原因码。文案语言取 `UserProfile.locale`（空则 `zh-CN`），随分析落库 `locale`。
- **过期回收**：新增 `services/meal-analysis/sweeper.service.ts`，由 `CronJobsService` 以
  `*/5 * * * *` 注册到现有低频率 cron 队列，把停留超过 10 分钟仍是 `analyzing` 的记录落成
  `model_timeout`（作业丢失时用户才有「重新分析」可点）。
- **写入契约**：payload 只剩 `mealAnalysis` 一个键。客户端唯一可编辑的是菜名列表
  （`{mealAnalysis:{dishes:[{name}]}}` → 整份标记 `source:'user'`），且**不重算**结论与区间；
  `analysisStatus` / `items` / `calorieRange` / `sourceRevision` 等服务端字段一律忽略客户端提交。
  失败重试复用既有 PATCH：重新提交同一张图（恰好 1 个 attachment）即递增 revision 并重新入队。
- **删除**：`services/meal-dish/*`（decomposition、template-learning）、`services/meal-ingredient/grounding`、
  `services/meal-analysis/matcher`（含各自 spec）；`records.service.ts` 的 `confirmed` 与模板学习分支
  （新建路径顺带去掉冗余的二次 revision 递增）；`common/validators/jsonb-schemas.ts` 的 meal schema；
  `config/app-defaults.constants.ts` 中只服务成分链路的份量/模糊匹配/宏量阈值常量。
- **Prisma**：`MealAnalysisStatus` 词表改为 `analyzing | analyzed | analysis_failed`
  （`prisma/migrations/20260915120000_meal_analysis_status_vocabulary`）。枚举必须与本刀同批：
  产出侧从此只写 `analyzed`，词表不换则类型与数据库都对不上。迁移里把旧的 `unconfirmed` / `confirmed`
  就地映射为 `analyzed`，对已有开发库安全（产品未上线，不做数据迁移承诺）。**coverage 列与索引、
  headline/区间投影列属于下一刀**（契约与投影侧）。
- **下游口径**：`today-analysis` 的餐食投影改为「菜名 + 区间 + 前两条结论」（标题 `饮食分析`，
  失败态仍为 `饮食分析缺失`），触发计数只认 `analyzed`；`reports` 的餐食分解改为
  `analyzedDays | analyzingDays | failedDays` 并同步摘要提示词（区间只能按范围引用）；
  `assistant` 去掉 `meal_coverage:*` 标签与 `mealAnalysisCoverage` 字段、系统提示词改按新词表。
- **未做（后续切片）**：投影热列 `mealHeadline` / `mealCalorieMin|Max|Bucket` 与 coverage 列删除、

  及其导入脚本在本刀后已无消费方，删除与否单独立项（记入 `docs/TODO.md`），避免顺手扩大爆炸半径。

## refactor(daily-records): 视觉失败改走 Result 边界（对齐 ADR-0012）

（餐食分析链路重构 P0-1 的收尾修正。）

### 背景

前一刀把视觉失败表示成自制的 `{ ok: true | false }` 联合类型。它不违 RFC 9457——餐食分析是后台作业，
失败从不经过 HTTP 响应，而是落成记录状态（`analysis_failed` + 原因码），「业务失败不得用 200 表示」
这条不变量也没被触碰——但它违反 ADR-0012 第 3 节：项目对「可预期的、可恢复的领域失败」只有一个
表示法 `ResultAsync<T, DomainFailure>`，且该 ADR 明确把 `{ ok, data }` / `{ ok, error }` 形状列为拒绝项。
全仓生产代码里也只有这一处是这个形状（其余同名形状仅出现在 spec 的解包辅助函数里）。

### 变更

- `vision.service.ts` 的 `analyze()` 改为返回 `ResultAsync<MealAnalysisVisionSuccess, DomainFailure>`：
  模型超时 → `DEPENDENCY_TIMEOUT`(504)；模型报错/不可达 → `DEPENDENCY_UNAVAILABLE`(503)（经
  `mapUnknownToDependencyFailure` 归类并保留 cause）；输出不合契约或被安全过滤清空 →
  `DEPENDENCY_BAD_GATEWAY`(502)。全部复用已登记的稳定码，不新增码，也不需要新的 HTTP 语义。
- `worker.service.ts` 改用 `isErr()` 分支，把失败码翻成落库原因码（`DEPENDENCY_TIMEOUT → model_timeout`、
  `DEPENDENCY_BAD_GATEWAY → invalid_output`、其余 → `model_failed`）：传输词汇与落库词汇各只有一份，
  映射集中在一个纯函数里。删除 `MealAnalysisVisionOutcome` 联合类型。
- spec 相应改断言 `isErr()` / `_unsafeUnwrap()` 与 `code`，并补 `DEPENDENCY_BAD_GATEWAY → invalid_output`
  的落库断言。

### 验证

- `pnpm typecheck`、`pnpm build`、`pnpm lint:eslint`（`--max-warnings=0`）、`pnpm exec oxlint`、
  全量单元测试通过。行为对外不变（落库状态与原因码与前一刀一致）。

## feat(assistant): 餐食分析 digest 工具（避免重复识图）

（餐食分析链路重构第 4 步；计划文档为 Luminous `plans/2026-09-15-meal-analysis-rearchitecture.md`，已实施完毕、计划文件已删。）

### 背景

P0-1/P0-2 之后餐食分析已是「一次多模态直出区间 + 排序结论」并落成投影列，但助手侧只能按天读日报记录：
回答「我最近吃得怎么样」要逐天拉记录、自己解析 payload，而列表读的 meal `payload` 恒为 null。
这一刀给助手一个结构化的窗口读，从此不再重复识图、也不从标题备注猜语义。

### 变更

- **工具注册**：新增 `get_meal_analysis_digest`（工具名表 / read 工具表 / `ASSISTANT_TOOL_SOURCE_MAP['daily_records']`）、
  路由关键词规则、system prompt（通用与 read 子图两处）都补上「饮食/餐食问题优先用它，别再看图或从文案猜」。
- **工具参数打通**：此前 `agent` 节点只把 `tool_calls` 的 name 传下去、args 被丢弃（工具只能从 `userMessage` 猜参数）。
  新增 `AssistantToolCall{name,args}`：state 的 `pendingToolCalls` 携带 args，`ToolExecutorFn` 与
  `AssistantToolExecutionContext.toolArgs` 一路带参；`tool-definitions.ts` 支持按工具声明参数 schema
  （digest 声明 `days` 1–15、`limit` 1–20 整数，其余工具仍是空 schema）。
- **窗口读走投影列**（`tools/records/query.service.ts` 的 `buildMealAnalysisDigest`）：一条范围查询取窗口内 meal facts，
  用投影列判 `analyzed`、取 headline 与热量区间，只为进入结果的 ≤`limit` 条回读 payload 取 `items` / `dishes`；
  `analyzing` / `analysis_failed` 的餐食不进 digest，其 payload 从不解析。模型给的 `days` / `limit` 服务端再夹一次
  （超过 15 天 / 20 餐时截断，并写进 envelope 的 `ambiguities` 与 `coverage: partial`）。
- `DailyRecordFact` 补齐餐食投影列（状态/时间/失败原因/headline/区间/档位）与 `dailyRecordFactSelect`；
  `reports` 复诊摘要里自取记录的内联 select 同步补齐。这是投影列第一次被跨模块读侧消费。
- **envelope**：`{ startDate, endDate, analyzedMealCount, meals[{ date, occurredTime, title, headline, calorieRange, items, dishes }] }`。
  `title` 原样回记录标题：餐食记录没有稳定餐次码，凭标题猜 lunch/午饭 正是本链路要废掉的文本启发式。
- **契约**：`GET capabilities` 的工具名枚举随新工具增长一项，`pnpm export:openapi` 重新导出（paths 124 / schemas 347 不变，仅多一个枚举值）。

### 验证

- `pnpm typecheck`、`pnpm lint:check`、`pnpm build`、全量单元测试通过。
- 新增用例：`query.service.spec.ts` 的 digest 六例（默认窗口、投影列读、只取 analyzed 且新→旧、days/limit 封顶、
  非法参数回落、明细与缺失区间）、`tool.service.spec.ts` 的模型参数透传、`read.service.spec.ts` 的 envelope 与截断语义、
  `tool-definitions.spec.ts` 的参数 schema、`router.spec.ts` 的饮食关键词；spec 里的 `executeTools` 断言与
  policy/runtime 工具清单同步。
- 未跑 e2e（需本地 Postgres/Redis）。
