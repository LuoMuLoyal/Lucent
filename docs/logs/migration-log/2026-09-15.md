## feat(daily-records): 新增症状目录端点

（症状链路优化 Phase 3 服务端侧；计划文档见 Luminous `plans/2026-09-14-symptom-chain-optimization.md`，
执行完毕后删除。）

### 背景

症状目录此前只存在于客户端常量（`fast_entry_choices.dart` 的四个硬编码项），后端对「有哪些症状」毫无概念：
新增症状要发版，将来若要做「常见症状统计」也没有稳定的码表可依。本轮把目录的**源**放到后端，客户端保留同码
兜底副本供离线/未登录渲染。

### 变更

- `constants/symptom-catalog.constants.ts`：九个目录码与展示顺序
  （headache / stomachache / dizzy / fever / nausea / cough / fatigue / insomnia / other）——码即 payload
  `symptom` 的线上取值，客户端偏好也存码。
- `src/i18n/{zh-CN,en}/symptom-catalog.json`：按 `Accept-Language` 本地化的展示文案（nestjs-i18n
  `AcceptLanguageResolver`）。
- `services/symptom-catalog.service.ts` + `dto/symptom-catalog.dto.ts`：`GET daily-records/symptom-catalog`
  返回 `{ items: [{ code, label }] }`；路由声明在 `@Get(':id')` 之前，避免被动态段吞掉。
- `daily-records.controller.ts` / `daily-records.module.ts` 接线；模块 README 的边界与内部结构同步。
- `docs/reference/generated/openapi.json` 重新导出（paths 123 → 124）。

### 补充：响应 schema 与 operationId 的注册

导出脚本**不看** `@SerializeOptions`，响应体要经 `registerResponseSchema()` 登记才会成为命名组件并回写到 200
响应上；method→operationId 则走 `plans/_naming-lookup.json` 的命名表。首版漏了这两处，生成物因此是
`Response<void>`。已补：

- `daily-records.controller.ts` 底部登记 `SymptomCatalogResponse`（对齐 `DailyRecordListResponse` 等既有条目）；
  方法补显式 `SymptomCatalogResponseDto` 返回类型（保持同步，`require-await` 不允许无 await 的 async）。
- `plans/_naming-lookup.json` 增 `DailyRecordsController_symptomCatalog → getSymptomCatalog`。
- 再导出后 200 响应为 `$ref: #/components/schemas/SymptomCatalogResponse`，`operationId: getSymptomCatalog`，
  客户端生成物随之变成类型化方法（Schemas 345 → 347）。

### 验证

  `services/symptom-catalog.service.spec.ts`（码与顺序、逐项走 `symptom-catalog` 命名空间、语言切换生效）

- 该端点是无用户维度的静态参考数据，不适用 e2e 的「跨用户 404」与 list 上限约定（数据量固定为目录长度）。

## refactor(daily-records): 新增餐食分析 v2 契约与规范化

（餐食分析链路重构 P0-1 第 1 步；计划文档在 Luminous 侧，实施完毕后该文件删除。）

### 背景

现有餐食链路是「视觉识别菜品 → 菜品分解 → 成分接地对照食物成分表 → 算热量」，实测在真实照片上行不通：
误差逐段放大成没有意义的数字，且要维护一张覆盖真实饮食的成分表。已核实的硬缺陷还包括：坏 JSON 被降级成
「空结果」却按成功写入、LLM 抛错无 catch 导致记录永久 `analyzing`、幂等只在调用前检查、
`confirmed` 完全由客户端 payload 决定、`defaultRatio` 不参与营养计算。

### 变更

- 新增 `src/modules/daily-records/schemas/meal-analysis.schema.ts`：v2 契约（zod）与服务端规范化。
  - `analysisStatus` 收敛为 `analyzing | analyzed | analysis_failed`（删除 `confirmed` / `unconfirmed`）；
  - `calorieRange` 独立字段 `{min,max,unit,bucket}`，`bucket` 由数值推导、区间取整并 clamp、
    `min<=max` 自动纠正、非法区间落 `null`——**不给伪精确单值**；
  - `items[{rank,kind,polarity,headline,detail}]` 按 `rank` 重排并重编号、丢弃空文案、封顶 5 条，
    `kind`/`polarity` 非法值回落到 `other`/`neutral`；`kind` 为封闭词表（carb/fat/protein/vegetable/fruit/
    fried/sugar/sodium/portion/balance/other）；
  - `dishes[{name,source}]` 只存菜名（去空、按名去重、封顶），`source` 区分模型识别与用户改名，**不存营养成分**；
  - `facets` 收敛词表与档位（`low|ok|high`），是规则/聚合用的机器语义唯一来源；
  - 生成器 `buildAnalyzingMealAnalysis` / `buildFailedMealAnalysis` 与稳定失败原因码
    （`image_count_invalid` / `vision_unavailable` / `model_failed` / `model_timeout` / `invalid_output`）；
  - `mealAnalysisHeadline()` 供列表条目取「最重要的一条」。
- v1 的 `coverage` / `mealInput` / `recognizedDishes` / `resolvedIngredients` / `compositionMatches` /
  `nutritionEstimate` 等成分级结构一概不再存在，不做兼容读取。

### 验证

- `pnpm typecheck` 通过。
- 新增 `src/modules/daily-records/schemas/meal-analysis.schema.spec.ts`（12 例）：schema 接受规范化结果、
  拒绝 v1 版本号与已删状态；`items` 重排/去空/封顶/非法枚举回落/未排序项置后；区间纠正、档位推导与非法区间；
  菜名去重与 `source` 回落；`facets` 过滤未知键；三种生成器形状与 `mealAnalysisHeadline`。
- 后续步骤（尚未开始）：`vision` 改为一次多模态调用直出 v2、`worker` 的 revision 复检与失败终态、
  删除成分表相关服务、投影热列与 Prisma 迁移。
