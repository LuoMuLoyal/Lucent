## refactor(daily-records): 新增餐食分析 v2 契约与规范化

（餐食分析链路重构 P0-1 第 1 步；计划文档在 Luminous 侧，实施完毕后该文件删除。）

### 背景

现有餐食链路是「视觉识别菜品 → 菜品分解 → 成分接地对照食物成分表 → 算热量」，实测在真实照片上行不通：
误差逐段放大成没有意义的数字，且要维护一张覆盖真实饮食的成分表。已核实的硬缺陷还包括：坏 JSON 被降级成
「空结果」却按成功写入、LLM 抛错无 catch 导致记录永久 `analyzing`、幂等只在调用前检查、
`confirmed` 完全由客户端 payload 决定、`defaultRatio` 不参与营养计算。

### 变更

- 新增 `src/modules/daily-records/schemas/meal-analysis.schema.ts`：v2 契约（zod）与服务端规范化。
  - `analysisStatus` 收敛为 `analyzing | analyzed | analysis_failed`（删除 `confirmed` / `unconfirmed`）；
  - `calorieRange` 独立字段 `{min,max,unit,bucket}`，`bucket` 由数值推导、区间取整并 clamp、
    `min<=max` 自动纠正、非法区间落 `null`——**不给伪精确单值**；
  - `items[{rank,kind,polarity,headline,detail}]` 按 `rank` 重排并重编号、丢弃空文案、封顶 5 条，
    `kind`/`polarity` 非法值回落到 `other`/`neutral`；`kind` 为封闭词表（carb/fat/protein/vegetable/fruit/
    fried/sugar/sodium/portion/balance/other）；
  - `dishes[{name,source}]` 只存菜名（去空、按名去重、封顶），`source` 区分模型识别与用户改名，**不存营养成分**；
  - `facets` 收敛词表与档位（`low|ok|high`），是规则/聚合用的机器语义唯一来源；
  - 生成器 `buildAnalyzingMealAnalysis` / `buildFailedMealAnalysis` 与稳定失败原因码
    （`image_count_invalid` / `vision_unavailable` / `model_failed` / `model_timeout` / `invalid_output`）；
  - `mealAnalysisHeadline()` 供列表条目取「最重要的一条」。
- v1 的 `coverage` / `mealInput` / `recognizedDishes` / `resolvedIngredients` / `compositionMatches` /
  `nutritionEstimate` 等成分级结构一概不再存在，不做兼容读取。

### 验证

- `pnpm typecheck` 通过。
- 新增 `src/modules/daily-records/schemas/meal-analysis.schema.spec.ts`（12 例）：schema 接受规范化结果、
  拒绝 v1 版本号与已删状态；`items` 重排/去空/封顶/非法枚举回落/未排序项置后；区间纠正、档位推导与非法区间；
  菜名去重与 `source` 回落；`facets` 过滤未知键；三种生成器形状与 `mealAnalysisHeadline`。
- 后续步骤见下方「餐食分析产出侧切换」条目。

## refactor(daily-records)!: 餐食分析改由一次多模态调用产出

（餐食分析链路重构 P0-1：产出侧切换；计划文档在 Luminous 侧，实施完毕后该文件删除。）

### 背景

承接上一条：v2 契约已就位，但**没有任何消费方**，旧管线（识别 → 分解 → 接地 → 算热量 → 人工确认）

## refactor(daily-records): 视觉失败改走 Result 边界（对齐 ADR-0012）

（餐食分析链路重构 P0-1 的收尾修正。）

### 背景

前一刀把视觉失败表示成自制的 `{ ok: true | false }` 联合类型。它不违 RFC 9457——餐食分析是后台作业，
失败从不经过 HTTP 响应，而是落成记录状态（`analysis_failed` + 原因码），「业务失败不得用 200 表示」
这条不变量也没被触碰——但它违反 ADR-0012 第 3 节：项目对「可预期的、可恢复的领域失败」只有一个
表示法 `ResultAsync<T, DomainFailure>`，且该 ADR 明确把 `{ ok, data }` / `{ ok, error }` 形状列为拒绝项。
全仓生产代码里也只有这一处是这个形状（其余同名形状仅出现在 spec 的解包辅助函数里）。

### 变更

- `vision.service.ts` 的 `analyze()` 改为返回 `ResultAsync<MealAnalysisVisionSuccess, DomainFailure>`：
  模型超时 → `DEPENDENCY_TIMEOUT`(504)；模型报错/不可达 → `DEPENDENCY_UNAVAILABLE`(503)（经
  `mapUnknownToDependencyFailure` 归类并保留 cause）；输出不合契约或被安全过滤清空 →
  `DEPENDENCY_BAD_GATEWAY`(502)。全部复用已登记的稳定码，不新增码，也不需要新的 HTTP 语义。
- `worker.service.ts` 改用 `isErr()` 分支，把失败码翻成落库原因码（`DEPENDENCY_TIMEOUT → model_timeout`、
  `DEPENDENCY_BAD_GATEWAY → invalid_output`、其余 → `model_failed`）：传输词汇与落库词汇各只有一份，
  映射集中在一个纯函数里。删除 `MealAnalysisVisionOutcome` 联合类型。
- spec 相应改断言 `isErr()` / `_unsafeUnwrap()` 与 `code`，并补 `DEPENDENCY_BAD_GATEWAY → invalid_output`
  的落库断言。

### 验证

- `pnpm typecheck`、`pnpm build`、`pnpm lint:eslint`（`--max-warnings=0`）、`pnpm exec oxlint`、
  全量单元测试通过。行为对外不变（落库状态与原因码与前一刀一致）。

## feat(assistant): 餐食分析 digest 工具（避免重复识图）

## refactor(today-suggestion): 饮食信号改读餐食 facets,删除文本启发式

（餐食分析链路重构第 5 步；计划文档为 Luminous `plans/2026-09-15-meal-analysis-rearchitecture.md`，已实施完毕、计划文件已删。）

### 背景

`caffeine_trend` 信号靠餐食记录的 `title`/`note` 里的「咖啡/茶/energy」关键词猜咖啡因摄入，
`caffeine_sleep_correlation` 规则再拿它跟睡眠趋势做关联——与已删除的症状严重度启发式同病：
换语言、换说法、或模型识别出的菜名不同，信号就会凭空消失或误报，而且「猜出来的咖啡因次数」
本身也不是可靠证据。

餐食 facets 的封闭词表（carb/fat/protein/vegetable/fruit/fried/sugar/sodium/portion/balance/other）
里**没有 caffeine**，所以「咖啡因改读 facets」按字面做不到。已与产品确认：删掉该信号与该规则，
把「饮食信号」重建为 facets 驱动，并新增一条消费它的饮食结构规则（否则信号没有消费方＝死代码）。

### 变更

  新增 `diet_facets`：只取投影列为 `analyzed` 的餐食（`analyzing` / `analysis_failed` 不进信号），
