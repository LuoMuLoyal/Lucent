## feat(monolith): 新增 `THROTTLE_DISABLED` 压测开关

### 背景

压测与故障演练需要把全局限流整个摘掉，而现有两个键做不到：`THROTTLE_TTL_MS` /
`THROTTLE_LIMIT` 只调窗口与配额，`THROTTLE_LIMIT` 的 schema 上限是 **1000**，所以
靠运行时热更新最多把天花板抬到「1000 次/秒/IP」，仍然会在高并发下产出 429。
实测 200 并发打 `/api/v1/health` 时 106/205 是 429，容量结论完全被限流污染。

### 变更范围

新增一个与配额无关的短路开关，把守卫整体跳过：

- `src/config/env/env-keys.enum.ts` — 新增 `THROTTLE_DISABLED`。
- `src/config/env/environment.validation.ts` — `z.enum(['true','false']).default('false')`。
- `src/common/throttler/runtime-throttler.guard.ts` — `canActivate` 首行判定，命中即
  `return true`，既不读快照也不调用 `super`，因此**不产生任何计数**。
- `src/common/throttler/runtime-throttler.guard.spec.ts` — 补 3 条用例：置 true 时
  完全跳过且 `increment` 零调用；显式 false 与未设置时行为不变（仍会 429）。
- `.env.development.example` / `.env.production.example` / `.env.test.example` — 补上
  这一组键。**顺带补了原本就缺的 `THROTTLE_TTL_MS` / `THROTTLE_LIMIT`**：这两项一直
  在代码与文档里存在，但三个模板文件里都没有，属于既存缺口。
- `docs/reference/environment-variables.md` — 补该项说明与白名单行。

### 为什么读 `process.env` 而不是运行时快照

`THROTTLE_TTL_MS` / `THROTTLE_LIMIT` 走 rnacos 运行时文档热更新；本项刻意不走。
压测脚本已经在用 rnacos 调窗口，若这个开关也进快照，脚本就要同时依赖两处状态，
一旦 rnacos 不可达（故障演练会专门停它）开关也会跟着失效。读裸 `process.env`
使它的语义保持「启动期决定、运行期不变」，与 `TRUST_PROXY` 等布尔开关一致。

### 风险与约束

置 `true` 等于摘掉全站限流；本拓扑无反代（`TRUST_PROXY=false`），届时唯一的流量
防线只剩云安全组。因此默认值必须是 `false`，且**只在压测/故障演练环境**打开。

## fix(monolith): SSE 连接并发上限 + 活跃连接指标

### 变更范围

- `src/common/api/sse/sse-connection-registry.service.ts` —— registry 增加两级准入：
  实例总上限（`SSE_MAX_CONNECTIONS`，默认 500）与单用户上限
  （`SSE_MAX_CONNECTIONS_PER_USER`，默认 3）。新增 `tryRegister()` 返回判别式结果
  （`accepted` / `global_limit` / `user_limit`），超限拒绝而非排队；连接数经
  `MetricsService.setSseActiveConnections()` 上报。
- `src/common/api/sse/sse.ts` —— `prepareSse` 返回 `SsePrepareResult`，准入判定在
  `writeHead` **之前**完成（SSE 一旦写出响应头，HTTP 状态即固定为 200，无法再改 503）。
  新增 `openSse(reply, tracker, language, userId)` 控制器便捷封装：被拒时抛
  `DomainFailureException(DEPENDENCY_UNAVAILABLE)`，由全局 `ApiExceptionFilter`
  统一产出 RFC 9457 Problem Details。
- 5 处 SSE 控制器调用点改为 `openSse(...)`，并传入 `user.sub` 用于单用户计量：
  `analysis`、`assistant`（×2）、`layouts`（×2）、`reports`。
- `src/common/metrics/metrics.service.ts` —— 新增 `sse_active_connections` gauge。
- `src/config/env/env-keys.enum.ts` / `environment.validation.ts` —— 两个新键，
  范围校验（1–100000 / 1–1000）。
- 三个 `.env.*.example` 补上这两项。
- `docs/reference/environment-variables.md` 补说明与白名单行。
- `sse-connection-registry.service.spec.ts` 新增 7 条准入用例（实例上限、单用户上限、
  被拒不占用户额度、释放后可重建、gauge 上报）。

### 为什么需要上限

长连接不消耗 CPU，但每条连接持有 response 缓冲、流上下文与上游生产者（LLM/检索）引用，
内存随并发线性增长。没有上限时，几百条连接即可把进程 RSS 顶到数 GB，拖垮同进程内的
HTTP 服务。超限一律拒绝而不是排队 —— SSE 的语义是"立刻开始推送"，排队既无意义又会
让调用方悬挂。

## fix(auth): 登录限流改为渐进延迟,移除可锁死他人账号的硬锁

### 背景

压测发现（`ops/stress-test/results/2026-11-28/REPORT.md` D7）：对任意已知邮箱
连发 11 次错误密码，之后**正确密码也返回 429**，锁 60 分钟。这意味着任何人
只要知道受害者邮箱就能把对方锁在门外，成本几乎为零 —— 防爆破机制本身变成了
定向拒绝服务手段。

### 变更范围

- `domain/policies/login-failures.ts` —— 移除硬锁语义：
  - 删除 `isLockedOut` 与 `lockedUntil` 的判定路径；
  - 新增 `backoffDelayMs(count)`：阈值（`CAPTCHA_THRESHOLD`）以下不延迟，
    以上每次翻倍（1s→2s→4s…），封顶 30s；
  - `evaluateBucket` 恒返回 `kind: 'allowed'`，附带 `delayMs` 与
    `captchaRequired`，**永不返回拒绝**；
  - `recordFailure` 不再写 `lockedUntil`（字段保留以兼容滚动升级期的旧桶）。
- `application/services/rate-limit.ts` —— `checkLoginRateLimit` 改为
  `loginDelayMs`（返回毫秒数）；重验路径 `checkReauthRateLimit` 改为独立实现，
  仍按 `LOGIN_FAILURE_MAX` 硬拒绝（会话内操作，无匿名锁死风险）。
- `application/services/credential.ts` —— 登录流程在凭据校验前 `await` 该延迟
  （`waitOutBackoff`），有上限所以正常用户几乎无感。
- 单测：`login-failures.spec.ts` 按新语义重写（25 条，含「999 次失败仍是 allowed」）；
  `rate-limit.spec.ts` / `credential.spec.ts` 同步调整。
- `src/modules/auth/README.md` 记录两条路径的差异与理由。

### 为什么不是「锁定更久/更严」

锁号把武器交给了攻击者：失败计数的副作用落在**受害者**身上（登录不了），
而攻击者只付出几次请求的代价。渐进延迟把副作用落在**发起方**身上 ——
猜测者每次都要等待，成本指数上升；受害者即使被刷失败，也只是登录慢几秒。

### 验证

- `pnpm --filter monolith typecheck` 通过。
- `pnpm --filter monolith test`（auth 三文件）：67 条通过。
- `pnpm --filter monolith lint:check` 0 error。

## chore(deploy): 容器安全基线 + 安全组暴露面核对

### 变更范围

- `compose.yaml` 的 `app` 服务补安全基线：
  - `read_only: true` + `tmpfs: /tmp`（阻断"落地文件"类攻击；字体/缓存临时文件有可写处）；
  - `cap_drop: [ALL]`（容器不需要任何 Linux capability）；
  - `security_opt: [no-new-privileges:true]`（禁止 setuid 提权）。
  镜像本身已是 `USER lucent`（uid 100），这些是叠加的第二道闸，
  不依赖 Dockerfile 单独生效。
- `docs/reference/deployment.md` 的暴露面一节补充 `9621` 的明确约束：
  LightRAG 无鉴权、唯一调用方是 app 容器（同 compose 网络走 `http://lightrag:9621`），
  因此**不应对任何外部来源放行**（含监控机），调试走 SSH 隧道。
  同时给出核对方式（`nc` 探测 + `nmap` 全端口扫描预期只有 `22`/`3000` 对外可达）。

### 为什么

压测实测（`ops/stress-test/results/2026-11-28/REPORT.md` D3/D4/D10）：
主机无 HIDS，挖矿进程与 EICAR 文件零拦截；裸机直跑时 app 是 root，可读
`/etc/shadow`、`docker.sock` 可写。容器化 + 只读根 + 丢 cap + 非 root 把这组风险
从"拿下主机"降级为"只能动一个受限进程"。`9621` 对监控机可达属暴露面超出文档，
需收口或在文档固化。

- 部署后应核对：`docker inspect` 显示 `read_only=true`、`CapDrop=[ALL]`；
  `ps` 中 app uid≠0。

## perf(suggestion): 信号与基线缓存改并行读取,减少同步往返

### 变更范围

`apps/monolith/src/modules/suggestion/application/services/pipeline.ts` ——
`run()` 里 `getSignals` 与 `getBaselineStatus` 两次缓存读原本**先后串行**，
但它们互相独立。改为一次 `Promise.all` 并发：缓存往返的 RTT 由两跳变一跳。

### 为什么

压测实测（`ops/stress-test/results/2026-11-28/REPORT.md` D8）：300 ms 的链路 RTT
能把 2.7 ms 的健康检查放大到 3–4.4 秒——单次请求里的每次串行 Redis/PG 往返都会
乘性叠加。跨可用区/高延迟链路上，"两跳串行"直接等于两倍延迟。把独立的读并行化
是最省改动的收益点，不改变任何语义。

### 验证

- `pnpm --filter monolith typecheck` 通过。
- `pnpm --filter monolith test -- src/modules/suggestion/`：527 条通过。
