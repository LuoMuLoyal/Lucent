## fix(admin): 修复内容管理接口 500

- 症状：`GET /api/v1/admin/content/legal-documents` 与 `GET /api/v1/admin/content/safety-tips` 在真实运行时返回 500，管理台打开这两个页面即落到 500 页。
- 根因：`StandardSchemaSerializerInterceptor.serialize()` 对 JSON 数组响应**逐项**调用 schema 校验，而这两个 handler 的 `@SerializeOptions` 给的是 `z.array(...)` 列表 schema，于是每个元素都被拿去校验「数组」并全部失败。仓库里仅这两个接口返回裸数组，故只有它们炸。OpenAPI 契约不受影响——200 响应由 `registerResponseSchema` 注册表提供（见 `scripts/contract/export-openapi.ts`），与 `@SerializeOptions` 无关。
- 修改：两个 list handler 改用 item schema（`adminLegalDocumentSchema` / `adminSafetyTipSchema`），注册表继续登记数组 schema，handler 注释说明该双声明。同时把 `updatedAt` 的 ISO 转换下沉到 owner service（与 `console.service.ts` 一致），控制器不再做 `toISOString()`；`SafetyTipsAdminService.create/update` 的审计 metadata 改传转换后的形状——Prisma Json 列不接受 `Date`。
- 单测：新增回归守卫——断言两个 list handler 的 `@SerializeOptions.schema` 不是顶层数组 schema，且注册表里对应 component 仍是数组；`legal-documents` / `medicines` 的 admin service 用例补充时间戳 ISO 断言与未知资源用例。
- 验证：`typecheck`、`lint:check`、`format:check` 通过；admin + legal-documents + medicines 聚焦 268 个单测通过；对运行中的实例实测 8 个路径全部 200（含 `/admin/`、`/admin/users`），SafetyTip 走完 create→update→delete 全链路，法定文档 no-op 更新 200，四类内容审计动作均落库；`pnpm export:openapi` 产物无 diff（132 paths / 370 schemas），Luminous 客户端无需重新生成。

## fix(admin): 修复仪表盘首屏渲染崩溃

- 症状：登录成功后立刻落到 500 页；服务端日志只有 `auth/login` 与 `admin/me` 的 200，**完全没有 `/api/v1/admin/metrics/overview` 请求**。强制刷新与清除站点数据均无效（与缓存、会话无关）。

- 测试：`classify.spec.ts` 改写为 `deriveIntent` 的投影语义；新增 `intent-classifier.service.spec.ts`（角色未配置/抛错/输出非法 → 降级；越权工具被丢弃）与 `graph.spec.ts` 的降级、候选集钳制用例；`graph.spec.ts` 不再钉"消息→工具"（那是模型行为），改为显式注入路由替身。新增 `agent/runtime/intent-eval.fixture.ts` 评测集（含事故三条真实样本，带事故当天旧路由的实测选择作对比基线）及其形状校验 spec。

## fix(assistant): DrugBank 段落检索的实体作用域读错字段

- 症状：不问中英文，`search_drugbank_passages` 一律返回"需要先解析出一个 DrugBank 实体作用域"的空信封。
- 根因有两层。①**这两个工具从未声明参数**（`TOOL_PARAMETERS` 里只有餐食 digest、CN 知识检索、本体/规则推理四项），模型只能传空参数，服务端只能读 `context.userMessage`（用户原句），于是 `drugbank_drugs.name ILIKE '%<整句>%'` 必然 0 行 —— 生产实测整句 0 行、`'%ibuprofen%'` 3 行；②即便传裸药名，`contains + take:5` 会把原药与酯/盐一起带回来（dexamethasone → DB01234 + 乙酸酯 + 棕榈酸酯），旧实现一律判 `partial`，作用域仍拿不到。单测没拦住是因为它们把裸药名当 `userMessage`、且 mock 了 Prisma。
- 修改：新增 `DRUGBANK_ENTITY_PARAMETERS`（`query` 必填，明确"只给药品名，不要传整句"）与 `DRUGBANK_PASSAGE_PARAMETERS`（`query` 是检索内容，药品身份由 `drugbankId`/`drugName` 给）；两个服务改为优先读 `toolArgs`、回退 `userMessage`；解析侧新增 `drugbankId` 精确匹配与**精确同名优先**的唯一化（精确命中不再算歧义）。
- 同时修掉"服务不可用被伪装成没有证据"：向量库未配置 → `verifiability: 'unavailable'`（并记 warn），作用域未解析 → `empty` 但 reason 指明是可操作的参数问题。
- 验证：新增"整句 `userMessage` + `toolArgs.query='ibuprofen'` 解析出唯一 DB01050""精确同名优先于酯/盐""向量库缺失 → unavailable"等用例；`pnpm typecheck` 与聚焦单测通过。

## fix(assistant): LightRAG 缺 `source` 时不再伪装成"工具不可用"

- `parseArguments` 把"模型没给 `source`"与"给了非法 `source`"同等对待，返回 `verifiability: 'unavailable'` 的空信封**且不打日志**。模型读到的是一句"检索服务不可用"，于是对用户宣称工具没开放 —— 事故现场 LightRAG 侧车其实是健康的（`/health` 200、语料齐备，现场直查 `/query` 能返回带引用的中文答案）。
- 修改：缺 `source` 默认落到 `leaflet`（新增 `LIGHTRAG_DEFAULT_SOURCE`，注释写明缺参数与非法值的区别）；非法值仍然拒绝，并记一条 warn 留痕。
- 验证：新增"缺 source → 走 leaflet 且正常发起检索、`LIGHTRAG-WORKSPACE: leaflet`""非法 source → warn + 可读信封"两个用例。
