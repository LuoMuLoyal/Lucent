## feat(assistant): 外部工具改为 DSH 式的按需加载

### 变更范围

- `domain/mcp/external-tools.ts`：新增 `EXTERNAL_LOADER_RAW_NAME`（`load_tools`）、
  `externalLoaderName()` / `isExternalLoaderName()`、`renderExternalToolCatalog()`。
- `adapters/agent/state.ts`：新增 `loadedExternalTools` 通道（union reducer）。
- `adapters/agent/nodes.ts`：`agent` 只绑定 `load_tools` + 本轮已加载项；
  `tools` 节点从 `load_tools` 的**调用参数**读名字写入 state。
- `adapters/acl/tool-executor.ts`：`executeExternalLoader` 本地校验（全或无），
  不把 loader 发给远端。
- `application/services/prompts.ts` + `adapters/agent/runtime.ts`：
  `externalTools` 变成提示词变量与代码提示词段落，每轮生成一次目录。
- `config/runtime/{prompt-registry,ai.schema}.ts`：`assistantSystem` 的占位符
  增 `externalTools`。

### 说明

**为什么现在才改。** 上一轮我把高德工具做成了「每轮全量 `listTools` → merge →
`bindTools(全部)`」。计划 §1.3 把 DSH 列为设计参照，DSH 的 `McpToolLoader` 是**按需
加载**：服务器工具不进工具列表，提示词只列名+摘要，模型显式 `load_tools` 之后才注册。
全量绑定把 12 个高德工具的 schema 每步塞进上下文，正是按需加载要消除的那部分成本。

**目录只放名字与首行摘要**（截断 160 字符，且不切断代理对）。12 个工具的目录是几百
token，绑 schema 是上千。`catalog` 按名字排序，否则重连一次就改变提示词前缀、打掉缓存。

**校验全或无。** 请求里任一名字不在 server 当前列表 → 一个都不加载。部分加载会让模型
以为自己说的事做成了一半，而它无从判断是哪一半。

**loader 不进 `TOOL_NAMES`。** 它属于 `amap__` 命名空间，是纯函数生成的公开名；放进
内置表会把「外部」这个名词重新拖回穷尽权限表，破坏 §5.5 的边界。

**写回放在 `tools` 节点，不放在 executor。** executor 是无状态的（MCP server 与提案
流共用它），而「本对话加载了什么」是图状态。名字从**调用参数**读，不从结果信封读：信封
只回显接受的名字，两端一旦不一致，图状态与实际绑定就会分歧。

### 验证

- `typecheck` exit 0；`lint:check` 0 error；`arch:check` passed（167 项，基线无新增）。
- `external-tools.spec.ts` 由 8 条扩到 14 条：loader 命名、目录格式（只首行、无
  schema、空描述不带悬空冒号）、按名排序、超长摘要不切断代理对、空列表渲染空串。
- 全量单测 4581 passed / 1 failed（既有 `GraphRecursionError`）。

## refactor(assistant): 系统提示词改为每步重建

### 变更范围

- `adapters/agent/state.ts`：`messages` 的注释与契约改写 —— **System 头不再存放在
  这里**，`prepare_context` 只写记忆块与用户问题。
- `adapters/agent/graph.ts`：`prepare_context` 删掉 `SystemMessage` 构造。
- `adapters/agent/nodes.ts`：`agent` 每步用**当步绑定的工具**调
  `buildSystemPrompt`，把结果前置到传给模型的消息列表。

### 说明

**这是上一段改动的必要配套，不是顺手优化。** 候选集一旦按步重算，一轮写死的提示词就
会继续宣称一个当步已不绑定的工具；模型照提示词调用，只拿到「不可用」信封。DSH 每步都
`systemPrompt.assemble({ …, toolSet })`，所以它的提示词与绑定永远同步。

**为什么不能简单地把 System 留在 `messages` 里替换。** `messages` 是 append reducer，
2026-10-07 的教训（计划 C7）是：想替换首条 System，实际又追加了一条，一轮出现两条
System 与两条用户消息。现在把「头」从记录里拿出来，每步在调用点拼，append 语义不受
影响。

### 验证

- `nodes.spec.ts` 由 4 条扩到 6 条：候选集按步重解析并据此收缩绑定；System 头由当步
  绑定的工具生成且是前置的第一条。
- 全量单测 4583 passed / 1 failed（既有 `GraphRecursionError`）。

## feat(assistant): 工具候选集按步重算，只收缩不扩张

### 变更范围

- `adapters/agent/deps.ts`：新增 `resolveAllowedTools(current) => Promise<ToolName[]>`。
- `adapters/agent/nodes.ts`：`agent` 每步先解析，再绑定结果。
- `adapters/agent/runtime.ts`：`resolveStepAllowedTools` 用 `IUserSettingsPort` +
  `AssistantPolicyService` 重新评估 `enabledToolNames`，与本轮快照取交集。

### 说明

**对齐 DSH 的 `when` 时机。** DSH 的 `tools.resolve()` 每步遍历每个注册项求值
`when({ agent })`；Lucent 原来一轮算一次 `policy.enabledToolNames`。差别在可观测行为上：
`lightragClient.isEnabled()` / `semanticaClient.isEnabled()` 读的是运行时快照，sidecar
中途挂掉或运维改键都发生在这一轮之内。

**只收缩不扩张。** 与 `current` 取交集：中途上线的 sidecar 不在本轮候选集里，因为那份
候选集是调用方为这次对话清过的；扩张会让模型拿到一个调用方从未放行的工具。

**两个依赖都可选。** 手写构造的测试实例没有它们，此时保持本轮快照不变，不影响既有用例。

### 验证

- `typecheck` exit 0；`lint:check` 0 error；`arch:check` passed。
- 全量单测 4583 passed / 1 failed（既有 `GraphRecursionError`，`docs/TODO.md` 已登记）。

## fix(medicine-dose-logs): 槽位唯一性从「通常成立」变成由数据库裁定

### 变更范围

- 新迁移 `20261124120000_add_dose_log_slot_uniq`：**部分**唯一索引
  `(user_id, reminder_id, scheduled_for, scheduled_time)`
  `WHERE deleted_at IS NULL AND reminder_id IS NOT NULL`。
- `domain/dose-log/dose-logs.ts` 新增 `createOrUpdateOnSlot(input, patchOnConflict)`。
- `infrastructure/persistence/dose-logs.ts` 实现它：insert 失败且错误是**该索引**的
  P2002 时，重读槽位并 update 到胜者行；其他冲突仍报错。
- `mark-dose-log.ts` 的 find-then-create 改为「快路径先读，未命中则交给索引裁定」。
- controller 上 `mark` 的 409 声明删除（冲突已被吸收成 update）；`create` 的 409
  文案改为准确描述。

### 说明

**只加约束不改写路径，等于把「两行」换成「500」。** 反过来，只改路径不加约束，
并发下依然会插两行。所以两件事必须一起做。

**索引为什么带两个 WHERE 条件。**

- `reminder_id IS NOT NULL`：临时日志没有槽位身份，领域规则明确「永不合并」——
  同一天同一药可以有多次独立服用，按 medicine+date+time 合并会把两次剂量吞成一次。
- `deleted_at IS NULL`：软删后重新标记同一槽位必须能插入新行，这是「软删不可复活」
  那条规则在存储层的落点。

**为什么不用 Prisma `upsert`。** 它需要一个 Prisma schema 认知的唯一键，而这个约束是
**部分**索引，Prisma schema 表达不了；写成复合 `where` 会静默命中与索引守护不同的
行集。改用「insert 失败 → 重读 → update」，由数据库仲裁。

**冲突判定必须按索引名。** P2002 不区分约束；把任何 P2002 都当「槽位被占」会把无关
冲突变成静默覆盖。判定从 `meta.target`（Postgres 上是列名数组）取，并在实现中
用结构判断而非 `instanceof`——Prisma 在这个仓库里存在多个模块身份，`instanceof`
会对它自己抛出的错误返回 false。

**实测踩到的坑**：`create` 经 `lift` 已把 P2002 包成 `DomainFailureException`，
包装后不再携带约束名。因此 `createOrUpdateOnSlot` 不能复用 `this.create`，而是走
未包错误的 `insertRaw`。

**`scheduled_time` 可为 NULL 的边角**：Postgres 唯一索引视 NULL 互不相等，所以一个有
reminder 但无具体时刻的槽位仍可能重复。这类槽位罕见（提醒自带 hour/minute，mark 会
带上 time），用 COALESCE 表达式索引反而会把「没时刻」折叠成同一个值、误判两个合法
槽位为重复。接受该边角，理由写在迁移文件里。

### 验证

- `typecheck` exit 0；`lint:check` 0 error。
- `medicine-dose-logs` 4 files / 53 tests 全过，新增 5 条：
  - 槽位空闲时直接插入且不读不更；
  - 输了 insert 竞争时收敛到胜者行（update）；
  - 其他约束的 P2002 仍报冲突、不 update；
  - 胜者已被软删时报冲突（不吞成成功）；
  - 非冲突失败原样抛出。
- 未验证：真实 Postgres 上的并发插入（mock 无法证明索引本身）。

## feat(today-suggestion): 漏服提示接入半衰期判定与每日上限

### 变更范围

- `medicine-reminders` 的 `CurrentMedicineFact` 增 `halfLife`；
  `PrismaReminders.listCurrentMedicines` 在自己查询里关联 `drugbank_drugs`
  （仅 `source = drugbank` 的行）。
- `medicines/index.ts` 导出 `evaluateHalfLifeGap` / `parseHalfLife` /
  `exceedsHalfLifeGap` 及类型。
- 新表 `user_medicine_notify_marks`（迁移 `20261124130000_add_medicine_notify_marks`）：
  `(user_id, current_medicine_id, notify_date)` 唯一。
- 新端口 `application/ports/medicine-notify-ledger.ts`：`findMark` + **`claimMark`**。
- `adapters/acl/collectors/medication.ts`：`overdueUnconfirmed` 先过
  `evaluateHalfLifeGap`，再由 `claimMark` 原子认领；`noData` / `belowThreshold` /
  `throttled` / 输掉认领 四种情况都不产出该信号。

### 说明

**为什么 `claimMark` 而不是 `recordMark`。** 第一版写成 `findMark` + 写入，那是
check-then-act：两个并发重算都读到「今天没提示」，都产出、都写——一行插入成功，
但用户已经看到两次。改成 `createMany({ skipDuplicates: true })` 并**用返回的
`count === 1` 判断是否抢到**：答案来自执行写入的那条语句本身，没有窗口。

**`noData` 必须保持原行为。** 没有 `half_life` 的药完全沿用固定时长逻辑，不变得更激进或
更保守——「接入不改变现状」。

**信号状态不降级。** 判定拒发时**不产出** `overdueUnconfirmed` 信号，而不是把它降级
成别的 kind；槽位在汇总计数里仍然是 overdue。降级会把「过期」这个事实从其他消费者
眼前抹掉。

**每日上限按自然日**，与 `half-life-gap.ts` 的 `isSameLocalDay` 同口径。

**跨上下文读**：`half_life` 由 `MedicineReminderReaderPort` 在自有查询里解析，
collector 只拿到成品事实。`source = drugbank` 的条件是必要的——`cn` 的 refId 撞上
同一串时不得借用 DrugBank 的半衰期。

## test(assistant): runner 工具用例改用官方 FakeToolCallingModel

### 变更范围

- `adapters/agent/deep-agent-runner.spec.ts`：`collects tool results through the
wrapped executor` 不再手写 `FakeListChatModel` 子类，改用 LangChain 自带的
  `FakeToolCallingModel`（`langchain` 主入口导出）。用例耗时从约 101 秒降到 78 毫秒。

### 说明

**根因是伪造模型自己的状态从不前进。** 旧实现照抄了「`bindTools` 返回一个只实现
`.stream`/`.invoke` 的结构替身」这个形态，但轮次计数器 `boundRound` 从未递增：
`pick()` 永远返回 `rounds[0]`，循环于是无限次发出同一个工具调用，直到 LangGraph 的
`GraphRecursionError`（上限 10000）兜底。

接下来对照官方 test fixture（`langchain/dist/agents/tests/utils.js`）确认设计意图：

- `toolCalls: ToolCall[][]` 是**每轮一组**，不是一份整体剧本；
- `_generate` 读 `toolCalls[index]`，然后 `index = (index + 1) % toolCalls.length`；
- `bindTools` 返回**新实例但共享 `indexRef`**，所以推进跨 `bindTools` 存活；
- `toolCalls[index]` 为空数组时不写 `tool_calls`，循环据此自然结束。

旧实现在这四点上一处也没对上，所以它不是「官方 fixture 的变体」，是另一套假设。
