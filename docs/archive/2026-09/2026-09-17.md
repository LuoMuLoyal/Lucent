## fix(medicine-import): 靶点 XML 动作按名称+物种匹配,消除跨物种错挂

（来源：2026-09-16 审查报告 W1，报告 `plans/Lucent-review-09-16.md` 保留中。）

### 背景

`applyXmlTargetActions` 此前用 `name → targetId` 的 last-one-wins Map 解析 XML
靶点。`drugbank_targets` 中 306 个名字对应多个物种（细菌株共用蛋白名，如
「2-c-methyl-d-erythritol 2,4-cyclodiphosphate synthase」同时属于 Shigella /
Thermus / Shewanella / 大肠杆菌 / 分枝杆菌），last-one-wins 会把 XML 的作用类型
挂到任意一行上，详情页于是显示同名但错误的物种与 PDB 条目。

### 变更

- `scripts/import/medicine/import-medicine-knowledge.ts`：把 name-only Map 升级为
  `(name, organism)` 复合键 Map；名字命中多行且物种对不上时不猜，单独计入
  `ambiguous` 计数（旧口径会静默错挂）。返回对象新增 `ambiguous` 字段，导入日志
  输出形如 `[xml-targets] applied N relation(s), M unresolved name(s), K ambiguous
(name matched several species)`。
- `scripts/import/medicine/parsers/common.py`（docstring 侧已说明 keyed by
  name + organism，导入侧此前只用了 name，本次对齐）。

### 验证

- 重跑 `import-medicine-datasets.ts --command drugbank-drugs`（全量 XML，
  raw 1014340 行）成功，输出 `applied 32032 relation(s), 2467 unresolved, 432
ambiguous`——432 个此前会被静默错挂的跨物种同名靶点现正确归入 ambiguous。
- 抽查 DB00537（DNA gyrase subunit A 挂到 XML 声明的 Bacillus / E. coli /
  H. influenzae / S. aureus 四个物种行）、DB08231（Genome polyprotein 挂到 14 个
  病毒物种行），物种均与 XML `<organism>` 精确一致。
- 12 个 narrative 字段残留标记（未闭合 `[CODE`、"label, 裸编号"、任意 `[CODE`）
  全表计数均为 0。

## fix(medicine-import): 重写参考标记清洗正则,清除残留裸文本

（来源：2026-09-16 审查报告 W3，报告 `plans/Lucent-review-09-16.md` 保留中。）

### 背景

旧 `_REFERENCE_MARKER` 只覆盖 `[L6616]` / `[label,L6616]` 两种形态，`[L45859,A4393]`
（多编号）与 `[FDA label, A31973, A31976]`（带标签多编号）不命中，落到
`_INLINE_LINK` 被解包成裸文本；源 XML 缺右括号的未闭合标记残留 `[L#####`。入库
实测 4 行残留未闭合 `[L#####`、8 行残留「label, 裸编号」。

### 变更

- `scripts/import/medicine/parsers/common.py`：
  - 重写 `_REFERENCE_MARKER`：支持「标签前缀 + 多个逗号分隔编号 + 闭合括号」；
  - 新增 `_UNTERMINATED_MARKER`：仅在句末标点后生效的未闭合标记规则（`[` 后
    Lookahead 无 `]` 才删），并限制编号必须带字母前缀 `[A-Z]{1,5}\d{2,}`，
    避免误伤 `[100 mg]` / `[P450 enzymes]` 等真实散文括号；
  - 保留 `_INLINE_LINK` 解包剩余括号链接（`[aspirin]` → `aspirin`）。
- `scripts/import/medicine/drugbank-narrative-cleaning.spec.ts`：新增
  `clean_narrative_text marker handling` 套件，覆盖真实语料形态（含多编号、
  缺右括号、句末、字段末尾）与必须保留的散文括号（`[Homo sapiens]`、
  `[P450 enzymes]`、`[100 mg]`、`[vitamin K]`、`ATPase [Actin]`）。

### 验证

- `pnpm exec vitest run --config ./vitest.tools.config.ts` 全绿（82 tests），
  其中 narrative cleaning 23 tests。
- 重跑 `drugbank-drugs` 导入后全库核查：12 个 narrative 字段中未闭合标记、
  「label, 裸编号」、任意 `[CODE` 残留计数均为 0。

## 复核结论（W2 / S4 不成立,未按报告改动）

- W2「旁路字段会静默送到 SQL 直到 PG 报 column not found」不成立：
  `scripts/shared/db-upsert.ts` 绑参是 `spec.columns.map(col => record[col])`，
  只读声明过的列，多余键根本不会被读取。真实风险相反：解析器键名写错成不在
  columns 里的名字会静默写 NULL，属另一议题。
- S4 归属错误：`git show c5a1d66a~1` 里 `shouldBypassCache` 已存在，是既有代码；
  且 `Access-Control-Allow-Origin: 'true'` 与 `MEDICINES_BYPASS_CACHE_HEADER` 是
  两个不同的 header，不会互相误判。

## feat(assistant): 引入 LightRAG 中文散文检索层（基础设施）

（来源：`plans/2026-09-16-lightrag-introduction-plan.md` 的 P1 阶段；计划文件
仍在执行中，后续 P2 评测未开始。）

### 背景

中文药品知识检索目前分三套：中文产品表走 SQL 键查（保留），中文散文（说明书字段级
语义检索 + 医学问答）走进程内 pgvector（`search_medicine_leaflets` /
`search_medical_qa_corpus`，依赖未安装的 `vector` 扩展与 0 行的 chunk 表），英文侧
走 DrugBank 结构化查询。计划把**中文散文**的导入与查询整体交给 LightRAG sidecar；
本次只做引入与基础设施，**不删除**旧工具（删除必须等 P2 评测通过）。

### 变更

**(a) 配置层**（`src/config/env/`）

- `EnvKey` 新增 `LIGHTRAG_ENABLED`(默认 `false`) / `LIGHTRAG_BASE_URL`
  (默认 `http://lightrag:9621`) / `LIGHTRAG_API_KEY` / `LIGHTRAG_TIMEOUT_MS`
  (默认 `8000`，范围 100–60000) / `LIGHTRAG_WORKSPACE_LEAFLET`(默认 `leaflet`) /
  `LIGHTRAG_WORKSPACE_QA`(默认 `qa`)。
- 新增交叉校验 `assertLightragEnvironment`：仅当 `LIGHTRAG_ENABLED=true` 时要求
  `LIGHTRAG_API_KEY` 非空；关闭状态下残留值不阻断启动。
- 这三个变量族与 `AI_*` **完全独立**：LightRAG 用自己的变量名与凭据，即使指向同一
  厂商也是两套配置、两个 key、各自轮换。

**(b) sidecar 编排与独立 env**

- 新增 `deploy/lightrag/.env.example`（入库，LightRAG 全部变量的唯一清单：存储
  四件套 `PGKVStorage`/`PGVectorStorage`/`PGTableGraphStorage`/`PGDocStatusStorage`、
  独立 `POSTGRES_*`、按角色分离的 `LLM_BINDING_*`/`EXTRACT_LLM_*`/`KEYWORD_LLM_*`/
  `QUERY_LLM_*`/`EMBEDDING_*`/`RERANK_*`）；`deploy/lightrag/.env` 进 `.gitignore`。
  独立文件的理由是凭据暴露面：共用 Lucent 的 `.env` 会让该 Python 容器读到
  `JWT_*` / `DATABASE_URL` / 微信密钥。
- `compose.dev.yaml` 新增 `lightrag` 服务并置于 `lightrag` profile 内（默认
  `up -d` 不起它，避免拖慢本地启动），端口只绑 `127.0.0.1:9621`。
- `compose.yaml`（production）新增 `lightrag` 服务：同 compose 网络、只 `expose`
  9621、`env_file: deploy/lightrag/.env`、`stop_grace_period: 60s`（升级需排空
  pipeline 后停 writer）。`compose.staging.yaml` 同款但发布到 `127.0.0.1:9621`
  （app 是宿主 PM2 进程）。

**(c) retrieval 客户端**（`src/modules/assistant/tools/retrieval/`）

- `lightrag.types.ts` — 客户端契约常量/类型。`LIGHTRAG_QUERY_MODES` 刻意**不含**
  `bypass`；默认模式 `naive`；`LIGHTRAG_SOURCES_WITHOUT_GRAPH = ['leaflet','qa']`。
- `lightrag-client.service.ts` — `LightragClientService`：`POST /query` 固定带
  `only_need_context=true` + `include_chunk_content=true` + `include_references=true`
  （**绝不让 sidecar 生成答案**：那既是双重生成，也绕开 Lucent 安全层）；工作区经
  `LIGHTRAG-WORKSPACE` 头；客户端超时 8s（短于工具级 20s，让超时原因由本层说清）。
  失败归一为判别式 `LightragCallFailure`（`disabled`/`timeout`/`unreachable`/
  `unauthorized`/`bad_request`/`server_error`/`malformed_response`）而非抛异常——异常会
  诱使调用方用一个 catch 把"服务不可用"与"确实没证据"合成后者。
  从 doc id `leaflet:<leafletId>:<sourceField>:<chunkIndex>` 反解溯源。
