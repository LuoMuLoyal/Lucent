## 队列服务 DI 注入修复 — @Inject 显式令牌

### 背景

运行时报错 `Suggestion copy generation job failed: this.copyService.generateViaLlm is not a function`（后变为 `copyService.generateViaLlm is not a function`）。

**初始诊断（错误）**：认为是 `super()` 构造函数竞态——`this.xxxService` 在 `super()` 期间未赋值。将闭包改为引用构造函数参数 `xxxService`，但错误仍然存在。

**运行时诊断**：在构造函数中添加 `Reflect.getMetadata('design:paramtypes', ...)` 诊断日志，发现：

- `design:paramtypes` 元数据正确包含 `SuggestionCopyService`（第三参数类型正确）
- 但 NestJS 注入的是一个 **普通 `Object`**（`constructor.name === 'Object'`，`instanceof SuggestionCopyService === false`）

**根因**：NestJS 在解析继承 `BaseAsyncQueueService` 的子类构造函数参数时，第三个参数（业务服务）虽在 `design:paramtypes` 中类型正确，但 NestJS DI 容器未按类型令牌查找 provider，而是注入了空 `Object`。这可能是 NestJS + SWC `emitDecoratorMetadata` + 继承类构造函数的交互边界行为。

### 改动

6 个队列服务统一修复——对第三个构造函数参数（业务服务）添加 `@Inject(ServiceClass)` 显式令牌，强制 NestJS 按类令牌解析；同时恢复 `private readonly` 字段赋值 + `this.xxxService` 闭包引用模式（闭包在 Worker 异步调用时执行，此时构造函数已完成，字段已赋值）：

- `SuggestionCopyQueueService`（`today-suggestion/services/copy/copy-queue.service.ts`）— `@Inject(SuggestionCopyService)`
- `ExplanationQueueService`（`today-suggestion/services/explanation/queue.service.ts`）— `@Inject(ExplanationService)`
- `TodayAnalysisQueueService`（`today-analysis/services/analysis-queue.service.ts`）— `@Inject(TodayAnalysisService)`
- `ClinicSummaryPdfQueueService`（`reports/services/clinic-summary/pdf-queue.service.ts`）— `@Inject(ClinicSummaryService)`
- `ReportSummaryQueueService`（`reports/services/ai-summary/summary-queue.service.ts`）— `@Inject(ReportsAiSummaryService)`
- `MedicineRecognitionQueueService`（`medicines/services/medicine-recognition-queue.service.ts`）— `@Inject(MedicinesService)`

每个服务的修复模式：

```typescript
// Before (broken)
constructor(factory, @Inject(CACHE_MANAGER) cache, copyService: SuggestionCopyService) {
  super(..., (data) => copyService.generateViaLlm(data), ...);
}

// After (fixed)
private readonly copyService: SuggestionCopyService;
constructor(factory, @Inject(CACHE_MANAGER) cache, @Inject(SuggestionCopyService) copyService: SuggestionCopyService) {
  super(..., (data) => this.copyService.generateViaLlm(data), ...);
  this.copyService = copyService;
}
```

## @Cron → BullMQ Repeatable 迁移

来源：`Lucent/plans/2026-07-24-worker-separation-and-cron-repeatable.md` Phase 4

### 改动

将 3 个 `@Cron` 定时任务迁移到 BullMQ Repeatable Job（`upsertJobScheduler`），为未来多 worker 实例消除定时任务重复触发问题。不涉及进程分离（Phase 1-3 未执行），单进程部署模式不变。

**修改文件**：

- `src/modules/today-suggestion/services/lifecycle/service.ts` — 删除 `@Cron` 装饰器、`@nestjs/schedule` import 和 `LIFECYCLE_REFRESH_CRON` import

- `src/modules/medicine-reminders/services/scheduler.service.spec.ts` — 删除 overlap protection 测试（`isDispatching` 已移除）

### 设计要点

- **`upsertJobScheduler` 而非 `queue.add({ repeat })`**：以固定 scheduler id 幂等 upsert，改 cron 表达式时原地更新，无残留规则
- **时区统一 `tz: 'UTC'`**：与生产容器（node:24-alpine 默认 UTC）行为一致
- **`isDispatching` 删除理由**：BullMQ 保证单个 worker 不并发消费同一 job；相邻 repeat 实例重叠由 DB 唯一 delivery 记录幂等兜底
- **`pnpm start:dev` 行为不变**：不设 `WORKER_MODE`，factory 走 `full` 模式，Queue + Worker 都在 API 进程内
