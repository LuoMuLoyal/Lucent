## refactor(auth): cookie 会话按 ADR-0024 四层落地

- 背景：上一版把 cookie 会话写在 `controllers/` + `dto/` + `strategies/`，
  是模块内的贫血分层；ADR-0024 把 `auth` 列为第二批迁移，本批只做**新增的那条
  垂直切片**，不动 Bearer/OAuth/密码管理（批次内公开 API 零变化）。
- 四层落位：
  - `domain/session/cookie_policy.ts`：`SessionCookiePolicy` 值对象 +
    `resolveSessionCookiePolicy`。属性推导是**安全策略**（`SameSite=None`
    必须配 `Secure`，而本地 HTTP 存不下 `Secure`），属领域知识，不是 HTTP 细节。
    本文件零 import，满足 domain 纯度。
  - `application/use_cases/cookie_session.ts`：编排五个用例。输入是**应用层自己的**
    `LoginCommand` / `RegisterCommand`，不复用 adapters 的 zod 类型——
    `pnpm arch:check` 的 `ddd-application-no-infra-or-adapters` 会拦。
  - `adapters/http/`：`cookie.controller.ts`（只做 HTTP）、`dto/session.ts`（zod 契约）、
    `presenters/session.ts`（决定什么可以出网）、`session_cookies.ts`
    （`Set-Cookie` 序列化）。
  - `infrastructure/`：本切片无需新增实现——cookie 是 HTTP 投递关注点，
    不是持久化或外部系统。
- 顺带去掉 `AccessTokenReader`：轮换后需要「会话属于谁」，而
  `AuthTokenService` 的会话记录里本来就有 `user`。新增 `refreshWithUser()`
  直接返回它，因此不必为了读回 `sub` 去解一次刚签发的 JWT。`refresh()` 保留为
  token-only 视图，Bearer 调用方不受影响。
- 删除 `common/api/session-cookie.ts`：属性归 domain，序列化归 adapters，
  它已无独立职责。`SESSION_COOKIE_NAME` 等常量随之下沉到 domain。
- 契约零变化：`pnpm export:openapi` 后 `openapi.json` **无 diff**（150 paths /
  388 schemas），operationId 仍是 `registerSession` / `loginSession` /
  `refreshCookieSession` / `logoutSession` / `getMe`。`plans/_naming-lookup.json`
  的键随控制器改名同步。
- 验证：`pnpm typecheck`、`pnpm lint:check`、`pnpm arch:check`（205 entries，
  基线未新增）、`pnpm format:check` 全通过；`pnpm test` 4238 passed；
  `test/e2e/{auth,admin}` 144 passed。

## fix(auth): refresh token 重放检测与 token family 撤销

- 背景：轮换原本直接 `DELETE` 旧 session 行，导致「已轮换的 token」与「不存在的
  token」无法区分。安全后果是 RFC 9700 §4.13.2 要求的重放检测**不可能实现**：
  攻击者重放偷到的旧 refresh token 只会得到一个 401，既不会被识别为盗用，
  也不会使合法用户当前会话失效。
- 模型：`user_sessions` 增加 `family_id`（token 族根，NOT NULL）与 `rotated_at`
  （该行的 refresh token 已被换走，`null` 表示可用）。迁移
  `20261023120000_user_session_token_family` 回填 `family_id = id`，让存量会话
  各自成为族根；`@@index([familyId])` 支撑族撤销。
- 认领语义：`claimSessionForRefresh` 从 `deleteMany` 改为 `updateMany` 盖
  `rotatedAt`。原子性不变（`rotatedAt: null` 是唯一的并发闸门），但行会留下。
- 重放检测（`AuthTokenService.classifyReuse`）：找到已轮换的行时按**轮换距今时间**
  分两类——
  - 窗口内（`REFRESH_REUSE_GRACE_MS = 10s`）：判定为并发竞态，只返回
    `AUTH_REFRESH_TOKEN_INVALID`，**不**撤族。没有这条，两个标签页同时刷新会
    互相把对方踢下线。
  - 窗口外：判定为盗用，`revokeSessionFamily` 撤销整族（含盗用者可能已拿到的
    新会话），并记 `error` 级安全日志（含 `familyId` / `revokedSessions` /
    `rotatedAgoMs`，不含原始 token）。
    这是明确的取舍：宽限窗口推迟但不阻止「与合法轮换同一瞬间被偷」的 token 被
    检测到，换取并发场景不误伤。
- 轮换产生的新会话**继承同一 `familyId`**；全新登录以自己的 id 作为族根。
- `listActiveSessions` 排除 `rotatedAt != null` 的 tombstone，因此会话列表不会
  把历史轮换行当成活跃设备。
- 清理：tombstone 保留原有 `expires_at`，既有 `DataRetentionService`
  （`expiresAt < now`）会一并回收，不新增泄漏面。
- 契约零变化：仍返回 `AUTH_REFRESH_TOKEN_INVALID`，`openapi.json` 无 diff。
- 测试：单测覆盖「窗口内不撤族」「窗口外撤族并撤销后合法 token 也失效」
  「竞态中行已消失回落为 invalid」「轮换继承族」「新登录自成族根」；
  e2e 用真实库把 `rotated_at` 推到窗口外验证整族失效，并断言 tombstone 不出现在
  `/auth/sessions`。
- 验证：`pnpm typecheck`、`pnpm lint:check`（0 error）、`pnpm arch:check`
  （205 entries，基线未新增）通过；`pnpm test` 4243 passed；
  `pnpm test:e2e:ci` 见下方全量结果。
