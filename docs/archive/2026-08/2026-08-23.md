## Better Auth 集成可行性验证（Task 1 Spike）

验证 Better Auth 1.7.1 + `@better-auth/prisma-adapter` 1.7.1 能否与 Lucent 现有的 Prisma 7 多文件 schema、自定义 generated client 输出以及 PostgreSQL 测试数据库协同工作。本次为预研，不替换既有 auth 服务、不暴露网络端点、不触碰生产数据库。

### 集成方式

- 依赖：在 `package.json` 添加 `better-auth@1.7.1` 与 `@better-auth/prisma-adapter@1.7.1`，`pnpm install` 成功。
- Schema：通过 `npx auth@latest generate` 生成 Better Auth 默认模型，保存到 `tmp/better-auth-schema.prisma` 供人工审查。
- 用户表映射策略：**采用独立的 `BAUser` 模型**（表 `better_auth_users`），而非直接合并进 Lucent 的 `User` 模型。

### 调研结论（摘要）

- **推荐 Dokploy（适配度 7.5/10），备选 Coolify（7.0/10）**。理由：Dokploy 的 compose 一等公民模型可整体迁移现有 `deploy/compose.yml`（pgvector 社区镜像 `pgvector/pgvector:pg18`、双网络、profile、资源限制——**该镜像是带 vector 扩展的社区镜像，非自打包**）；Docker Image 支持任意 registry（腾讯云 TCR）拉取 + registry 回滚，与现有 CI 同构；两者内置 Traefik 均已跟进 v3.6（Coolify 自 v4.0.0-beta.444 起默认更新，Dokploy v3.6.7，RateLimit 中间件 v3.2+ 可用），该维度不构成差异；两者自托管均免费（Dokploy: Apache-2.0 + DSAL；Coolify: Apache-2.0），均有高权限控制平面的安全公告历史（Dokploy 2026-07 二十个公告 / Coolify 2026-01 十一个严重 CVE），须纳入升级运维。
- 项目方确认的部署前提：**PaaS 控制平面与 Lucent 业务分两台机器**；监控栈按轻量化可观测性方向换 **Victoria 系列**（victoria-metrics 单机 + 按需 vmalert，见 `plans/observability-lightweight-research.md`），继续以 compose 服务自管在业务机。

- 不推荐：Easypanel（生态弱）、CapRover（Traefik v2、维护放缓）、Dokku（无 UI、compose 弱）、Portainer/YunoHost（非 PaaS）。

## Better Auth 用户表方案决策（Task 2 前置）

根据计划约束「Better Auth user 表与 Lucent domain user 关系直接统一」，决定将 Better Auth 的 user 数据合并进 Lucent 既有 `User` 模型，而不是保留独立的 `BAUser` 桥接表。

### 合并方案要点

- 在 `User` 模型新增 `email_verified` Boolean 字段（Better Auth 需要），保留 `email_verified_at` 作为领域冗余/迁移锚点。
- `User.email` 由可选改为必填，与 Better Auth 默认 user schema 对齐；OAuth-only 注册流程必须确保邮箱可获取或显式拒绝无邮箱身份。
- 通过 Better Auth `user.fields` 配置将 `name` 映射到 `nickname`、`image` 映射到 `avatar`，避免新增重复字段。
- Better Auth `Session`/`Account` 模型的外键指向 `User`；`User` 原 `sessions` 关系（指向 `UserSession`）改名为 `lucentSessions` 等不冲突名称，为 Better Auth 的 `sessions`/`accounts` 关系腾出命名。
- Task 2 同步创建 NestJS 级 `BetterAuthConfig` / adapter service，注入 `PrismaService`，不直接暴露 Better Auth handler。

### 影响与风险

- 破坏性变更：大量既有 spec mock 与类型推断需同步更新 `email` 必填、`emailVerified` 新增、关系名变化。
- 需要一次性整理测试库 schema（`prisma db push` 或基于干净基线生成 migration），避免 Task 1 中出现的既有 drift 被再次带入。
- 保留 `User.password_hash` 不动（Task 3 再由 Better Auth `account.password` 接管 credential 密码），Task 2 只完成 user/session/account/verification 的 schema 与 adapter 配置。
