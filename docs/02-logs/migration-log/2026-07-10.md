# 2026-07-10 迁移日志

## 审查报告问题修复 (LUC-2026-0710-01)

### 背景

- 根据三份审查报告（增量审查、全仓库审查、回查纠正）确定的问题，对 Lucent 后端进行集中修复。
- 回查纠正后确认的有效问题：P0×4、P1×5。

### 改动内容

#### P0: 反馈记录操作无事务包裹 — `feedback.service.ts`

- `recordFeedback` 方法中的「创建反馈记录 + 更新建议状态」两个操作现在包裹在 `prisma.$transaction` 中，确保原子性。
- 同时修复 `updateData as never` 类型断言：改用 `Prisma.UserSuggestionUpdateManyMutationInput` 类型 + `SuggestionLifecycleState.DISMISSED` 枚举值。
- 更新 `feedback.service.spec.ts`：mock `$transaction` 方法。

#### P0: 建议生命周期无定时刷新 — `lifecycle.service.ts`

- 新增 `lifecycle.constants.ts`：定义 `SUGGESTION_ACTIVE_DURATION_MS`（8h）、`SUGGESTION_FADING_DURATION_MS`（4h）、`LIFECYCLE_REFRESH_CRON`（每 5 分钟）。
- `LifecycleService` 新增 `refreshLifecycleStates()` 方法，使用 `@Cron` 装饰器定时执行：
  - ACTIVE → FADING：`activatedAt` 超过 8 小时的建议自动转为 FADING。
  - FADING → EXPIRED：`activatedAt` 超过 12 小时的建议自动转为 EXPIRED。
- `app.module.ts` 注册 `ScheduleModule.forRoot()`。

#### P0: JWT validate 未检查用户状态 — `jwt-access.strategy.ts`

- `UserPayload` 接口新增可选 `status` 字段。
- `AuthTokenService.generateTokenPair` 签发时嵌入 `user.status`。
- `JwtAccessStrategy.validate` 检查 `status`：非 `active` 的用户（suspended/deleted）的 token 被拒绝。旧版 token（无 status 字段）兼容通过。

#### P0: 软删除全局过滤缺失 — `pin.service.ts` + `medicine-dose-logs.service.ts`

- `SecurityPinService.loadSecurityPinUser`：`findUnique` → `findFirst` + `deletedAt: null`，防止查询到已软删除的用户。
- `MedicineDoseLogsService.ensureOwned`：`userMedicineDoseLog.findUnique` → `findFirst` + `deletedAt: null`。
- `MedicineDoseLogsService.resolveReminderSlot`：`userMedicineReminder.findUnique` → `findFirst` + `deletedAt: null`。
- 同步更新对应测试文件的 mock（`findUnique` → `findFirst`）。

#### P1: 通知与持久化非原子 — `escalation.service.ts`

- 调整 `escalateIfNeeded` 中的操作顺序：先 `prisma.userSuggestion.update`（标记已通知），再 `notificationsService.createOrReplaceScoped`（发送通知）。
- 如果通知发送失败，建议已被标记为已通知，防止下一轮生成时重复发送通知。
- 更新 `escalation.service.spec.ts`：通知失败时 `updateMock` 仍被调用一次。

#### P1: /explain 和 /feedback 端点无限流 — `today-suggestion.controller.ts`

- `app.module.ts` 注册 `ThrottlerModule`（全局 100 req/min）+ `ThrottlerGuard` 作为全局 Guard。
- `POST /today/suggestions/:id/feedback`：`@Throttle({ default: { ttl: 60_000, limit: 20 } })`（20 次/分钟）。
- `POST /today/suggestions/:id/explain`：`@Throttle({ default: { ttl: 60_000, limit: 5 } })`（5 次/分钟，防止 LLM 成本失控）。

#### P1: `$queryRawUnsafe` 替换 — `app.service.ts`

- 健康检查中的 `prisma.$queryRawUnsafe('SELECT 1')` 替换为 `prisma.$queryRaw\`SELECT 1\``，获得编译时类型安全。
- 更新 `app.service.spec.ts`：mock `$queryRaw` 替代 `$queryRawUnsafe`。

- `pnpm build` ✅（580 files, 0 issues）

### 影响

- 安全性提升：JWT 现在拒绝非 active 用户的 token；软删除用户/记录不会被 `findUnique` 查询返回。
- 数据一致性：反馈记录操作原子化；通知发送前先持久化状态。

## 架构升级 (LUC-2026-0710-02)

### 背景

- 基于架构审查分析，对 Lucent 后端进行五项架构升级：AI 管道、LLM 重试、队列基础设施、Repository 抽象、JSONB Zod 校验。

### 改动内容

#### AI 管道：LangGraph 重构为真正的 tool-loop

- **旧图结构**：`START → prepare_context → respond → END`（空转图，LLM 不参与工具决策，keyword 路由）
- **新图结构**：`START → prepare_context → agent ↔ tools → respond → END`
  - `prepare_context`：根据 enabledContextSources 设置 allowedTools，构建初始 messages（SystemMessage + HumanMessage）
  - `agent`：调用 LLM（`model.bindTools()` + `invoke()`），LLM 通过 function calling 决定工具调用
  - `tools`：执行 LLM 请求的工具，添加 ToolMessages，递增 loopCount
  - 条件边：`pendingToolCalls > 0 && loopCount < MAX_TOOL_LOOPS` → `tools`，否则 → `respond`
- 新增 `tool-definitions.ts`：22 个工具的 LangChain function-calling 定义
- `runtime.service.ts` 新增 `runConversation()` 方法：运行完整 tool-loop，返回 toolResults + finalContent
- `core.service.ts` 更新：调用 `runConversation()` 替代旧的 `planConversation() + executeMany()` 两步流程
- 如果图产生了 `finalContent`，通过 `streamPreGeneratedContent()` 分块流式输出；否则回退到 `generateStream()` 做独立流式调用
- 图节点名从 `['prepare_context', 'respond']` 变为 `['prepare_context', 'agent', 'tools', 'respond']`

#### LLM 调用重试 + 指数退避

- 新增 `common/llm/llm-retry.helper.ts`：
  - `isRetryableLlmError(error)` — 区分可重试错误（429、5xx、timeout、network）和不可重试错误（400、401）
  - `withLlmRetry(operation, options)` — 3 次尝试，800ms 基础延迟，指数退避
- `BaseLlmGeneratorService`：`generate()` 和 `generateStream()` 的 LLM 调用包裹 `withLlmRetry`
- `AssistantRuntimeService`：`generateStream()` 的 LLM 调用包裹 `withLlmRetry`
- 常量 `maxRetries: 0` 保留在 MODEL_OPTIONS 中（LangChain 内置重试关闭），重试由 `withLlmRetry` 统一管理

#### 队列基础设施统一

- 新增 `common/queue/queue.factory.ts`：
  - `BullmqQueueFactory` — 全局可注入服务，统一管理 Redis 连接、Queue/Worker 创建、错误处理、生命周期
  - `createQueue<TData, TResult>(options)` — 返回 `{ queue, worker }`，Redis 不可用时返回 `{ null, null }`
  - `onModuleDestroy()` — 自动关闭所有管理的 Worker 和 Queue
- 新增 `common/queue/queue.module.ts`：`@Global()` 模块，注册到 `AppModule`
- 三个队列服务重构为使用工厂：
  - `MailQueueService`：保留 mail 配置驱动的 `defaultJobOptions` 和 `workerConcurrency`
  - `MealAnalysisQueueService`：保留 jobId 去重逻辑
  - `DataExportQueueService`：保留自定义 retry 选项

#### Repository 抽象（三模块全量迁移）

- **daily-records**：
  - `daily-record.repository.ts`：`DailyRecordRepositoryPort`（`findManyWithAttachments`、`findByIdWithAttachments`、`findManyByDateWithAttachments`、`findOwnershipData`、`create`、`update`、`softDelete`、`transaction`）+ `DailyRecordRepository`（Prisma 实现）
  - `DailyRecordsService` 和 `DailyRecordsOwnershipService` 全量迁移到 Port，不再直接注入 `PrismaService`
  - `daily-records.module.ts`：注册 Repository，导出 Port 供其他模块注入
- **assistant**：
  - `repositories/conversation.repository.ts`：`AssistantConversationRepositoryPort`（会话 CRUD、`findByIdWithMessages`、`persistTurn` 事务封装）+ `AssistantConversationRepository`
  - `repositories/summary.repository.ts`：`AssistantSummaryRepositoryPort`（`saveSummary`、`findLatestByDate`、`findByDateRange`）+ `AssistantSummaryRepository`
  - `ConversationService` 和 `HistoricalAiSummaryService` 迁移到 Port
  - `assistant.module.ts`：注册两个 Repository Port
- **auth**：
  - `repositories/session.repository.ts`：`AuthSessionRepositoryPort`（`createSession`、`findSessionByRefreshToken`、`updateSessionContext`、`deleteSession`、`deleteAllUserSessions`、`findSessionsByUser`）+ `AuthSessionRepository`
  - `repositories/account.repository.ts`：`AuthAccountRepositoryPort`（`softDeleteUser`）+ `AuthAccountRepository`
  - `TokenService` 和 `AccountService` 迁移到 Port
  - `auth.module.ts`：注册两个 Repository Port
- 所有相关单元测试（`daily-records.service.spec.ts`、`ownership.service.spec.ts`、`auth.service.spec.ts`、`token.service.spec.ts`）更新为 mock Repository Port 替代 `PrismaService`

#### JSONB Zod 校验

- 新增 `common/validators/jsonb-schemas.ts`：
  - `mealAnalysisPayloadSchema` — 餐食分析 payload 的 Zod schema
  - `mealRecordPayloadSchema` — 完整 meal record payload schema
  - `suggestionEvidenceSchema`、`suggestionActionSchema` — 建议相关 JSONB schema
  - `safeParseJsonb()` — 通用安全解析函数
- `meal-analysis.types.ts`：`parseMealRecordPayload()` 现在通过 Zod schema `safeParse` 校验，失败时回退到手动解析结果

### 验证

- `pnpm typecheck` ✅
- `pnpm lint:check` ✅（--max-warnings=0）
- `pnpm test` ✅（862 tests passed, 121 suites）

### 影响

- AI 管道从 keyword 路由升级为 LLM function-calling 驱动的真正 tool-loop，支持多轮工具调用
- LLM 瞬态失败不再直接传导为用户可见错误，重试后自动恢复
- 三个队列服务共享 Redis 连接和生命周期管理，减少重复代码和连接数
- daily-records、assistant、auth 三个模块的 Prisma 查询有了接口抽象，Service 层不再直接依赖 `PrismaService`，便于单元测试和未来数据源切换
- MealRecordPayload 读取时有 Zod 校验保护，防止 JSONB 结构变更导致的运行时错误
