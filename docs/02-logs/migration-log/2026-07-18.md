# 2026-07-18 迁移日志

## 修复 refresh token 接口缺少 @Public() 装饰器

### 问题

`SessionController.refresh`（`POST /api/v1/auth/refresh`）缺少 `@Public()` 装饰器。全局 `JwtAuthGuard`（`app.module.ts` 中通过 `APP_GUARD` 注册）会对所有未标记 `@Public()` 的路由执行 JWT 验证，导致 refresh 接口在 access token 过期后返回 401，形成死循环——用户无法刷新令牌，只能重新登录。

代码注释 `// No auth guard — accessToken may be expired` 与实际行为矛盾：全局守卫启用后，该接口被拦截。

### 修复

- `src/modules/auth/controllers/session.controller.ts`：
  - import `Public` 装饰器。
  - 在 `refresh` 方法上添加 `@Public()` 装饰器（方法级别，不影响同控制器中 `logout`/`sessions`/`revokeSession` 的认证要求）。
  - 注释从 `No auth guard — accessToken may be expired` 改为 `Public — accessToken may be expired, refresh uses the refreshToken body`。
- 运行 `pnpm export:openapi` 重新生成 `docs/openapi.json`：`/api/v1/auth/refresh` 不再包含 `security` 字段，与 `logout` 接口（仍需 `access-token`）形成正确对比。

### 验证

- `pnpm lint:check`：零问题。
- `pnpm typecheck`：零问题。
- `pnpm build`：744 文件编译成功。
- `pnpm test -- src/modules/auth/controllers/session.controller.spec.ts`：4 个测试全部通过。

## 实现 LLM 调用熔断器

### 背景

`plans/2026-07-16-deployment-hardening.md` 唯一剩余项。已有超时（`AI_MODEL_TIMEOUT_MS=10s`）+ 错误分类重试（`llm-retry.helper.ts`，3 次指数退避），但连续故障时无快速失败机制——LLM 提供商宕机会导致每个请求都走完 3 次重试（~24s）才回退，浪费资源并拖慢响应。

### 实现

- 新增 `src/common/llm/llm-circuit-breaker.service.ts`：
  - 轻量级进程内计数器，三态机：`closed → open → halfOpen → closed`
  - 默认参数：5 次连续失败触发熔断，30s 恢复超时，2 次探测成功后关闭
  - `open` / `halfOpen`（探测容量耗尽）状态下 `acquire()` 抛出 `LlmCircuitOpenError`（继承 `ServiceUnavailableException`，HTTP 503）
  - `halfOpen` 状态限制单探测（`halfOpenMaxProbes=1`），探测失败立即重新 `open`
- `LlmCommonModule` 注册并导出 `LlmCircuitBreakerService`，所有 LLM 调用共享同一实例
- `BaseLlmGeneratorService`（4 个子类）和 `AssistantRuntimeService` 构造函数新增 `circuitBreaker` 参数
- `generate()` / `generateStream()` 调用前 `acquire()`，成功后 `recordSuccess()`，失败后 `recordFailure()`
- `AssistantModule` 新增 `LlmCommonModule` 导入

### 设计决策

- **不引入 `opossum` 依赖**：单 slot 部署下单进程计数器已足够，无需 Redis 协调
- **全局单例而非 per-role**：所有 LLM role（analysis/chat/language）通常指向同一提供商，提供商宕机同时影响所有 role
- **不替代重试**：熔断器包裹在 `withLlmRetry` 外层——`open` 时直接快速失败，`closed` 时正常重试，`halfOpen` 时仅放行一个探测请求

### 验证

- `pnpm lint:check`：零问题。
- `pnpm typecheck`：零问题。
- `pnpm build`：746 文件编译成功。
- `pnpm test`：9 个测试文件 132 个测试全部通过（含 18 个熔断器单元测试 + 3 个 BaseLlmGeneratorService 熔断器集成测试）。
- `plans/2026-07-16-deployment-hardening.md` 全部章节已清空。

## 修复 daily-records 候选记录生成器测试缺少熔断器依赖

### 问题

`DailyRecordCandidatesGeneratorService` 构造函数在接入熔断器时新增了第三个依赖 `LlmCircuitBreakerService`，但其测试 `generator.service.spec.ts` 未同步更新 provider 列表，导致 Nest DI 报错：

```
Nest can't resolve dependencies of the DailyRecordCandidatesGeneratorService
(LlmRuntimeService, MetricsService, ?). Please make sure that the argument
LlmCircuitBreakerService at index [2] is available in the RootTestModule module.
```

4 个测试用例全部失败（configures the language model role / configures the tool naming options / builds a non-empty system prompt / builds a user prompt from context and copy）。

### 修复

- `src/modules/daily-records/services/candidates/generator.service.spec.ts`：
  - 新增 `LlmCircuitBreakerService` import。
  - `Test.createTestingModule` providers 数组新增 `{ provide: LlmCircuitBreakerService, useValue: new LlmCircuitBreakerService() }`，与其它生成器 spec（today-analysis / reports / today-suggestion）使用真实实例的模式一致。

### 验证

- `pnpm test -- modules/daily-records/services/candidates/generator.service.spec.ts`：4 个测试全部通过。

## 修复 CI trivy-action 版本引用

### 问题

GitHub Actions docker job 报错：

```
Error: Unable to resolve action `aquasecurity/trivy-action@0.28.0`,
unable to find version `0.28.0`
```

trivy-action 在供应链攻击响应后将所有 tag 迁移到 `v` 前缀（如 `v0.35.0`），仅保留 `0.35.0` 兼容标签，`0.28.0`（无 `v` 前缀）标签已被移除。

### 修复

- `.github/workflows/lucent-ci.yml`：`aquasecurity/trivy-action@0.28.0` → `aquasecurity/trivy-action@v0.36.0`（当前最新稳定版）。
