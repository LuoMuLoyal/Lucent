# 2026-07-22 AI 生成建议卡文案改造

## 修复开发服务器启动崩溃（stack-trace + urlencoded content-type parser 冲突）

### 背景

`pnpm start:dev` 启动后立即崩溃，报错 `TypeError: stackTrace.parse is not a function`。
该错误掩盖了真正的启动失败原因，导致无法定位问题。

### 根因分析

两个独立问题叠加：

1. **stack-trace@0.0.1 缺少 `parse` 函数**：`winston@3.19.0` 依赖 `stack-trace: "0.0.x"`，
   pnpm lockfile 解析到 `0.0.1`，该版本只导出 `get()`，没有 `parse()`。
   当应用抛出未捕获异常时，winston 的 `ExceptionHandler.getTrace()` 调用 `stackTrace.parse(err)`
   导致二次崩溃，掩盖了原始错误。
2. **Fastify urlencoded content-type parser 重复注册**：`@adminjs/fastify` 的 `buildAuthenticatedRouter`
   内部注册了 `@fastify/formbody`（注册 `application/x-www-form-urlencoded` 解析器），
   随后 NestJS 的 `app.listen()` → `init()` → `registerParserMiddleware()` 试图再次注册同一解析器，
   抛出 `FastifyError: Content type parser 'application/x-www-form-urlencoded' already present`。
   Node.js v24 默认将未处理的 Promise rejection 转为 `uncaughtException`，触发了上述 winston 崩溃。

### 修复

#### 1. stack-trace 版本修复

- `pnpm-workspace.yaml` 新增 `overrides.stack-trace: 0.0.10`
- pnpm v11 不再从 `package.json` 的 `pnpm.overrides` 读取配置，须使用 `pnpm-workspace.yaml`

#### 2. Body parser 冲突修复

- `src/main.ts`：`NestFactory.create()` 选项新增 `bodyParser: false`，禁用 NestJS 默认 body parser
- `src/setup-app.ts`：手动注册 `application/json` content-type parser（urlencoded 由 AdminJS 的
  `@fastify/formbody` 处理）

### 涉及文件

| 文件                  | 改动                                              |
| --------------------- | ------------------------------------------------- |
| `pnpm-workspace.yaml` | 新增 `overrides.stack-trace: 0.0.10`              |
| `src/main.ts`         | `NestFactory.create` 选项新增 `bodyParser: false` |
| `src/setup-app.ts`    | 手动注册 JSON content-type parser                 |
| `pnpm-lock.yaml`      | stack-trace 从 0.0.1 更新到 0.0.10                |

### 验证结果

- `pnpm start:dev` — 启动成功，无崩溃
- `GET /api/v1/health` — 响应正常，database + cache 组件均 up
- `pnpm lint:check` — 0 errors

## 修复 daily-records 分页参数验证失败

### 背景

前端登录后跳转 record 页面时，`GET /api/v1/user/daily-records` 返回 400 验证错误：
`page must not be less than 1; page must be an integer number; pageSize must not be greater than 100; pageSize must not be less than 1; pageSize must be an integer number`

### 根因

`QueryDailyRecordDto` 的 `page` 和 `pageSize` 属性使用 `@IsInt()` / `@Min()` / `@Max()` 验证器，
但缺少 `@Type(() => Number)` 装饰器。全局 `ValidationPipe` 配置了 `transform: true` 但未启用
`enableImplicitConversion`，因此 `class-transformer` 不会自动将查询字符串（如 `"1"`）转换为
`Number` 类型。`@IsInt()` 和 `@Min()` / `@Max()` 均要求值为 `number` 类型，字符串直接失败。

### 修复

- `src/modules/daily-records/dto/query-record.dto.ts`：`page` 和 `pageSize` 新增 `@Type(() => Number)`
  装饰器及 `@ApiPropertyOptional` 的 `type: Number` / `default` / `maximum` 属性，与
  `medicine-query.dto.ts` 和 `snapshot-query.dto.ts` 的既有模式对齐。
- 重新导出 `docs/openapi.json` 并重新生成 Luminous Dart 客户端。

## 修复可空枚举字段反序列化失败

### 背景

前端登录后获取健康档案时，`UserHealthProfileDto` 的 `sexAtBirth` 字段反序列化报 `CheckedFromJsonException`，程序卡在 Mine 页面。

### 根因

`openapi_retrofit_generator` 对 `nullable: true` + `allOf` + `$ref` 模式的枚举字段生成非空类型（`SexAtBirth` 而非 `SexAtBirth?`）。后端返回 `null` 时 `v as String` 失败。

对比发现：无 `nullable: true` 的 `@ApiPropertyOptional` 枚举字段正确生成为可空类型（如 `CreateHealthContextAllergyDto.severity`）。`nullable: true` 标志反而导致生成器对枚举生成非空类型。

### 修复

- `src/modules/user-health-context/dto/response.dto.ts`：`sexAtBirth`、`unitSystem`、`severity` 从 `@ApiProperty({ nullable: true, ... })` 改为 `@ApiPropertyOptional({ ... })`（移除 `nullable: true`）。
- `src/modules/user-health-context/dto/update-profile.dto.ts`：`unitSystem`、`sexAtBirth` 的 `@ApiPropertyOptional` 移除 `nullable: true`。
- 重新导出 `docs/openapi.json`、运行 `openapi_retrofit_generator` + `build_runner` 重新生成 Dart 客户端。
- `Luminous/lib/features/health_context/data/mappers/mapper.dart`：三处 `.name` 改为 `?.name` 适配可空类型。

## AI 文案生成异步化重构

### 变更摘要

将建议卡 AI 文案生成从同步阻塞改为 BullMQ 异步队列 + Redis 缓存去重，消除用户请求延迟，复用 `BaseLlmGeneratorService` + `BaseAsyncQueueService` 架构。

### 背景

原 `CopyGeneratorService` 直接实例化 `ChatOpenAI`，违反架构规范；同步调用 LLM 增加用户请求延迟 500-2000ms。

### 变更详情

#### 1. 新增类型定义 (`types/copy-generation.types.ts`)

- `CopyJobData`：BullMQ job 数据，携带完整 LLM 上下文（evidence、confidence、suggestionType、ruleId、subtype、originalTitle/Reason/Boundary）
- `CopyGenerationContext = CopyJobData`
- `CopyPromptCopy`：LLM prompt 本地化文案

#### 2. 新增 `SuggestionCopyLlmService` (`services/copy/copy-llm-generator.service.ts`)

- 继承 `BaseLlmGeneratorService`，使用 `language` 角色模型
- 结构化输出 (Zod schema + function calling)
- 替代原 `CopyGeneratorService`（直接实例化 ChatOpenAI）

#### 3. 新增 `SuggestionCopyQueueService` (`services/copy/copy-queue.service.ts`)

- 继承 `BaseAsyncQueueService`，BullMQ 队列名 `suggestion-copy-generation`
- Worker concurrency: 3
- 模仿 `ExplanationQueueService` 模式

#### 4. 重构 `SuggestionCopyService` (`services/copy/copy.service.ts`)

- **读路径** `getOrEnqueue()`：查 Redis cache → hit 返回 AI 文案 / miss 返回兜底 + 入队
- **写路径** `generateViaLlm()`：二次 cache check + LLM 调用 + 写入 cache
- **降级路径** `generateSync()`：Redis 不可用时同步调用 LLM
- 批量方法 `getOrEnqueueBatch()` / `generateSyncBatch()`

#### 5. 修改 prompts (`prompts/copy.prompt.ts`)

- `buildCopyUserPrompt` 签名变更：接收完整 `CopyGenerationContext` 而非仅 `templateKey + params`
- `buildCopySystemPrompt` 新增 4 条规则（evidence 引用、confidence 语气、suggestionType 优先级、original 文案参考）

#### 6. 删除 `services/copy/generator.service.ts`

- 直接实例化 `ChatOpenAI`，违反架构规范，职责由 `SuggestionCopyLlmService` 替代

#### 7. 修改 `SuggestionService` (`services/suggestion.service.ts`)

- 注入 `SuggestionCopyQueueService`
- `copyRequests` 传入完整 candidate 信息（evidence、confidence、suggestionType 等）
- 调用方式从 `generateBatch` 改为 `getOrEnqueueBatch` / `generateSyncBatch`（根据 queue.isConfigured 分支）

#### 8. 更新模块配置 (`today-suggestion.module.ts`)

- 移除 `CopyGeneratorService`
- 新增 `SuggestionCopyLlmService`、`SuggestionCopyQueueService`

#### 9. 测试

- 新增 `copy-llm-generator.service.spec.ts`（6 个测试）
- 新增 `copy-queue.service.spec.ts`（5 个测试）
- 新增 `copy.service.spec.ts`（11 个测试）
- 更新 `suggestion.service.spec.ts` mock 适配新接口

### 性能对比

| 指标         | 原同步方案            | 新异步方案                        |
| ------------ | --------------------- | --------------------------------- |
| 用户请求延迟 | 500-2000ms (LLM 同步) | < 10ms (cache 查询 + 兜底返回)    |
| LLM 调用成本 | 每次用户请求          | 相同 templateKey+params 只调 1 次 |
| 重试能力     | 无                    | BullMQ 3 次指数退避               |

## i18n 硬编码清理（不兼容旧版本）

### 变更摘要

将 `today-suggestion` 模块中所有面向用户的中英文硬编码字符串迁移到项目现有 `nestjs-i18n` 体系，规则服务只产生 locale-neutral 的 i18n key，DTO 层在响应时按 `Accept-Language` 本地化。

### 背景

上一轮删除了 `SuggestionCandidate` 的 `title`/`reason`/`boundary` 字段后，规则服务中仍残留大量硬编码中文 evidence label（`当前杯数`、`目标杯数`）、action label（`去记录`、`去确认`）、enum value（`未确认`、`加重`）、LLM prompt 指令文案、system prompt 中文词汇示例，以及两处重复的最终兜底文案。

### 变更详情

#### 1. 新增 i18n 翻译文件

- `src/i18n/zh-CN/today-suggestion.json` — 中译
- `src/i18n/en/today-suggestion.json` — 英译
- 包含 `evidence.*`（18 个 label key）、`evidence_value.*`（2 个 enum value）、`action.*`（8 个 action label）、`field.*`（3 个 profile field name）、`fallback.*`（4 个最终兜底文案）、`prompt.*`（6 条 LLM 指令）、`error.*`（1 条错误消息）

#### 2. 改造 7 个规则服务

所有规则服务中的 `evidence[].label` 从硬编码中文改为 locale-neutral key（如 `'current_count'`），`evidence[].value` 从带单位的中文（`'2 杯'`）改为纯数值（`'2'`），enum value 从中文（`'未确认'`）改为 key（`'unconfirmed'`）。`primaryAction.label` 和 `secondaryActions[].label` 同样改为 i18n key。

`coverage.service.ts` 的 `fieldLabels` 映射表从 `{ birthDate: '出生日期', ... }` 简化为直接传递原始字段名作为 i18n key。

#### 3. `SuggestionService` 注入 `I18nService`

- `toDto()` 新增 `locale` 参数
- evidence label/value 通过 `this.i18n.t()` 本地化
- action label 通过 `this.i18n.t()` 本地化
- `resolveCopy()` 最终兜底文案从硬编码中文改为 `this.i18n.t('today-suggestion.fallback.*')`
