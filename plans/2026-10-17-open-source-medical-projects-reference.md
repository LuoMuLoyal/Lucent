# 开源医疗项目：功能差距与借鉴清单

Created: 2026-10-17
Status: 参考池（非执行计划，采纳项另立计划）

## 一、文档用途

对 GitHub 医疗开源项目做了一轮调研（检索 3,490 个仓库，入库 74 个，元数据经 API 实测）。
本文件逐项对比：**他们有什么具体功能，我们没有，或者做得不如他们**。

对比基线是 Lumos 现状：

- `Lucent`：`medicines`（药品搜索/详情/药盒识别/风险检查）、`medicine-dose-logs`（服药记录）、
  `medicine-reminders`（提醒）、`daily-records`（每日记录）、`user-health-context`（健康档案）、
  `assistant`（AI 问答）
- `Luminous`：Five-tab 客户端（today / record / medicine / review / mine）

## 三、逐项详述

### 缺口 1：药品不良反应反向查询

- 参考：https://github.com/tatonetti-lab/onsides（⭐107，MIT）
- **他们有什么**：给定不良反应，可以倒查哪些成分会导致它。OnSIDES 的
  `ingredient × adverse_event` 关系表天然支持双向索引
- **我们现状**：`CnMedicineLeaflet.adverseReactions` 是 TEXT，只能正向展示；
  无法回答"我起皮疹了，是不是我吃的某种药引起的"
- **借鉴点**：建 `ingredient ↔ reaction` 关系表，加 `reactionId` 反向索引。
  这是服药后出现症状时最自然的用户诉求，目前系统完全无法响应
- **授权**：MIT

### 缺口 2：不良反应频次分层

- 参考：OnSIDES（同上）/ FAERS
- **他们有什么**：区分常见 / 少见 / 罕见 / 未知，并按来源说明书数量给权重
- **我们现状**：说明书文本里频次信息是混在叙述中的，无法结构化比较
- **借鉴点**：`frequencyLabel` + `labelCount`，UI 上按频次分组折叠，
  而不是平铺一大段文字
- **为什么重要**：用户对"常见"和"罕见"的反应强度和决策完全不同，平铺等于没信息

### 缺口 3：真实世界用药风险信号

- 参考：FAERS（openFDA，CC0）+ https://github.com/bips-hb/pvm（GPL-3.0，算法参考）
- **他们有什么**：用 ROR / PRR / BCPNN / GPS 等统计方法，从自发上报数据里
  发现"说明书没写但实际在发生"的信号
- **我们现状**：完全没有这一维。我们的风险判断 100% 依赖说明书与 DrugBank 静态数据
- **借鉴点**：离线计算信号结果表，用于运营侧发现问题、以及后续规则调优的输入。
  **不建议进实时链路**
- **为什么重要**：这是识别"药品上市后新风险"的唯一途径

### 缺口 4：药品禁忌症结构化

- 参考：https://github.com/openemr/openemr（⭐5530，GPL-3.0，**只读设计**）
  / https://github.com/JamesZBL/db-hospital-drug（⭐299，**无许可证，只读设计**）
- **他们有什么**：禁忌症作为独立字段/表，与患者疾病、过敏、妊娠状态做交叉判定
- **我们现状**：`CnMedicineLeaflet` 有 `contraindications`，`DrugbankDrug` 也有，
  但都是长文本；风险检查里对禁忌的处理弱于对相互作用的处理
- **借鉴点**：把禁忌症拆成 `(药品, 禁忌条件类型, 禁忌条件值, 严重度)` 结构，
  与 `UserCondition`、`UserAllergy` 做确定性匹配

### 缺口 5：药物—食物相互作用未启用

- 参考：DrugBank（本地已有）
- **他们有什么**：把 food–drug 交互纳入用药建议
- **我们现状**：⚠️ **数据在手上但没用起来**。`DrugbankDrug.foodInteractions`
  是 JSONB 字段，已导入，但 `RiskDetectionService` 的 findings 里没有食物维度
- **借鉴点**：这是**成本最低的一项** —— 数据已有，只需在风险检查里增加食物分支，
  并在药品详情增加「饮食注意」区块

### 缺口 6：用药依从性追踪

- 参考：https://github.com/Futsch1/medTimer（⭐633，MIT）
  / https://github.com/waseefakhtar/dose-android（⭐636，MIT）
- **他们有什么**：
  - 每次提醒后记录"已服用 / 跳过 / 稍后"，形成依从率统计
  - 连续漏服高亮、依从率折线图
- **我们现状**：有 `medicine-dose-logs`（服药记录）与 `medicine-reminders`（提醒），
  但缺少**把两者关联起来的依从性视图** —— 用户看不到"我这周按时吃药的比例"
- **借鉴点**：提醒响应事件（taken/skipped/snoozed）落库，`review` tab 出依从率

### 缺口 7：剩余药量 / 补药提醒

- 参考：medTimer（同上）
- **他们有什么**：录入药品总量与每次用量，自动推算剩余天数，快用完时提示补药
- **我们现状**：无
- **借鉴点**：`medicines` 加库存字段，按 `dose-logs` 消耗推算。对慢病用户价值高

### 缺口 8：条码扫描

- 参考：openFDA NDC 数据集 / openemr
- **他们有什么**：扫药品条码（NDC / 国药准字）直接定位药品
- **我们现状**：有 `recognize`（药盒图片 AI 识别），但**无条码路径**。
  条码是确定性的，比视觉识别准确得多，且快
- **借鉴点**：`cn_medicine_products` 已有 `nationalDrugCode` 与条码字段，
  加扫码入口的成本不高，可作为图片识别的兜底

### 缺口 9：检验指标结构化 + 趋势

- 参考：https://github.com/thetahealth/mirobody（⭐1374，Apache-2.0）
  / https://github.com/xming521/CTAI（⭐675，**无许可证，只读思路**）
- **他们有什么**：
  - mirobody：化验单 → 结构化指标（LOINC/ICPC-3 归一），数值 + 单位 + 参考区间
  - CTAI：多次检查的定量指标做成折线/对比图，看病灶变化趋势
- **我们现状**：`daily-records` 是通用记录；没有专门的检验指标模型，
  无法回答"我的血糖这三个月在变好还是变差"
- **借鉴点**：这是**最大的功能空白**。健康管理类产品的核心价值在趋势，
  我们目前只有离散记录

### 缺口 10：指标参考区间判定

- 参考：mirobody（同上）
- **他们有什么**：每个指标带参考区间，自动判定偏高/偏低并标色
- **我们现状**：无。用户输入"空腹血糖 6.8"系统不知道这是偏高还是正常
- **借鉴点**：跟缺口 9 是同一件事的两面，一起做

### 缺口 11：过敏—药品交叉反应

- 参考：openemr allergy check
- **他们有什么**：基于成分/药物类别（如"青霉素类"）做过敏交叉反应判断，
  而不是字面匹配
- **我们现状**：`risk-detection.service.ts` 的过敏匹配是字符串 `includes`。
  能匹配"青霉素"→"青霉素V钾片"，但匹配不到"penicillin"，也匹配不到
  "阿莫西林"属于青霉素类
- **借鉴点**：引入药物类别层级（ATC 或 DrugBank 分类），做"类别级"过敏匹配。
  这是**准确性问题**，不是新功能

### 缺口 12：药物—疾病禁忌

- 参考：openemr / https://github.com/apache/ctakes（⭐139，Apache-2.0）
- **他们有什么**：把患者疾病与药品禁忌、适应证做结构化匹配
- **我们现状**：有 `user-health-context` 与 `UserCondition`，但风险检查中
  疾病主要作为 LLM 上下文，**未参与确定性判定**
- **借鉴点**：先做常见慢性病（高血压/糖尿病/肾病/肝病/妊娠）的确定性禁忌表，
  覆盖 80% 场景，不必一上来做全量

### 缺口 13：AI 回答带引用来源

- 参考：mirobody / https://github.com/wizardlancet/OpenOE-Lite（⭐94，MIT）
- **他们有什么**：每条结论标注来自哪个文件/哪段原文，用户可核查
- **我们现状**：`assistant` 有 RAG（LightRAG / Neo4j），但回答未逐条标注出处
- **借鉴点**：生成链路里保留 chunk 命中来源，输出时附引用。医疗场景下
  可核查性直接决定用户信任度

### 缺口 14：结构化病历编辑器

- 参考：https://github.com/huimeicloud/hm_editor（⭐123，LGPL-2.1）
  / https://github.com/tlzzu/SoDiaoEditor（⭐614，**无许可证**）
- **他们有什么**：结构化病历编辑（数据元组件化、模板、打印续打、修订留痕）
- **我们现状**：`daily-records` 是自由文本/简单结构
- **借鉴点**：**对本产品优先级不高**（我们面向个人而非医生），若未来做
  "就诊记录整理"再考虑

### 缺口 15：家属代管 / 多人协作

- 参考：https://github.com/fastenhealth/fasten-onprem（⭐2796，GPL-3.0）
- **他们有什么**：一个账户管理多个家庭成员的健康档案
- **我们现状**：单用户模型
- **借鉴点**：给药场景中"帮老人/孩子记药"是高频需求。需要评估数据模型改动成本

### 缺口 16：数据导出 / FHIR 互操作

- 参考：https://github.com/hapifhir/hapi-fhir（⭐2414，Apache-2.0）
- **他们有什么**：标准 FHIR 导出，数据可迁移到其他系统
- **我们现状**：数据锁定在自有 schema
- **借鉴点**：至少提供导出（CSV/PDF/JSON）。FHIR 完整映射投入大，可后置

### 缺口 17：离线可用

- 参考：healsense（Flutter + Drift）/ medTimer
- **他们有什么**：本地数据库，无网可用
- **我们现状**：依赖后端 API
- **借鉴点**：用药提醒是**最需要离线**的功能（没网也要提醒吃药）。可考虑
  本地通知兜底

## 四、按投入产出排序的建议

**先做这 4 个（数据已有或成本极低）：**

1. **药物—食物相互作用**（缺口 5）—— `foodInteractions` 字段已导入，只是没用
2. **过敏类别匹配**（缺口 11）—— 修准确性，不是造新功能
3. **AI 回答加引用**（缺口 13）—— 提升信任度，改动集中在生成链路
4. **用药依从性视图**（缺口 6）—— 数据基本已有（dose-logs + reminders），
   缺的是关联与统计

**中期做（需要新数据模型）：**

5. **不良反应结构化 + 反向查询**（缺口 1、2）—— 另立数据源计划已覆盖
6. **检验指标 + 趋势**（缺口 9、10）—— 最大空白，也最大工作量
7. **剩余药量提醒**（缺口 7）
8. **条码扫描**（缺口 8）

**长期 / 视定位而定：**

9. 真实世界信号（缺口 3）—— 偏运营侧
10. 药物—疾病禁忌（缺口 12）—— 先做常见慢性病
11. 家属代管（缺口 15）、离线（缺口 17）、导出（缺口 16）
