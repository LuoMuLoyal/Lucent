# 用药智能：从「风险提示」升级为「可解释的用药决策」

> 状态：**草案，待评审**。2026-10-24 起草。
> 范围：`Lucent` 后端为主；`Luminous`（患者端）与 `Lumine`（分析端）的呈现差异在 §七 说明。
> 前置阅读：`Luminary/apps/lumine/PRODUCT.md` §五/§十、`src/modules/today-suggestion/README.md`、
> `src/modules/medicines/README.md`。

## 一、结论

用户提出的判断成立：**现有「用药提醒 + 药品风险检查」确实普通**。

核实后，问题比「普通」更具体——**能力已经建好，但知识没接上**：

| 现状       | 做了什么                                      | 缺什么                                           |
| ---------- | --------------------------------------------- | ------------------------------------------------ |
| 建议引擎   | 8 条规则，其中与用药相关的只有 2 条           | 其余 6 条全是睡眠/饮水/饮食等通用健康建议        |
| 风险检查   | `risk-scoring.ts` 是固定权重加分表            | 只回答「有没有冲突」，不回答「为什么」「怎么办」 |
| 药品知识层 | **Neo4j 图已建好**（3,278 节点 / 211,630 边） | Lucent 只经 assistant 工具用它，业务侧没接       |

三个方向（机理、全景、半衰期）**可以都做，但共用一条地基**：把已经存在的 Neo4j 图
变成业务端点能调用的关系查询能力。

> **2026-10-24 更正**：本计划初稿把「本地 Prisma 知识库几乎是空的」当作 P0 阻塞项，
> 并据此设计了一套「自己建关系查询」的方案。该判断**不完整**——它漏看了一条既有事实：
> 图数据早在 Neo4j 里，且 Lucent 已有可用的客户端。见 §二 与 §四。

## 二、前提：图在 Neo4j 里，数据是齐的

⚠️ **这一节是本计划的地基。初稿在这里判断错了，务必先读完。**

### 2.1 图已经建好，规模与内容都够

`semantica-service/README.md` 记载（实测）：**3,278 节点 / 211,630 边**，
由 DrugBank 结构化字段**确定性映射**入图，**不经 LLM 抽取**。

最关键的是：`scripts/probe_oag.py` 里已经有**正是方向一要用的查询**，且都是类型化多跳：

```cypher
-- cyp_mediated_ddi：抑制某 CYP 的药 × 以该 CYP 为底物的药
MATCH (a:Drug)-[:INHIBITS]->(e:Protein)<-[:SUBSTRATE_OF]-(b:Drug)
WHERE e.gene_name IN ['CYP3A4','CYP2D6','CYP2C19','CYP1A2','CYP2C9']
  AND id(a) <> id(b)
RETURN e.gene_name AS enzyme, a.name AS inhibitor, b.name AS substrate
```

这就是「布洛芬 + 华法林为什么冲突」的答案形态，**不需要新建任何表**。
`probe_oag.py` 另有 `shared_targets`（共享靶点）、`cascade_metabolic_chain`（4 跳级联）、
`inhibition_plus_interaction`（机制 + 直接相互作用联立）等探针，与 §三 的三个方向一一对应。

### 2.2 边类型

实测 21 种关系类型（ADR-0022 明确以实测为准，`VERIFICATION-SCALE.md` 的 26 种已过时）。
方向一/二用到的核心边：

| 边               | 语义                             | 用途                 |
| ---------------- | -------------------------------- | -------------------- |
| `INHIBITS`       | 药物抑制酶/靶点                  | 机理链起点           |
| `SUBSTRATE_OF`   | 药物是某酶的底物                 | 机理链终点           |
| `INDUCES`        | 药物诱导酶                       | 机理链（反向调浓度） |
| `ACTS_ON`        | 药物作用于靶点（含酶以外的靶点） | 方向二共同靶点       |
| `TRANSPORTED_BY` | 药物经某转运体（P-gp 等）        | 外排/吸收相互作用    |
| `INTERACTS_WITH` | 直接相互作用记录（平铺）         | 与机理链联立         |

### 2.3 ⚠️ 两个必须知道的图数据陷阱（不读会写出错的功能）

**陷阱一：`INTERACTS_WITH` 在库里是单向的，镜像只在出口侧生效。**

Neo4j 里只有 2,534 条原始单向边；`graph/orientation.py` 的 `mirror_edge` 在
**查询出图时**合成反向边。因此：

- 经 `/reason`、可视化导出 → 能看到镜像，华法林能查到它的 530 条相互作用；
- **`/query` 原样执行调用方 Cypher → 看不到镜像**，
  `MATCH (d:Drug {id:"DB00682"})-[:INTERACTS_WITH]->()` 返回**空**。用 `cypher-shell`
  核对同样看到空——**这不是 bug，是设计**。

→ 方向一的查询如果走 `/query`，**必须自己写无向匹配 `-[r]-`**，不能依赖出站遍历。

**陷阱二：`INHIBITS` × `SUBSTRATE_OF` 的笛卡尔积会爆。**
`reasoning_limits.py` 专门记录：两者 join 会组合爆炸。多跳查询必须有 `LIMIT`
与超时预算（`statement_timeout` 15s，`SEMANTICA_DEFAULT_TIMEOUT_MS` 20s）。

### 2.4 Lucent 侧已有可复用的客户端

`src/modules/assistant/tools/ontology/semantica-client.service.ts` **已经存在且完备**：
带 bearer token、超时预算、热开关（`SEMANTICA_ENABLED`）、失败返回判别式结果
（区分「服务不可用」与「图上查不到」）。**不要重写**——缺的是把它从 `assistant`
之间「借」出来的合法路径（跨模块只能走 barrel 或 ADR-0009 的 reader port）。

### 2.5 另一个独立事实：本机 dev 的 Prisma 知识库确实是空的

这不影响 §四 的方案（那条路走 Neo4j），但**一旦要回填 Lucent 自己的药品详情接口
仍然需要**：

| 表                      | 实际行数 | 应有规模   |
| ----------------------- | -------- | ---------- |
| `drugbank_drugs`        | 100      | 19,842     |
| `drugbank_drug_targets` | **0**    | 10,009     |
| `drugbank_targets`      | **0**    | ~14,000    |
| `drugbank_structures`   | **0**    | 14,622     |
| `cn_medicine_products`  | **0**    | ≈205,000   |
| `medical_qa_chunks`     | **0**    | ≈1,350,000 |

→ 降级为**独立工作项**（§八 的 P4），不再是本计划的前置阻塞项。
另确认：`enzymes` 列在 Prisma 模型里**不存在**（PRODUCT.md §二 称其「已导入」是错的），
这类关系**只存在于 Neo4j**。

              ┌─────────────────────┼─────────────────────┐

## 四、地基：经 Neo4j 的关系查询

### 4.1 连接方式：直连 Neo4j（已裁决 2026-10-24）

**结论：Lucent 直连 Neo4j（Bolt），不经过 semantica。**

原先 `compose.graph.yaml` 写着「Lucent 从不直连 Neo4j」，ADR-0022 的许可分析也建立在
「经 HTTP 进程边界调用」上。重新评估后确认**这两条都不构成约束**：

| 顾虑                   | 实际情况                                                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 「架构决定禁止直连」   | 那是描述过去的实现，不是约束条款；已更正为「两条合法路径」（见 `compose.graph.yaml` 文件头）                               |
| 「GPLv3 需要法务评估」 | 触发条件是**产品对外交付**，与是否直连无关。Neo4j driver 是 Apache-2.0；semantica 同样用 driver 连自建实例，只换调用方进程 |
| 「技术效果不同」       | 不会。两边执行同一段 Cypher，直连反而少一个故障点                                                                          |

**直连的实质收益**：

- **超时自己定**。semantica 对端 `statement_timeout` 15s、客户端预算 20s；多跳机制查询
  容易慢，走 sidecar 等于把自己锁在别人的超时里。直连设 `transaction timeout` 即可。
- 少一跳网络、少一个进程依赖。
- 无需为复用客户端处理 `assistant` → `medicines` 的跨上下文依赖。

**代价**：Lucent 要持有 Neo4j 凭据（`NEO4J_URI` / `NEO4J_USER` / `NEO4J_PASSWORD`），
部署侧需打通 7687（安全组限源，与 5432/6379 同档处理）。

**semantica 的职责不变**：agent 生成 Cypher、`/reason` 规则推理仍走它。
直连只承接**业务只读查询**这一类。

> 不新开 ADR：本决定不改变图后端选型、sidecar 边界与部署拓扑，只是多了一个读图客户端。
> ADR-0022 的许可条款已就地补注（2026-10-24 修订）。

### 4.2 查询能力（端点设计）

按用户决定：**先在 `medicines` 模块内加读端点**，不新建 `workbench` 模块。

| 端点                                    | 入参                    | 出参                                             |
| --------------------------------------- | ----------------------- | ------------------------------------------------ |
| `GET /medicines/relations/interactions` | `drugbankIds[]`（2–10） | 两两之间的机制链（酶/靶点/转运体）+ 直接相互作用 |
| `GET /medicines/:id/relations`          | 单药 ID + `kinds?`      | 该药的 1 跳关系                                  |
| `GET /medicines/:id/substitutes`        | 单药 ID + `via`（酶）   | 不走该酶的其他同靶点药物（**替代候选**）         |

设计要点：

- **Cypher 由服务端构造，不接受调用方传入**。端点只接受 `drugbankIds` 这类**参数**，
  Cypher 是固定模板——否则等于把任意 Cypher 执行面暴露给公网客户端。
- **返回证据而不只是结论**：每条通路带 `enzyme` / `target` / `action` / `provenance`。
- **`substitutes` 的边界**：只给「不走该酶的同靶点药物**候选**」，不是处方建议。
- **必须设 LIMIT**：§2.3 陷阱二。
- **无向匹配**：§2.3 陷阱一——`INTERACTS_WITH` 在库里是单向的，查询必须用 `-[r]-`。

### 4.3 实现位置（ADR-0024 四层）

```text
src/modules/medicines/
├── domain/relations/
│   ├── relation.ts           # RelationKind 值对象、DrugRelation 实体
│   └── relations.ts          # RelationsReader port（只读）
├── application/use_cases/
│   └── query-relations.ts    # 编排：ID → 固定 Cypher 模板 → 归一结果
├── adapters/http/
│   ├── dto/relations.ts
│   └── presenters/relations.ts
└── infrastructure/graph/
    ├── connection.ts         # neo4j-driver 驱动单例 + 只读 session
    └── relations.ts          # 实现 RelationsReader（固定 Cypher 模板）
```

约束：

- `domain/` 零依赖，不认识 Neo4j 类型。
- Cypher 模板**只在 `infrastructure/graph/relations.ts`**；与 semantica 不同，
  这里没有「调用方传 Cypher」的口子。
- 图查询失败要降级为**可区分的结果**（「图服务不可用」≠「图上查不到」），
  沿用 `SemanticaClientService` 的判别式返回风格，不要 catch 成「无风险」。

**文件命名**：kebab-case（2026-10-24 起全仓统一）。

### 4.4 环境变量

| 变量             | 说明                                  | 默认                    |
| ---------------- | ------------------------------------- | ----------------------- |
| `NEO4J_URI`      | Bolt 地址                             | `bolt://127.0.0.1:7687` |
| `NEO4J_USER`     | 用户名                                | `neo4j`                 |
| `NEO4J_PASSWORD` | 口令（**仅 `.env`，不进运行时快照**） | 无，缺失即视为未启用    |
| `NEO4J_DATABASE` | 图库名                                | `neo4j`                 |
| `NEO4J_ENABLED`  | 热开关（关闭时端点返回「未配置」）    | `false`                 |

需同步 `docs/reference/environment-variables.md` 与 `.env.*.example`。

## 五、方向一：机理冲突解释 + 替代建议

### 5.1 从「警告」到「决策」

| 现在                              | 改后                                                                              |
| --------------------------------- | --------------------------------------------------------------------------------- |
| 「布洛芬 + 华法林：增加出血风险」 | 「布洛芬抑制 CYP2C9，而华法林经 CYP2C9 代谢 → 华法林血药浓度升高 → 出血风险上升」 |
| 用户下一步不明                    | 「同为止痛但**不经 CYP2C9** 的其他药物：…（供与医生讨论）」                       |

差别在于：前者是**警告**，后者是**决策支持**。且这只有拥有关系数据的人能做——
通用 App 查不到「为什么」。

### 5.2 实现

- 输入：当前风险检查里 `type = 'interaction'` 的 finding（已有）。
- 对每条 finding，用 §四 的 `relations` 查询找出**两药之间的共同酶/靶点**。
- 输出：`finding` 上新增 `mechanism: { via, path[], evidence[] }`。
- **找不到机制时明确说「机制未收录」**，不要编造——这是可溯源性的底线。

### 5.3 契约影响

`medicineRiskFinding` 增加可选字段，向后兼容（患者端不读它也不受影响）。

## 六、方向二与方向三

### 6.1 方向二：用药全景（我在吃什么）

- 输入：`UserCurrentMedicine` 集合 → 解析成 `drugbankId`（已有解析链路）。
- 检测：
  1. **重复成分**：不同商品名、同一化合物（`ingredient-canonicalization.ts` 已有基础）
  2. **共同靶点/共同酶**：用 §四 的多药查询
  3. **多科室叠加**：有 `healthEventId` 关联时可以按来源分组
- 呈现：一个「用药全景」页面，优先突出**患者不知道的**（重复成分），而非已知的（说明书里的禁忌）。

### 6.2 方向三：半衰期感知的漏服提示（可并行）

- 不依赖图，只依赖 `half_life`（**需解析文本**，2,537 条中部分是「4-6 hours」这类范围）
- 输入：`UserMedicineDoseLog.scheduledFor/scheduledTime/takenAt`
- 逻辑：漏服时长 ÷ 半衰期 → 判断缺口是否已影响稳态浓度
- **风险**：会变成「更烦人的提醒」。设计约束——只在缺口**跨越一个半衰期以上**才提示，
  且每天最多一次。

## 七、两端呈现的差异（必须提前定）

同一套后端能力，两端形态完全不同：

| 维度     | Lumine（分析者）           | Luminous（患者）          |
| -------- | -------------------------- | ------------------------- |
| 信息密度 | 全量证据链、可溯源、可导出 | 一个明确动作              |
| 机理展示 | 完整通路图 + 每条边的来源  | 一句话解释「为什么」      |
| 替代建议 | 候选列表 + 排除理由        | 一条建议 + 「与医生讨论」 |
| 交互     | 自由探索、可下钻           | 卡片式、不可下钻          |

**风险**：如果一开始就按「两边都要」设计一个中间形态，会两边都不好用。
建议：**后端契约保持中性**（返回结构化证据），两端各自包装，不共享展示层逻辑。
